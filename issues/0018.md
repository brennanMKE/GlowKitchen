# 0018 — COLORLOOP crawls too slowly to read as animation, and stops entirely when color change is disabled

| | |
|---|---|
| **Status** | resolved |
| **Module** | LED / Rendering |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-26 |
| **Closed** | 2026-08-28 |

## Description

`EFFECT_COLORLOOP` advances its hue by **±1 per tick**, which on hardware reads as a static color rather than a loop. Observed on a 10-LED strip at default `speed=128`: "pink on every LED… not animating unless it is slow" — `hueIndex` took roughly **30 seconds** to traverse a 3-color palette. Separately, when `colorChangeEnabled` is false the effect converges on one hue and goes **completely static**.

## Long Description

Carved out of [#0015](0015.md) after on-device verification. The renderer is correct — it was confirmed cycling `0 → 1 → 2 → 0` in the heartbeat log — but the rate makes it useless as a visible effect, and it is the one mode of the seven that does not read as animated.

### Why it crawls

`renderColorloop()` in `src/effects.h` steps one hue unit per tick:

```c
s.effectTimeout = now + speedInterval(s.speed, 60, 2);
...
hue = (fwd <= bwd) ? (uint8_t)(hue + 1) : (uint8_t)(hue - 1);
```

Hue distance between adjacent palette entries is whatever the colors happen to be — for well-separated colors that is often 80–128 units, so a single transition takes 80–128 ticks. The measured result was ~10 s per color and ~30 s for a full 3-color cycle.

`speed` only modulates the tick interval (60 ms → 2 ms), so even `speed=255` merely takes the full cycle from ~30 s to ~1 s across the whole palette while spending most of that time in transit between colors rather than on them. The step size, not the interval, is the wrong knob.

### The static case

```c
if (hue == target && s.colorChangeEnabled) {
    s.effectPhase = (s.effectPhase + 1) % s.colorCount;
```

With `colorChangeEnabled == false` the target never advances. The hue walks to the first palette entry and then stays there forever — a "color loop" that displays one color. Flagged independently by the Opus review of [#0015](0015.md).

### Also worth settling

[#0015](0015.md)'s plan called COLORLOOP's `intensity` knob (saturation, `128 + intensity/2`) "the weakest" of the seven and nominated it as the first thing to cut if flash got tight. Flash did not get tight — 81,392 bytes remain — so the knob survives, but if this renderer is reworked, reconsider whether saturation is the right thing for `intensity` to control here.

## Expected behavior

At default `speed`, COLORLOOP visibly cycles the whole strip through its palette at a rate a person reads as animation — seconds per color, not tens of seconds. With `colorChangeEnabled` false it should either keep looping (the mode's entire purpose) or be documented as intentionally frozen.

## Actual behavior

Reads as a static color. Full 3-color cycle takes ~30 s at default speed; with `colorChangeEnabled` false it never leaves the first color.

## Notes

- Not demo-blocking: the other six modes read correctly on hardware. CHASE and PULSE were both confirmed good by eye.
- Likely fix is a step size scaled from `speed` (and possibly from the hue distance to target) rather than a fixed ±1, so `speed` controls perceived rate instead of only tick frequency. Whatever is chosen, the `speed`→rate mapping should be documented with endpoints the way [#0015](0015.md)'s plan pinned the other six.
- The `colorChangeEnabled` interaction deserves an explicit decision rather than falling out of the code. Every other renderer treats that flag as "should the palette advance"; for COLORLOOP that is the whole effect.
- Whatever lands needs a native test that can actually fail — see [#0008](0008.md) and [#0014](0014.md) for what happens when it can't.

## Relation

- Carved out of: [#0015](0015.md) — the seven new render modes.
- Parent: [#0013](0013.md) — ad hoc custom effects umbrella.

## Fix

Two changes in `renderColorloop()` (`src/effects.h`), both in the hue walk:

1. **Step size scales with `speed`** — `1 + (speed * 11) / 255`, so 1 at speed 0
   and 12 at speed 255, replacing the fixed `+/-1`. `speed` now controls the
   perceived rate rather than only the frame cadence, which was the actual
   defect: the interval knob could not compensate for a step size stuck at 1
   while hue gaps between palette entries run 80-128 units. At the default
   speed 128 the step is 6 every ~31 ms, crossing a 128-unit gap in ~0.7 s.
   The walk snaps to the target when `dist <= step` so a larger step cannot
   overshoot and orbit.
2. **`colorChangeEnabled` is deliberately ignored here**, unlike every other
   renderer. Elsewhere that flag means "should the palette advance"; for
   COLORLOOP advancing the palette *is* the effect, so honouring it parked the
   hue on the first entry forever. Settled explicitly per this ticket's Notes
   rather than left to fall out of the code.

The `intensity`-as-saturation knob was left alone — this ticket's "also worth
settling" item. It works, costs nothing now that flash is not tight, and
changing it would be a separate behavioural change with no reported problem
behind it.

## Verification

```
pio test -e native            # 91 test cases: 91 succeeded (87 before, +4 here)
pio run -e esp32c3            # SUCCESS -- firmware.bin 1,236,192 bytes
pio run -e esp32c3-debug      # SUCCESS, flashed to the dev board over USB
```

Four new gates in `test/test_effects/test_effects.cpp`, each derived from the
arithmetic that produced the bug rather than from its appearance:

| Test | Asserts |
|---|---|
| `test_colorloop_completes_cycle_at_default_speed` | >= 3 palette entries reached in 3 s at speed 128 |
| `test_colorloop_speed_changes_perceived_rate` | speed 255 reaches strictly more entries than speed 0 in the same window |
| `test_colorloop_loops_with_color_change_disabled` | still cycles with `colorChangeEnabled == false` |
| `test_colorloop_lands_exactly_on_palette_hues` | every phase advance lands exactly on a palette hue (no overshoot) |

**Deliberate-perturbation proof** — the standard this project failed three
times ([#0008](0008.md) rounds 2-3, [#0014](0014.md) round 1, [#0017](0017.md)
round 1) and the one this ticket's Notes demanded:

- Restoring the old `step = 1`: `test_colorloop_completes_cycle_at_default_speed`
  **FAILED** ("reached 2 palette entries in 3 s; want >= 3") and
  `test_colorloop_loops_with_color_change_disabled` **FAILED** (same, 2 entries).
- Restoring `hue == target && s.colorChangeEnabled`:
  `test_colorloop_loops_with_color_change_disabled` **FAILED** ("reached 0
  entries in 3 s"), the other three passed — correctly, since that
  perturbation only affects the disabled-colour-change path.
- Reverting both: 91/91 again, `git diff --stat src/effects.h` clean of the
  perturbations.

**On hardware** (dev board `84fce68774a4`, `demo_effect.sh 84fce68774a4 loop 25`,
`EFFECT_TRACE` read through `scripts/monitor_serial.py`). First-LED RGB over
one run, sampled from the trace:

```
   7.7s  #221200   (yellow-red transit)
   9.2s  #003200   (green)
  10.7s  #04002e   (blue)
  12.2s  #25000d   (red)
  13.7s  #221200
```

A full 3-colour cycle in ~6 s at the preset's `speed=255`, against ~30 s
before. 24 distinct colours written across the 20 s captured — it reads as
animation, which is what this ticket asked for.

**Not verified:** how it looks to a person. The trace proves the hue is moving
at the intended rate and the colours are the palette's; it does not prove the
rate is *pleasant*. Worth one look at the strip before this is called done.
