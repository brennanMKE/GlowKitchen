# 0018 — COLORLOOP crawls too slowly to read as animation, and stops entirely when color change is disabled

| | |
|---|---|
| **Status** | open |
| **Module** | LED / Rendering |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-26 |

## Description

`EFFECT_COLORLOOP` advances its hue by **±1 per tick**, which on hardware reads as a static color rather than a loop. Observed on a 10-LED strip at default `speed=128`: "pink on every LED… not animating unless it is slow" — `hueIndex` took roughly **30 seconds** to traverse a 3-color palette. Separately, when `colorChangeEnabled` is false the effect converges on one hue and goes **completely static**.

## Long Description

Carved out of [#0015](0015.md) after on-device verification. The renderer is correct — it was confirmed cycling `0 → 1 → 2 → 0` in the heartbeat log — but the rate makes it useless as a visible effect, and it is the one mode of the seven that does not read as animated.

### Why it crawls

`renderColorloop()` in `src/effects.h` steps one hue unit per tick:

```c
s.effectTimeout = now + speedInterval(s.speed, 60, 2);
...
hue = (fwd <= bwd) ? (uint8_t)(hue + 1) : (uint8_t)(hue - 1);
```

Hue distance between adjacent palette entries is whatever the colors happen to be — for well-separated colors that is often 80–128 units, so a single transition takes 80–128 ticks. The measured result was ~10 s per color and ~30 s for a full 3-color cycle.

`speed` only modulates the tick interval (60 ms → 2 ms), so even `speed=255` merely takes the full cycle from ~30 s to ~1 s across the whole palette while spending most of that time in transit between colors rather than on them. The step size, not the interval, is the wrong knob.

### The static case

```c
if (hue == target && s.colorChangeEnabled) {
    s.effectPhase = (s.effectPhase + 1) % s.colorCount;
```

With `colorChangeEnabled == false` the target never advances. The hue walks to the first palette entry and then stays there forever — a "color loop" that displays one color. Flagged independently by the Opus review of [#0015](0015.md).

### Also worth settling

[#0015](0015.md)'s plan called COLORLOOP's `intensity` knob (saturation, `128 + intensity/2`) "the weakest" of the seven and nominated it as the first thing to cut if flash got tight. Flash did not get tight — 81,392 bytes remain — so the knob survives, but if this renderer is reworked, reconsider whether saturation is the right thing for `intensity` to control here.

## Expected behavior

At default `speed`, COLORLOOP visibly cycles the whole strip through its palette at a rate a person reads as animation — seconds per color, not tens of seconds. With `colorChangeEnabled` false it should either keep looping (the mode's entire purpose) or be documented as intentionally frozen.

## Actual behavior

Reads as a static color. Full 3-color cycle takes ~30 s at default speed; with `colorChangeEnabled` false it never leaves the first color.

## Notes

- Not demo-blocking: the other six modes read correctly on hardware. CHASE and PULSE were both confirmed good by eye.
- Likely fix is a step size scaled from `speed` (and possibly from the hue distance to target) rather than a fixed ±1, so `speed` controls perceived rate instead of only tick frequency. Whatever is chosen, the `speed`→rate mapping should be documented with endpoints the way [#0015](0015.md)'s plan pinned the other six.
- The `colorChangeEnabled` interaction deserves an explicit decision rather than falling out of the code. Every other renderer treats that flag as "should the palette advance"; for COLORLOOP that is the whole effect.
- Whatever lands needs a native test that can actually fail — see [#0008](0008.md) and [#0014](0014.md) for what happens when it can't.
