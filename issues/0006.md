# 0006 — A bad OTA release has no automatic fallback; devices must be recovered by hand

| | |
|---|---|
| **Status** | open |
| **Module** | OTA / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-15 |

## Description

If a release boots badly, nothing brings it back. The firmware never marks the new image valid or invalid, so the ESP32's built-in A/B rollback is effectively disabled and a broken build sticks. Recovery is a ladder and a USB cable, per device. The good news: the prebuilt bootloader **already** has rollback compiled in, so this is fixable in app code and shippable over OTA.

## Long Description

### What is already available

Verified in the installed toolchain — no bootloader change and no USB reflash required:

```
# framework-arduinoespressif32-libs/esp32c3/sdkconfig
CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y
CONFIG_APP_ROLLBACK_ENABLE=y
CONFIG_BOOTLOADER_WDT_ENABLE=y
CONFIG_BOOTLOADER_WDT_TIME_MS=9000
```

With rollback enabled, an image written by OTA boots in state `ESP_OTA_IMG_PENDING_VERIFY`. Something must then declare it good; if the device resets first, the bootloader automatically reverts to the previous slot.

### Why it currently does nothing

The Arduino core resolves that pending state itself, at startup, before any project code runs (`cores/esp32/esp32-hal-misc.c`):

```c
bool verifyRollbackLater() __attribute__((weak));
bool verifyRollbackLater() { return false; }
...
if (!verifyRollbackLater()) {
    if (ota_state == ESP_OTA_IMG_PENDING_VERIFY) {
        if (verifyOta()) {
            esp_ota_mark_app_valid_cancel_rollback();
        } else {
            esp_ota_mark_app_invalid_rollback_and_reboot();
        }
    }
}
```

`verifyRollbackLater()` is **weak** and returns `false` by default, so the core marks every freshly-flashed image valid within milliseconds of boot — long before it is known whether WiFi works, MQTT connects, or the LEDs render. The rollback machinery is present but has already committed by the time it could be useful.

### The fix

Override the weak symbol in `src/main.cpp` and take ownership of the decision:

```cpp
// Defer the OTA commit decision to our own health check instead of letting the
// Arduino core mark every new image valid at boot.
bool verifyRollbackLater() { return true; }
```

Then, once the device has demonstrably come up healthy, commit:

```cpp
esp_ota_mark_app_valid_cancel_rollback();
```

A reasonable health gate, in increasing order of confidence:

1. WiFi associated and an IP obtained
2. MQTT connected and subscribed
3. at least one `FastLED.show()` completed
4. all of the above sustained for a soak period with no reset

Given [#0003](0003.md) — where MQTT is healthy while the LEDs are not — condition 3 is worth including rather than stopping at MQTT.

Until `esp_ota_mark_app_valid_cancel_rollback()` is called, **any** reset reverts to the previous firmware: a crash, a panic, the task watchdog, or the bootloader WDT at 9 s. That covers the realistic bad-release failure modes without writing a boot-loop counter by hand.

### The one failure mode this does not cover

An image that comes up, passes the health check, commits — and only then misbehaves. Once marked valid there is no automatic path back, so a bad-but-bootable release still needs the canary gating in [#0001](0001.md). This issue is the single-device foundation that [#0001](0001.md) calls Stage 1; it is worth landing on its own because it is small and independently useful.

### Care required

- A soak period that outlasts the commit means a device that legitimately reboots (power blip) during the window reverts to older firmware unexpectedly. Keep the window short — tens of seconds, not minutes.
- `OTA_URL` pushes go through the same path, so a broken local dev build also auto-reverts. That is desirable, but it means a dev build that deliberately never reaches the health gate will be rolled back — which will look like the push "didn't take". Log the commit clearly.
- The rollback target is whatever is in the other slot, which after several local pushes may not be what you expect. Log both the running and previous partition at boot.

## Expected behavior

A release that fails to come up healthy is automatically replaced by the previous working firmware on the next reset, with no physical access.

## Actual behavior

The Arduino core marks every OTA image valid at boot before its health is known. A release that boots into a broken state stays there permanently and must be recovered over USB, per device.

## Notes

- Nothing here requires a bootloader change, so it ships over OTA like any other release.
- `esp_ota_get_running_partition()` / `esp_ota_get_last_invalid_partition()` are useful for logging what rolled back and why; surfacing the running partition label in `publishState()` would make a fleet-wide rollback visible from `list_devices.sh`.
- Pairs naturally with the newer-only version comparison noted in [#0001](0001.md): without it, a rolled-back device sees the bad release as "different" and re-installs it on the next check, producing an update/rollback loop.
