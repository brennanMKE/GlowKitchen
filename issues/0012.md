# 0012 — No remote recovery: any wedged device requires a physical power cycle

| | |
|---|---|
| **Status** | open |
| **Module** | Firmware / Reliability / MQTT |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-16 |

## Description

When a strip stops working there is currently no way to recover it except walking to it and pulling power — which for `kitchen` means a ladder. This happened three separate ways in a single day. Build a recovery ladder so a device can always be brought back over the network: an MQTT `RESTART`, a task watchdog that catches a blocked main loop, and a connectivity watchdog that catches a device that is up but unreachable.

## Long Description

### What actually happened, and what each case needed

| failure | symptom | recoverable remotely today? | what would have fixed it |
|---|---|---|---|
| `millis()` rollover stranded `slowBlend()` ([#0008](0008.md)) | LEDs frozen, MQTT perfectly healthy | **no** | MQTT `RESTART` |
| `checkForOtaUpdate()` hung on `tv` and `kitchen` | device vanished from the broker entirely | **no** | task watchdog |
| device up but never reconnects to WiFi/MQTT | invisible, LEDs may still animate | **no** | connectivity watchdog |

Four strips sat frozen for days in the first case **while answering `STATUS` the entire time** — connected, responsive, taking configuration changes, with only the render timer stuck. A single reboot command would have fixed all four without anyone leaving their chair. Two more devices were then lost to the second case and needed a physical trip.

The distinction that matters: **an MQTT command recovers logic that is stuck while the loop still runs. Only a watchdog recovers a loop that has stopped running.** Neither substitutes for the other, which is why this needs to be a ladder rather than one feature.

### Layer 1 — MQTT `RESTART`

```
lights/kitchen/cmd  →  RESTART
```

Publish state, flush the UART, brief delay so the MQTT ack goes out, then `ESP.restart()`.

Restrict it to **device-specific topics**, not `lights/all/cmd`, exactly as `OTA_URL` is. Rebooting the whole installation at once is occasionally what you want and occasionally what you very much do not, and a retained or mistyped broadcast should not be able to do it. A deliberate fleet reboot is five commands.

Recovers: any state that a fresh boot clears — the rollover freeze, a corrupted render state, a stale configuration. Does **not** recover a device that is no longer reading MQTT.

### Layer 2 — task watchdog, for a blocked loop

The parts are already compiled into the framework and completely unused:

```
CONFIG_ESP_TASK_WDT_EN=y
CONFIG_ESP_TASK_WDT_INIT=y
CONFIG_ESP_TASK_WDT_PANIC=y
CONFIG_ESP_TASK_WDT_TIMEOUT_S=5
CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y
```

`src/main.cpp` contains **zero** references to `esp_task_wdt`. The Arduino loop task is not subscribed, so nothing watches it. Subscribing it (`esp_task_wdt_add(NULL)`) and resetting it each iteration turns a hung `loop()` into an automatic reboot instead of a ladder.

**The critical design point — feeding it during legitimate long operations.** An OTA download blocks `loop()` for tens of seconds, far past any sane watchdog timeout. The answer is already in the code: `httpUpdate.onProgress()` fires every ~4 KB. Feeding the watchdog *there* gives exactly the behaviour wanted:

- a download that is **progressing** keeps the watchdog fed → no reset
- a download that has **stalled** stops feeding it → reset and recover

That is precisely the `tv` / `kitchen` failure, and it would have healed itself in seconds.

`ensureWifi()` is the other blocker — a 30-second `while` loop that would trip the watchdog on the first WiFi drop. It should be made non-blocking regardless ([#0008](0008.md) notes it as the largest contributor to the rollover stranding window); short of that it must feed the watchdog inside its wait.

Getting the timeout right matters more than the feature: too short and normal operation reboots the fleet, which is far worse than the problem being solved. Pick it from measured worst-case loop time, not from a guess, and validate on a device before it ships anywhere near `kitchen`.

### Layer 3 — connectivity watchdog

A device that boots, renders, and never reaches the broker is invisible and unrecoverable — no command can reach it by definition. If WiFi or MQTT has been down continuously for N minutes (10–15 is a reasonable start), reboot.

Two guards are essential:

- **Do not reboot-loop.** Count consecutive connectivity reboots in NVS and back off — a router that is genuinely down should not have five strips power-cycling every ten minutes for hours. Reset the counter on a successful MQTT connect.
- **Keep the lights on.** A strip that cannot reach the network should still render; losing WiFi is not a reason to go dark. The reboot is to recover connectivity, not to punish it.

### What remains physical, honestly

This ladder does not make USB obsolete:

- firmware that does not boot at all → needs bootloader-assisted rollback ([#0006](0006.md)) or USB
- a partition-table change → cannot be delivered by OTA, ever ([#0009](0009.md))
- corrupted flash → USB

The goal is to eliminate the cases we have actually hit, all three of which were recoverable in principle and none of which were recoverable in practice.

## Expected behavior

A misbehaving strip can be recovered over the network: by command when it is still listening, and automatically by watchdog when it is not. Physical access is reserved for genuinely unbootable firmware.

## Actual behavior

Every failure mode encountered so far has required walking to the device and pulling power, including one behind a ladder — even in cases where the device was online and responding to MQTT throughout.

## Notes

- Layers 1 and 2 are individually small. Layer 2 is the one that needs care, because a badly-tuned watchdog is a fleet-wide reboot loop — strictly worse than the bug it prevents.
- Worth adding uptime and reset reason (`esp_reset_reason()`) to `publishState()` as part of this. Without them there is no way to tell a watchdog reset from a power blip from a panic, and "did the watchdog fire?" is otherwise unanswerable remotely. This would also have shortened [#0003](0003.md) considerably — the whole diagnosis turned on uptime, which no device reports.
- These layers compose with [#0006](0006.md) rather than duplicating it: that issue recovers a *bad image*, this one recovers a *stuck device running a good image*.
