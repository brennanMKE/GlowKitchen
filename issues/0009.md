## Description

`v0.0.4` was published to GitHub as a normal release and **not one device could apply it**. `firmware.bin` was 1,340,544 bytes against a 1,310,720-byte OTA slot, so `Update.begin()` rejected it with "Not Enough Space" on every device, on every path, every time — and reported the failure only to serial. From MQTT the fleet looked like it was simply ignoring the update.

## Long Description

### How it got past everything

PlatformIO reported `Flash: 99.1% (used 1,298,274 bytes from 1,310,720)` — a pass. That figure is the sum of **loadable ELF sections**. The artifact that actually gets flashed adds the ESP32 image header, per-segment headers, padding, and an appended SHA-256: **42,270 bytes** of overhead the size check never accounts for.

So the build says "fits" while the file on disk does not. The only honest measurement is `stat` on `firmware.bin`.

### Why it was invisible

Nothing on the OTA path reports to MQTT. `checkForOtaUpdate()` logs to serial and returns; a failure is indistinguishable from "no update available" unless a device is on USB. Every diagnostic attempt — nightly check, boot check, manual `OTA_UPDATE` — produced silence, which was read as the trigger not firing rather than the update being rejected.

### This is not caused by this project's code

`v0.0.3` rebuilt on the current toolchain is **1,337,744 bytes — also 27,024 over**. The OTA feature added for [#0002](0002.md) accounts for only 2,800 bytes. The remaining ~27 KB arrived with the Arduino core update between June and August. The `0.0.3` running on the strips was built when the toolchain still produced a smaller image.

The corollary is uncomfortable: **the fleet had already drifted into a state where no release could be built that it could install**, and nothing would have revealed that until someone tried.

## Fix

Landed in `bc7e664`.

- **`scripts/release.sh`** builds the release environment and measures the real `firmware.bin`, refusing to proceed if it exceeds the OTA partition. It prints headroom, warns under 20 KB, and on success prints the exact publish commands — including the two release-shape traps (the asset must be named `firmware.bin`, and the release must not be marked pre-release, since GitHub excludes those from `/releases/latest`).
- **Debug/release environments** in `platformio.ini`: `esp32c3` at level 1 (OTA-installable) and `esp32c3-debug` at level 5 (USB only). The log level is a size decision, so it is now a build target rather than a file edit.

## Verification

- Negative test: forcing the `v0.0.4` configuration makes `release.sh` exit **1** with "REFUSING TO RELEASE: image is 29,856 bytes too large."
- Positive: the release env builds at 1,295,392 bytes, 15,328 spare, gate passed, and `firmware_info.sh` reads `0.0.5` from the image.
- Both environments build clean.

## Notes

- **15 KB of headroom is not a solution, it is a reprieve.** The next feature of any size breaches it again. The durable fix is `min_spiffs.csv` (1,966,080 per app slot, ~625 KB spare at full logging), but a partition table lives outside the app image and **cannot be delivered over OTA** — every device needs one USB flash. Worth bundling with the next time hardware is handled anyway.
- The gate hardcodes `0x140000`. If `board_build.partitions` is ever set, that constant must move with it.
- OTA failures still only reach serial. Publishing the last OTA result to MQTT would have made this obvious in minutes rather than hours — worth doing, and it pairs with the `DIAG` idea in [#0003](0003.md).
- `scripts/firmware_info.sh` still falls back to a heuristic because `FW_VERSION_MARKER` is absent from the image — tracked as item 5 of [#0004](0004.md).
