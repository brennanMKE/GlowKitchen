## Description

Phase 2 of [#0013](0013.md). Implement the seven `EffectMode` values that [#0014](0014.md) declares but leaves unimplemented, each modulated by `speed` and `intensity` (0–255, default 128). Chase first — it was the explicitly requested one — then the rest.

### 0. What this phase is, in one line

Fill in the seven `EffectMode` values [#0014](0014.md) declared but left unimplemented,
each driven by `timeReached()` and modulated by `speed`/`intensity` through **one
documented linear mapping per knob** — no magic curves — plus the three limitations
[#0014](0014.md) deferred here and the `docs/add_new_theme.md` rewrite.

### 1. Ground rules (read before writing a renderer)

1. **Hue space, not RGB.** `EffectState::colors` is `const uint8_t*` — a hue array —
   and stays that way. Every new renderer paints `CHSV(hue, sat, val)`. This is what
   [#0014](0014.md) chose deliberately (`renderBlend()`'s shortest-path arithmetic has
   no meaning on RGB triples) and what `customHues` (`src/effects.h`) bridges for
   `THEME_CUSTOM`.
2. **Index the palette as `s.colors[idx % s.colorCount]`, never raw.** `hueIndex` is
   clamped at load against whatever `getCurrentColorCount()` returned *then*; a palette
   change makes a stale index an out-of-bounds read. `renderFlicker()` indexes raw
   today — **do not change it** (compatibility promise), but all new code uses the
   modulo form.
3. **"Off" is `CHSV(hue, 255, 0)`, never `CRGB::Black` and never `fill_solid()`.**
   `CRGB::Black`/`fill_solid`/`fadeToBlackBy`/`nblend`/`random8`/`random16` do not
   exist in `test/test_effects/fastled_shim.h`, and using them breaks the native build
   — which is the only build an agent can actually verify. Value 0 is black on device
   regardless of hue, and it keeps the shim's store injective so the test can read the
   value byte back. **Allowed FastLED surface inside `src/effects.h`: `CRGB`, `CHSV`,
   `sin8`, `min`, `max`.** Needing anything else means extending the shim deliberately
   and saying so in `## Fix`.
4. **No `float`/`double` in the new renderers.** `renderBlend()` already drags in
   soft-float, so this is a size and determinism argument, not a linkage one: integer
   math is cheaper and byte-reproducible on the host.
5. **No new `lib_deps`.** Especially not ArduinoJson (see the umbrella).
6. **Bounds.** A renderer writes `s.leds[0 .. s.numLeds-1]` and nothing else.
   `leds[]` is `MAX_LEDS = 500` on device but `numLeds` defaults to 240 — a native
   test with a tight buffer is what catches an overrun, so write to exactly
   `numLeds`.
7. **Degenerate input guard.** First line of every new renderer:
   `if (s.numLeds <= 0 || s.colorCount <= 0 || !s.colors) return false;`
   `THEME_CUSTOM` with `colorCount == 0` is unreachable today thanks to
   [#0014](0014.md)'s boot guard, but [#0016](0016.md) can produce it, and `% 0` is a
   hard fault, not a glitch.

### 2. Timing — the [#0008](0008.md) constraint, restated

Every new renderer ticks off **one** deadline field, tested with
`timeReached(now, deadline)` from `src/time_utils.h`. Nothing else.

- **`EVERY_N_MILLISECONDS` and every other `EVERY_N_*` macro are forbidden.** They wrap
  `millis()` internally and sidestep the helper entirely — the [#0008](0008.md) freeze
  re-entering by the back door. There are currently zero uses in the firmware. Before
  committing, `grep -rn "EVERY_N" src/` and `grep -rnE "(<|>)\s*now\b|now\s*(<|>)" src/`
  and confirm every hit is deliberate.
- **Use `nowMs()`, not `millis()`, for the seven new modes.** `renderBlend()` already
  does; `renderFlicker()` deliberately does not (see [#0014](0014.md) `## Fix`). Going
  through `nowMs()` means the `SET_CLOCK_OFFSET` bench harness can drive a chase or a
  strobe to within seconds of the `2^32` wrap on real hardware, which is the only
  on-device rollover evidence available.
- **Therefore: the `SET_CLOCK_OFFSET` handler must also rebase the new timer.** It
  currently does `fx.blendTimeout = nowMs(); fx.rotateTimeout = nowMs();`. Add
  `fx.effectTimeout = nowMs();`. Omitting this reproduces [#0008](0008.md)'s round-2
  defect exactly: the offset jump strands the very timer the harness exists to move,
  the strip freezes for ~67 s, and an operator reasonably concludes the fix failed.
  **This code compiles only under `-DENABLE_CLOCK_OFFSET`, i.e. only in
  `[env:esp32c3-debug]` — a green `pio run -e esp32c3` will not catch a miss. Build
  both envs.**
- `SPARKLE`'s per-LED array holds brightness, not deadlines, so it needs no rebasing.
  One timer, one rebase line.

### 3. Where the state lives

#### 3a. `EffectState` grows; `LegacyEffectState` must not

Append a clearly delimited block at the **end** of `EffectState` in `src/effects.h`:

```c
    // ---- issue #0015 only. renderBlend()/renderFlicker() MUST NOT read any
    // field below this line, and test/test_effects/legacy_effects.h's
    // LegacyEffectState deliberately does not mirror them. See the plan in
    // issues/0015.md, section 3a.
    uint8_t    speed;          // per-frame input, 0-255 (128 = default)
    uint8_t    intensity;      // per-frame input, 0-255 (128 = default)
    uint32_t   effectTimeout;  // the ONE deadline the active renderer ticks off
    uint16_t   effectPhase;    // head position / cycle counter, per renderer
    uint8_t    effectSub;      // secondary counter, per renderer
    int8_t     effectDir;      // +1 / -1, SCAN only
    EffectMode lastMode;       // for the mode-change reset in loopLED()
    uint8_t*   sparkleVal;     // -> sparkleValues[MAX_LEDS], SPARKLE only
```

Sharing `effectPhase`/`effectSub`/`effectTimeout` across the seven is deliberate: only
one renderer runs at a time, the fields are 9 bytes total, and each renderer documents
what it uses them for in a comment directly above itself.

**Why `LegacyEffectState` does not grow.** It exists to be a *decoupled* mirror of only
the fields `BLEND`/`FLICKER` read — that decoupling is precisely what [#0014](0014.md)
round 2 added, after a shared struct type made a `blendOffset` widening invisible.
Adding `#0015` fields to it would re-couple the two types for no benefit: the legacy
renderers cannot read fields their frozen 2026-era source never mentioned.

**How to keep the two from drifting.** Three layers, in order of strength:

1. `runThemeDiff()` in `test_effects.cpp` already populates `LegacyEffectState`
   **field by field**, not by assignment. Adding fields to `EffectState` therefore
   cannot break it, and it must stay field-by-field.
2. The existing eight frame-diff cases are the live enforcement: if `renderBlend()`
   started reading `s.speed`, the legacy path has no such influence and the buffers
   diverge. **Caveat, stated honestly:** this only fires if the new field's value
   actually changes what BLEND does — reading `s.speed` and computing the same 100 ms
   at the default 128 would slip through.
3. So close it mechanically too: in `## Verification`, paste the output of
   `grep -nE "s\.(speed|intensity|effectTimeout|effectPhase|effectSub|effectDir|lastMode|sparkleVal)" src/effects.h`
   and confirm every hit is inside a `#0015` renderer, none inside `renderBlend()`
   or `renderFlicker()`.

#### 3b. New globals in `main.cpp`

```c
uint8_t sparkleValues[MAX_LEDS];   // ~500 bytes SRAM; wired to fx.sparkleVal in setupLED()
```
Seed `fx.sparkleVal = sparkleValues;` in `setupLED()` next to `fx.timeouts = timeouts;`.

#### 3c. Per-frame seeding and the mode-change reset

In `loopLED()`, alongside the existing `fx.*` seeding:

```c
const uint8_t EFFECT_DEFAULT_PARAM = 128;
fx.speed     = (currentTheme == THEME_CUSTOM) ? customEffect.speed     : EFFECT_DEFAULT_PARAM;
fx.intensity = (currentTheme == THEME_CUSTOM) ? customEffect.intensity : EFFECT_DEFAULT_PARAM;
```

Built-ins are `BLEND`/`FLICKER`, which ignore both — passing 128/128 is a definiteness
choice, not a behavior one, and it means a future built-in mapped to `CHASE` gets sane
defaults for free.

Then, before dispatch:

```c
if (mode != fx.lastMode) { resetEffectState(fx, nowMs()); fx.lastMode = mode; }
```

with, in `src/effects.h`:

```c
// Resets ONLY the #0015 fields. Must never touch blendTimeout, rotateTimeout,
// hueTimeout, blendOffset or timeouts[] -- doing so would change what BLEND and
// FLICKER do on a theme switch, i.e. regress #0014's compatibility promise.
inline void resetEffectState(EffectState& s, uint32_t now) {
    s.effectTimeout = now;
    s.effectPhase = 0;
    s.effectSub = 0;
    s.effectDir = 1;
    if (s.sparkleVal) for (int i = 0; i < s.numLeds; i++) s.sparkleVal[i] = 0;
}
```

`fx.lastMode` zero-initializes to `EFFECT_BLEND`, so a device booting into Green
(`FLICKER`) fires exactly one reset that touches nothing `FLICKER` reads. Confirm that
claim by re-running the frame-diff suite — it drives the renderers directly, never
`loopLED()`, so it will not catch a mistake here; the review should read this line.

### 4. Shared helpers (write these first — they are also the flash budget)

```c
// speed 0 -> slowMs, 255 -> fastMs, linear. One helper, endpoints documented per
// renderer, no undocumented curve anywhere.
inline uint16_t speedInterval(uint8_t speed, uint16_t slowMs, uint16_t fastMs) {
    return (uint16_t)(slowMs - (((uint32_t)(slowMs - fastMs) * speed) / 255));
}

// Paints `width` LEDs starting at `start`, wrapping around the strip if `wrap`,
// clamped to [0, numLeds) otherwise. Shared by CHASE and SCAN.
inline void paintRun(EffectState& s, int start, int width, uint8_t hue, uint8_t val, bool wrap);
```

`CHASE` and `SCAN` differ only in wrap-vs-bounce and their width ceiling; two copies of
the painting loop is the easiest ~400 bytes to waste in this phase.

### 5. The seven renderers

`base = min(s.maxBrightness, s.brightness)` throughout — the lit brightness of every
new mode, so `SET_BRIGHTNESS` keeps working. All `speed` endpoints below are **initial
values, tunable on a strip** (see §9); the *shape* — linear between two documented
endpoints via `speedInterval()` — is not negotiable, because that is what the ticket
means by "an undocumented magic curve is the thing that makes these impossible to tune
later".

#### Speed endpoints

| mode | slowMs (speed=0) | fastMs (speed=255) | @128 | one tick does | @240 LEDs, speed 128 |
|---|---|---|---|---|---|
| `CHASE` | 40 | 2 | 21 ms | head advances 1 LED | ~5.0 s per lap |
| `WIPE` | 40 | 2 | 21 ms | front advances 1 LED | ~5.0 s per full wipe |
| `SCAN` | 25 | 1 | 13 ms | eye advances 1 LED | ~3.1 s per sweep |
| `SPARKLE` | 60 | 5 | 33 ms | spawn + one fade step | — |
| `PULSE` | 40 | 4 | 22 ms | phase += 1 (256 = one breath) | ~5.6 s per breath |
| `STROBE` | 600 | 40 | 319 ms | one full on+off cycle | ~3.1 Hz |
| `COLORLOOP` | 60 | 2 | 31 ms | hue moves 1 unit toward target | ~1 s per 32 hue units |

Consequence to document, not to fix: the three position-based modes advance one LED per
tick, so their traverse time scales with `numLeds`. A 500-LED strip chases about twice
as slowly as a 240-LED one at the same `speed`. Making the step length strip-relative
is a defensible alternative but adds a divide per tick and a rounding decision; not
worth it here.

**`STROBE` has a hard floor of 40 ms (25 Hz) on its full cycle.** Faster is a
photosensitivity risk, is unpleasant, and is near the WS2812 refresh time for 240 LEDs
(~7.2 ms) anyway. The `speedInterval()` endpoints already enforce it; do not let a
later tuning pass go below it.

#### Intensity mappings — the deliverable

| mode | `intensity` modulates | formula | @0 | @128 | @255 |
|---|---|---|---|---|---|
| `CHASE` | run width | `w = 1 + ((uint32_t)intensity * (max(1, numLeds/4) - 1)) / 255` | 1 LED | 30 LEDs | 60 LEDs |
| `WIPE` | contrast of the un-wiped region | `vAhead = ((uint32_t)base * (255 - intensity)) / 255` | previous color at full brightness | ~50 % | black |
| `SCAN` | band width | `w = 1 + ((uint32_t)intensity * (max(1, numLeds/8) - 1)) / 255` | 1 LED | 15 LEDs | 30 LEDs |
| `SPARKLE` | density (spawns per tick) | `n = 1 + ((uint32_t)intensity * numLeds) / (255 * 48)` | 1 | 3 | 6 |
| `PULSE` | trough depth | `floorV = ((uint32_t)base * (255 - intensity)) / 255` | no visible pulse | dips to ~50 % | dips to black |
| `STROBE` | duty cycle | `onMs = clamp((uint32_t)period * intensity / 255, period/16, period*15/16)` | ~6 % on | 50 % on | ~94 % on |
| `COLORLOOP` | saturation | `sat = 128 + intensity/2` | pastel (sat 128) | sat 192 | pure (sat 255) |

Widths/counts are at `numLeds = 240`. Every one is a linear ramp with documented
endpoints; every one is monotone in `intensity`; none saturates to a no-op at either
end except where that *is* the intent (`PULSE` at 0, `WIPE` at 0).

Justifications where the spec is silent:

- **`CHASE` ceiling `numLeds/4`.** A run longer than a quarter of the strip stops
  reading as a travelling run and starts reading as a slow wipe. `SCAN`'s ceiling is
  half that because a Cylon eye wider than an eighth of the strip loses the "eye".
- **`WIPE` (the ticket says "— per spec").** I chose to give it a mapping rather than
  leave the knob inert: a user setting `intensity: 200` and seeing nothing change is
  worse than a documented choice. Contrast is the one continuous, cheap, visible
  property a wipe has that is not already `speed`. At 255 it is the classic
  wipe-onto-black; at 0 it is a soft recolour of the whole strip. One multiply per LED.
- **`SPARKLE` divisor 48.** Paired with a fade of 24 per tick (a sparkle lives ~10.6
  ticks), steady-state lit count is `spawns × 10.6` ≈ 32/240 (13 %) at default, 64
  (27 %) at 255, 10 (4 %) at 0. That is the range that reads as "sparkle" rather than
  "static" or "noise". The divisor and the fade step are a pair — change one, restate
  both in `## Fix`.
- **`COLORLOOP` (also "— per spec"). This is the weakest of the seven and the first
  thing to drop.** It is the only mode showing one flat colour at a time, so saturation
  is the only free axis; the floor of 128 exists because a fully desaturated strip is
  white, which defeats the point of a colour loop. If the reviewer objects, or if flash
  gets tight (§7), make it inert and say so — do not invent a second mapping.

#### Per-renderer algorithms

All seven follow the same skeleton:

```c
inline bool renderX(EffectState& s, uint32_t now) {
    if (s.numLeds <= 0 || s.colorCount <= 0 || !s.colors) return false;
    if (!timeReached(now, s.effectTimeout)) return false;
    s.effectTimeout = now + speedInterval(s.speed, SLOW_MS, FAST_MS);
    /* ... paint into s.leds[0 .. s.numLeds-1] ... */
    return true;
}
```

- **`CHASE`** — `effectPhase` is the head index. Paint the whole strip
  `CHSV(hue, 255, 0)`, then `paintRun(s, effectPhase, width, hue, base, /*wrap=*/true)`.
  Advance `effectPhase = (effectPhase + 1) % numLeds`. When it wraps to 0 and
  `colorChangeEnabled`, advance `s.hueIndex` (one palette entry per lap), which the
  caller copies back to the global exactly as `FLICKER` does today. `hue =
  s.colors[s.hueIndex % s.colorCount]`.
- **`WIPE`** — `effectPhase` is the front index. LEDs `0..effectPhase` get
  `CHSV(hue, 255, base)`; LEDs `effectPhase+1 .. numLeds-1` get
  `CHSV(prevHue, 255, vAhead)` where `prevHue = s.colors[(s.hueIndex + s.colorCount - 1) % s.colorCount]`
  — no extra state needed to remember the previous colour. Advance the front; on
  completion reset to 0 and advance `s.hueIndex` if `colorChangeEnabled`.
- **`SCAN`** — `effectPhase` is the eye position, `effectDir` is ±1. Clear, then
  `paintRun(s, effectPhase, width, hue, base, /*wrap=*/false)`. `effectPhase +=
  effectDir`; reverse `effectDir` at either end; advance `s.hueIndex` on each full
  round trip if `colorChangeEnabled`. Deliberately **no fading tail** — a uniform band
  keeps it distinct from `CHASE` by motion rather than shading, and saves the divide
  per LED. Adding a linear tail is an acceptable deviation if flash allows (§9).
- **`SPARKLE`** — every tick: fade all `sparkleVal[i]` by 24 (saturating at 0), then
  spawn `n` sparkles at `s.rng(0, s.numLeds)` by setting `sparkleVal[i] = 255`. Paint
  `s.leds[i] = CHSV(s.colors[i % s.colorCount], 255, (sparkleVal[i] * base) / 255)`.
  Deriving the colour from the LED index rather than at spawn time avoids a second
  `MAX_LEDS` array; a random colour per pop is an acceptable deviation at +500 bytes
  SRAM. **Uses `s.rng`, the injected function pointer — never Arduino `random()`
  directly**, so the native test stays deterministic.
- **`PULSE`** — whole strip one colour. `wave = sin8(s.effectSub)`;
  `v = floorV + (((uint32_t)(base - floorV) * wave) / 255)`. `effectSub++` per tick
  (wraps naturally at 256 = one breath); on wrap advance `s.hueIndex` if
  `colorChangeEnabled`.
- **`STROBE`** — `effectSub` is the on/off flag. On each deadline, toggle it, paint the
  strip `CHSV(hue, 255, effectSub ? base : 0)`, and set
  `s.effectTimeout = now + (effectSub ? onMs : period - onMs)`. Note this renderer sets
  its own deadline rather than using the skeleton's single line. Advance `s.hueIndex`
  on each off→on transition if `colorChangeEnabled`.
- **`COLORLOOP`** — `effectSub` is the current hue, `effectPhase` the target palette
  index. Per tick, step `effectSub` one unit along the **shortest path** toward
  `s.colors[effectPhase % s.colorCount]` (`uint8_t` arithmetic makes this two
  comparisons); on arrival, `effectPhase = (effectPhase + 1) % colorCount` and advance
  `s.hueIndex` to match. Paint the whole strip `CHSV(effectSub, sat, base)`. Equal
  adjacent palette entries (Green's array repeats) simply arrive immediately and move
  on. This walk is why `COLORLOOP` needs none of `renderBlend()`'s interpolation code.

### 6. Testing

The `[env:native]` harness exists and `fastled_shim.h`'s injective `CRGB::operator=(CHSV)`
is the enabler: a test can read the hue back from `leds[i].r`, the saturation from
`.g`, and the value from `.b`. There is no legacy counterpart for the seven, so the
frame-diff method does not apply; what follows is what *does*.

**Where the tests live.** Add them to the existing `test/test_effects/test_effects.cpp`
(one `main()`, one Unity suite). A second `.cpp` in the same folder would be a second
`main()`; a second *folder* is fine and is an acceptable deviation if the file gets
unwieldy — it would `#include "../test_effects/fastled_shim.h"`, and it is the reason
the `THEME_NAMES[]` linkage fix in §8 must land first.

**Gate 0 — the eight existing frame-diff cases must still pass, unchanged.** That is
the proof this phase did not disturb `BLEND`/`FLICKER`. Plus the grep in §3a.

**Gate 1 — `BUILTIN_EFFECT_MODE[]` self-selection ([#0014](0014.md) gotcha).** Two
changes, both needed:
  1. New `test_builtin_effect_mode_table()` asserting the table's contents against
     independent literals: `EFFECT_FLICKER` for `THEME_GREEN`, `EFFECT_BLEND` for the
     other five.
  2. Change the six `runThemeDiff()` call sites to pass the literal mode
     (`EFFECT_FLICKER` / `EFFECT_BLEND`) instead of `BUILTIN_EFFECT_MODE[THEME_X]`, so
     the diff no longer selects its renderer from the table it is meant to be
     independent of. Today a wrong table entry silently runs the same renderer on both
     sides and still passes.

**Gate 2 — bounds / no overrun (highest value).** For each of the seven: allocate
`CRGB buf[numLeds + 8]`, fill the 8-LED tail with a sentinel, run ~600 frames at a 5 ms
step, assert the tail is untouched after every frame. Sweep
`numLeds ∈ {1, 2, 7, 64, 240, 500}`, `intensity ∈ {0, 1, 127, 128, 254, 255}`,
`speed ∈ {0, 128, 255}`. Also assert the `colorCount == 0` and `numLeds == 0` guards
return `false` and write nothing. This is what catches an off-by-one in `paintRun()`'s
wrap, a width that exceeds the strip at `intensity = 255`, or a `SCAN` bounce that
steps one past either end.

**Gate 3 — rollover ([#0008](0008.md)).** For each of the seven, start at
`(uint32_t)(0u - 3000u)` and run 1200 frames at a 10 ms step, so the `2^32` wrap lands
at frame 300. Assert the renderer returns `true` at least once in every window of
`3 × expectedInterval / step` frames across the whole run. A renderer written with
`deadline < now` goes permanently silent after the wrap, so **this test can fail** —
and it is the single most important one in the suite.

**Gate 4 — determinism.** Two independent runs of each renderer with the same seed and
inputs produce identical frame sequences (per-frame `memcmp`). Catches an
un-injected RNG, uninitialized state, or anything reading a real clock.

**Gate 5 — monotonicity.** At `numLeds = 240`, `speed = 128`, sweep `intensity`
0→255 in steps of 15 and assert the per-mode metric is non-decreasing (or
non-increasing where noted), measured over 600 frames:
  - `CHASE`, `SCAN` — count of LEDs with value > 0 in a settled frame: increases.
  - `WIPE` — mean value of the un-wiped region: **decreases**.
  - `SPARKLE` — mean lit count over the run: increases.
  - `PULSE` — minimum value seen over one full breath: **decreases**; peak stays
    exactly `base` at every intensity.
  - `STROBE` — fraction of simulated milliseconds spent lit: increases, and lands
    within ±5 % of 0.50 at `intensity = 128`.
  - `COLORLOOP` — the saturation byte: increases.
  And one shared **speed** test: the number of `true` returns in a fixed 10 s window is
  non-decreasing in `speed`, for all seven.

**Gate 6 — palette coverage.** Over 6000 frames (60 s simulated) with
`colorChangeEnabled`, assert (a) every hue written is a member of the active palette —
except `COLORLOOP`, which walks between entries, where the assertion is that it
*reaches* every palette entry — and (b) every palette entry is used at least once.
Catches a `hueIndex` advance that never fires, wraps wrong, or indexes past the array.

**Prove the tests can fail.** [#0008](0008.md) and [#0014](0014.md) both bounced on a
test that could not fail. Repeat [#0014](0014.md)'s protocol for at least three
perturbations, paste the failing output in `## Verification`, then revert and show the
suite clean:
  1. `timeReached(now, s.effectTimeout)` → `s.effectTimeout < now` in one renderer →
     Gate 3 must fail after frame 300.
  2. `paintRun()`'s end index `<` → `<=` → Gate 2 must fail on the sentinel.
  3. Invert one intensity mapping (`255 - intensity` → `intensity`) → Gate 5 must fail
     for that mode only.
And state, per [#0014](0014.md)'s residual gotcha, that each gate proves only what its
window actually reaches — so justify the frame counts: 600 frames × 5 ms covers ~3
seconds, enough for `CHASE` to advance ~140 LEDs at default speed but **not** a full
240-LED lap, so the palette-coverage and lap-advance assertions need the 6000-frame
window, not the 600-frame one. Check that arithmetic against the final speed endpoints
before trusting Gate 6.

**What only a strip can confirm — be explicit about all of it in `## Verification`:**
  - Whether the effects *look* right: speed endpoints, whether 30 LEDs reads as a chase
    at 240, whether the strobe is tolerable, whether the sparkle density is pleasing.
  - The real `hsv2rgb_rainbow` conversion, gamma, and WS2812 output. The shim stores
    `{h,s,v}` and converts nothing.
  - **FastLED's power cap.** `setupLED()` calls
    `setMaxPowerInVoltsAndMilliamps(5, 500)`. `PULSE`, `STROBE` and `COLORLOOP` light
    the *whole strip* at `base` — far more current than `BLEND`'s gradient — so the
    limiter will scale global brightness down on those frames. `PULSE`'s peak may be
    clipped, and the modes may simply look dimmer than the native test's numbers
    suggest. Nothing native can see this; flag it as a hardware observation item.
  - Mirror-mode interaction. `loopLED()` mirrors every mode except `FLICKER`, so the
    new modes get mirrored when `mirrorEnabled`. That is probably desirable for
    `CHASE`/`SCAN` on a bi-directional strip and probably halves `SPARKLE`'s apparent
    randomness. **Do not change that dispatch line** — it is `BLEND`-shared and
    changing it risks regressing [#0014](0014.md). Note it and move on.
  - IR remote and every MQTT round-trip.

### 7. Flash budget — the live risk in this phase

Baseline after [#0014](0014.md): release `firmware.bin` = **1,226,976 bytes**; OTA slot
`0x140000` = 1,310,720 (`scripts/release.sh`, `OTA_PARTITION_SIZE`); headroom
**83,744 bytes**. The ticket's escalation line is ~40,000, i.e. a `firmware.bin` above
**1,270,720 bytes**. The debug env (1,273,376) does not fit OTA by design and does not
gate anything.

| + helpers + `EffectState` growth | | | |
| + `CHASE` | | | |
| … one row per renderer … | | | |

Also record the RAM figure PlatformIO prints — `sparkleValues[500]` adds ~500 bytes
static.

**Expectation:** 20–40 lines of integer math per renderer with two shared helpers should
cost roughly 400–900 bytes each, ~3–6 KB total, landing around 78,000 bytes of headroom.
**Any single renderer over ~2 KB means something went wrong** — a `float` crept in, a
helper got copy-pasted instead of shared, or a new FastLED symbol got pulled in. Stop
and investigate at that row rather than at the end.

**If headroom drops below 40,000:** stop, report it in `## Verification`, and raise it
with the orchestrator before continuing. Remedies in order of preference:
  1. Drop the `COLORLOOP` saturation knob and the `SCAN` tail (if added).
  2. Merge `CHASE` and `SCAN` into one parameterized renderer — they differ only in
     wrap-vs-bounce and their width ceiling.
  3. Merge `STROBE` into `PULSE` as a square-wave variant.
  4. **Do not** silently change the partition scheme. That is [#0009](0009.md) /
     [#0004](0004.md) item 6, it needs a USB pass on every device, and it belongs to the
     umbrella, not to this ticket.

### 8. The three [#0014](0014.md) deferred items

Do items 1 and 2 **first**, before any renderer — item 1 is what makes a second test
translation unit safe, and item 2 is a five-minute test that could invalidate the
harness the rest of the phase leans on.

1. **`THEME_NAMES[]` linkage** (`src/themes.h`). `const char* THEME_NAMES[]` has
   external linkage; a second linked TU including the header is a duplicate-symbol
   error. Change to `static const char* const THEME_NAMES[]`. The existing
   `static_assert` and all indexing sites are unaffected.
   Same file, related: `static uint8_t customHues[]` in `src/effects.h` gives every
   including TU its **own** copy — harmless today (the test never reads it) but silently
   wrong the moment two TUs expect to share it. Preferred fix: leave it `static` and add
   an explicit invariant comment — *"`src/effects.h` is included by exactly one firmware
   translation unit; adding a second `.cpp` under `src/` requires moving `customHues`
   into `main.cpp` behind an `extern` declaration."* Optional, and genuinely correct if
   the toolchain takes it: a C++17 `inline uint8_t customHues[MAX_CUSTOM_COLORS];`,
   which gives one shared definition. `[env:native]` already sets `-std=gnu++17`; the
   Arduino-ESP32 core may not. It is a 30-second experiment — if `pio run -e esp32c3`
   accepts it, take it; if not, take the comment and say so.
2. **`BUILTIN_EFFECT_MODE[]` is unverified.** Fixed by Gate 1 in §6.
3. **`docs/add_new_theme.md`** — see §10.

### 9. Order of work

Each step builds, tests green, and is independently committable on `issue/0015`.

0. **Prep.** Deferred items 1 and 2 (§8). Baseline build + size. Add the
   `EffectState` block, `sparkleValues[]`, the `loopLED()` seeding and mode reset, the
   `SET_CLOCK_OFFSET` rebase line, and the two shared helpers. Build **both** envs.
1. **`CHASE`** — explicitly the requested effect, and it establishes every pattern:
   `speedInterval()`, `paintRun()`, the head-advance skeleton, `hueIndex` reuse, and
   the first cut of Gates 2–6. The most expensive step by far, and everything after it
   is cheaper because of it.
2. **`SCAN`** — reuses `paintRun()` and the head machinery. Doing it second is a
   deliberate check that the helper *is* shared: its flash delta should be markedly
   smaller than `CHASE`'s. If it isn't, the helper isn't doing its job.
3. **`WIPE`** — same skeleton, different painting; introduces the previous-colour idea.
4. **`PULSE`** — first whole-strip mode, introduces the `sin8` phase machinery.
5. **`STROBE`** — reuses `PULSE`'s whole-strip painting with a square wave; validates
   the duty-cycle mapping against Gate 5's ±5 % assertion.
6. **`SPARKLE`** — needs the per-LED array and the injected `rng`, so its RAM and flash
   costs are isolated and attributable rather than mixed into an earlier step.
7. **`COLORLOOP`** — last, because its intensity mapping is the weakest and it is the
   designated first thing to trim if §7 escalates.
8. **Docs** (§10), final size measurement, `## Fix` / `## Verification` writeup.

### 10. `docs/add_new_theme.md` — the rewrite

The current step 1 is actively wrong: appending `THEME_YOUR_THEME = 6` collides with
`THEME_CUSTOM`. Rewrite around the `(EffectMode, hue array)` model:

- **Reframe the opening.** A theme is a `(EffectMode, hue array)` pair. Drop the
  "two types of themes: Green and Other" framing entirely — that was the old
  `if (currentTheme == THEME_GREEN)` dispatch, which no longer exists.
- **Where things live now:** `src/themes.h` (the `HueTheme` enum, `THEME_NAMES[]`, the
  hue arrays and counts), `src/effects.h` (`EffectMode`, `BUILTIN_EFFECT_MODE[]`,
  `getCurrentEffectMode()`, every renderer), `src/main.cpp` (the accessors, the MQTT
  dispatch, `getThemeMqttCommand()`). Mention that `effects.h` includes `themes.h` and
  never the reverse, and why.
- **Step 1, corrected:** insert the new theme **before `THEME_CUSTOM`**, and bump
  `THEME_CUSTOM`, `THEME_COUNT` **and** `CYCLEABLE_THEME_COUNT`. Name the two
  `static_assert`s that will catch a half-done job.
- **Step 2:** insert the `THEME_NAMES[]` entry at the matching index — before
  `"Custom"`, not appended.
- **New step:** add the matching `BUILTIN_EFFECT_MODE[]` entry, chosen from the nine
  modes. This is the step that did not exist before [#0014](0014.md).
- **Steps for the accessors, the MQTT string, and `getThemeMqttCommand()`** — mostly as
  they are, with the current names.
- **New step:** add a fixture to `THEMES[]` in `test/test_effects/test_effects.cpp`.
  `static_assert(NUM_THEME_FIXTURES == CYCLEABLE_THEME_COUNT)` fails the native build
  otherwise — a real trap worth documenting rather than letting someone rediscover.
- **New section: the nine effect modes**, with the speed and intensity tables from §5.
  This doc becomes their single source of truth; `## Fix` should point at it rather
  than duplicating the numbers a third time.
- **New caution — persisted theme indices shift.** `currentTheme` is stored in NVS as a
  raw index. Inserting a theme before `THEME_CUSTOM` moves `THEME_CUSTOM` from 6 to 7,
  so a device that upgrades over OTA with a persisted `6` boots into the *new* theme
  rather than custom. That is what `SETTINGS_VERSION` ([#0016](0016.md)) is for; until
  it lands, appending at the end of the *cycleable* range is the only safe insertion
  point and even that shifts `THEME_CUSTOM`.

### 11. Driving verification before [#0016](0016.md) lands

Nothing can *set* these modes over MQTT yet. Three mechanisms, in the order the
implementer should reach for them:

1. **The native harness** — primary, and the only one an agent can actually run. Gates
   0–6 exercise all seven renderers with real palettes and real parameter sweeps
   without a board.
2. **A debug-only forced-effect hook**, for the bench pass. `DEV_THEME_OVERRIDE` is
   bounded to `0..CYCLEABLE_THEME_COUNT-1` and cannot reach `THEME_CUSTOM`, so add a
   block in `setupLED()` guarded by a **new `-DDEV_FORCE_EFFECT` flag set only in
   `[env:esp32c3-debug]`** that populates `customEffect` (mode, 2–3 colours,
   `colorCount`, `speed`, `intensity`), calls `refreshCustomHues()`, and sets
   `currentTheme = THEME_CUSTOM`. This mirrors the `ENABLE_CLOCK_OFFSET` precedent
   exactly: the debug env is already USB-only and already over the OTA size gate, and
   the release build must not contain a byte of it. Confirm that by checking the
   release `firmware.bin` size is unchanged by the addition. A temporary uncommitted
   local edit is the alternative, but it makes the bench pass unreproducible later —
   prefer the flag.
3. **A `SET_EFFECT` stub** — explicitly **out of scope**. That is
   [#0016](0016.md)'s ticket and adding a partial parser here would pre-empt its
   validation and NVS-versioning design.

Be honest in `## Verification`: if no board is available, the bench pass is a **bail**
per `issues/Issues.md` — name what could not be verified, do not call it a pass.


### 13. Uncertainties, and where the implementer may deviate

- **Speed endpoints (§5).** Chosen from arithmetic about traverse times, not from
  looking at a strip. Retune freely on hardware; keep the linear `speedInterval()`
  shape and record the final numbers in `## Fix` and in `docs/add_new_theme.md`.
- **`COLORLOOP`'s saturation mapping.** The weakest of the seven. Drop it to inert if
  the reviewer objects or flash gets tight.
- **`SCAN`'s missing tail.** A linear falloff would look better and costs a divide per
  LED. Add it if the budget is comfortable after step 5.
- **`SPARKLE`'s colour derivation.** `i % colorCount` avoids a second `MAX_LEDS` array;
  a random palette pick at spawn time is nicer and costs ~500 bytes SRAM. Either is
  fine; say which.
- **Reusing `hueIndex` as the new modes' palette cursor.** It is consistent with
  `FLICKER`, needs no new field, and is already persisted and clamped. But it is also
  reported in the heartbeat log and saved to NVS, so a fast-advancing chase makes that
  value churn. If that reads wrong on a device, a dedicated `effectColorIndex` in the
  `#0015` block is a clean alternative — say which you did.
- **Test file layout.** One file vs. a second folder (§6).
- **`customHues` as an `inline` variable** vs. `static` plus a comment (§8).
- **Hue-only palettes are a real limitation these renderers inherit.**
  `refreshCustomHues()` runs custom `CRGB` colours through `rgb2hsv_approximate()` and
  keeps only the hue, so saturation and value are discarded: a "white" or pastel custom
  chase is not expressible today. That is [#0016](0016.md)'s problem, not this
  ticket's — but flag it to the orchestrator, because it constrains what `SET_EFFECT`
  can honestly promise.
- **Flash estimate.** ~3–6 KB total is my read; if the real cost runs 3× that, escalate
  at step 5 rather than discovering it at step 8.

## Long Description

Step 3 of the spec's build order. Each renderer operates on the active color array (built-in theme palette or `CustomEffectConfig.colors`) and must be driven by a `timeReached()` deadline.

| # | mode | behavior | `intensity` modulates |
|---|---|---|---|
| 2 | `CHASE` | a run of lit LEDs travelling along the strip | chase width |
| 3 | `WIPE` | color fills progressively from one end | — (per spec) |
| 4 | `SCAN` | Larson/Cylon — a band sweeping back and forth | band width |
| 5 | `SPARKLE` | random LEDs pop and fade | sparkle density |
| 6 | `PULSE` | breathing — whole strip fades up and down | depth of the fade |
| 7 | `STROBE` | hard on/off flashing | duty cycle |
| 8 | `COLORLOOP` | whole strip cycles through the colors | — (per spec) |

Where the spec doesn't pin down exactly what `intensity` means for a given mode, pick something defensible and **document the mapping in `## Fix`** — an undocumented magic curve is the thing that makes these impossible to tune later.

### Constraints

- **`timeReached()` only.** Seven new renderers are seven new chances to reintroduce the [#0008](0008.md) freeze. Do not substitute `EVERY_N_MILLISECONDS` — it wraps `millis()` internally and sidesteps the helper.
- **Flash budget.** Headroom was 84,000 bytes before this work started; seven renderers are the bulk of [#0013](0013.md)'s code growth. Report `firmware.bin` size in `## Verification` and flag it if headroom drops below ~40,000 bytes.
- **No regression to `BLEND`/`FLICKER`.** If [#0014](0014.md) landed a frame-capture harness, extend it to cover the new modes; if it settled on visual inspection, say so and note what could not be automated.

## Expected behavior

All nine modes render, each responding sensibly to `speed` and `intensity`. The six built-in themes are untouched.

## Actual behavior

Only `BLEND` and `FLICKER` have implementations; the other seven enum values render nothing.
