# 0005 — Nightly OTA check runs at 03:00 US Central instead of 15:00 Pacific

| | |
|---|---|
| **Status** | open |
| **Module** | OTA / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-15 |

## Description

The scheduled OTA check is hardcoded to the US Central timezone and to hour 3, so it fires at 03:00 Central — 01:00 Pacific. The devices are in San Francisco and the check is meant to run at **15:00 Pacific**, in the afternoon when someone is awake to notice a bad update, not in the middle of the night.

## Long Description

Two independent values in `loopOta()` are wrong:

```cpp
configTzTime("CST6CDT,M3.2.0,M11.1.0/2", "pool.ntp.org", "time.nist.gov");
...
if (now.tm_hour != 3) return;                  // only in the 03:xx hour
```

The timezone should be Pacific and the hour should be 15:

```cpp
configTzTime("PST8PDT,M3.2.0,M11.1.0/2", "pool.ntp.org", "time.nist.gov");
...
if (now.tm_hour != 15) return;                 // only in the 15:xx hour
```

The DST transition rule is unchanged — `M3.2.0,M11.1.0/2` (second Sunday in March, first Sunday in November at 02:00) is the same US rule for both zones. Only the base offset and abbreviation differ: `CST6CDT` → `PST8PDT`.

### Why the hour matters more than it looks

The current behavior is worse than a two-hour offset. At 01:00 Pacific the whole fleet updates while everyone is asleep, and because there is no canary or rollback ([#0001](0001.md), [#0006](0006.md)), a bad release means waking up to six dead strips — `kitchen` needs a ladder. Moving the check to 15:00 puts it in the middle of the afternoon, where a failure is noticed immediately and can be recovered the same day.

### Interaction with the once-per-day guard

The `ota_last_yday` guard in NVS keys off `tm_yday`, which is unaffected by the hour change. Changing 3 → 15 does not double-run on the changeover day: a device that already ran at 03:00 has stored today's yday and will skip the 15:00 window the same day, then resume normally the next.

Worth checking as part of this: the guard writes `ota_last_yday` *before* the check runs, deliberately (a successful update reboots and never returns). That is still correct at 15:00.

## Expected behavior

The scheduled check runs once per day at 15:00 America/Los_Angeles, correctly tracking PST/PDT.

## Actual behavior

It runs at 03:00 America/Chicago, i.e. 01:00 Pacific.

## Notes

- Two-line change, but it can only reach the fleet in a release. Fold it into the next one rather than cutting a release solely for this — the current schedule still works, it just runs at the wrong time.
- Consider making the hour a named constant (`OTA_CHECK_HOUR`) next to `STARTUP_OTA_DELAY_MS` rather than a bare literal in the middle of the scheduler.
- Verify after deploying by checking a device's clock rather than waiting a day: the firmware does not currently log local time. Adding the formatted local time to the existing heartbeat would make this trivially confirmable and is worth doing at the same time.
