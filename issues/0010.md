# 0010 — Replace the 69,876-byte Mozilla CA bundle with pinned GitHub roots

|---|---|

## Description

The firmware embeds the full Mozilla root store to validate exactly one vendor. It occupies **69,876 bytes** — measured from the linked image, `_binary_x509_crt_bundle_start` at `0x3c10dce8` to `_binary_x509_crt_bundle_end` at `0x3c11eddc`. Replacing it with the two roots GitHub actually chains to costs ~2 KB, recovering **~68 KB**: more than four times the entire remaining headroom of the current release.

## Long Description

### Why this is worth doing

`v0.0.5` ships at 1,295,920 bytes with **14,800 bytes spare** in the 1,310,720-byte OTA slot. One CA bundle is consuming five times the free space in the image. It is the single largest recoverable item, and unlike the partition change in [#0009](0009.md) it is **deliverable over the air** — no USB, no ladder.

### The trap: three hosts, two different roots

The OTA path touches three hostnames, and they do **not** share a trust root. Verified live on 2026-08-16:

| host | used for | top-of-chain root | expires |
|---|---|---|---|
| `api.github.com` | version check (`tag_name`) | Sectigo Public Server Authentication Root E46 | 2038-01-18 |
| `github.com` | the `/releases/latest/download/` redirect | Sectigo Public Server Authentication Root E46 | 2038-01-18 |
| `objects.githubusercontent.com` | **the actual firmware.bin download** | ISRG Root YR (Let's Encrypt) | 2032-09-02 |

Pinning only the root that `api.github.com` presents would let the version check succeed and then fail the download — the exact failure shape that already cost hours in [#0009](0009.md), because nothing on the OTA path reports to MQTT. **Both roots must be pinned.**

Note also that GitHub has already migrated from DigiCert to Sectigo. Root rotation is not hypothetical here; it has happened recently.

### Implementation

`WiFiClientSecure::setCACert()` takes a PEM string, and mbedTLS's parser accepts concatenated PEM blocks, so both roots go in one constant:

```cpp
// Pinned in place of the full Mozilla bundle (see issue #0010). Two roots are
// required: GitHub's API and web hosts chain to Sectigo, while the release
// asset is served from objects.githubusercontent.com, which chains to ISRG.
// Pinning only one lets the version check pass and the download fail.
static const char GITHUB_ROOT_CAS[] PROGMEM =
    "-----BEGIN CERTIFICATE-----\n"  // Sectigo Public Server Authentication Root E46
    ...
    "-----END CERTIFICATE-----\n"
    "-----BEGIN CERTIFICATE-----\n"  // ISRG Root YR
    ...
    "-----END CERTIFICATE-----\n";
```

Then `client.setCACert(GITHUB_ROOT_CAS)` replaces `client.setCACertBundle(...)` in both `checkForOtaUpdate()` and `performOtaFromUrl()`. The `rootca_crt_bundle_start` / `_end` externs go away, and with them the embedded blob.

Roots are pinned rather than leaves or intermediates: leaf certs rotate constantly (Let's Encrypt every ~90 days) and intermediates every few years, while these roots run to 2032 and 2038.

### The risk, and why it is acceptable here

If GitHub moves to a root that is not pinned, **every GitHub OTA path stops working at once, fleet-wide, silently**. That is a real failure mode and deserves to be stated plainly.

What makes it tolerable is that the escape hatch does not depend on TLS at all. `OTA_URL:` ([#0002](0002.md)) selects a plain `WiFiClient` for `http://` targets, so a LAN push carries no certificate validation whatsoever. Recovery from a broken pin is:

```bash
pio run                                  # build with the new roots
./scripts/ota_local.sh <device>          # push over the LAN, plain HTTP
```

No USB, no ladder — just network reach. That path is exactly why this trade is worth taking. Worth confirming it still works on a device *before* the pin ships, since it becomes the only remedy.

Two caveats on that safety net:

- It requires being on the same network as the strips, so it is not a remote fix.
- `OTA_AUTO:false` should be set on a device being recovered, or its startup check will keep retrying the broken GitHub path.

### Release-script gate

`scripts/release.sh` should refuse to publish a build whose pinned roots no longer match reality. For each of the three hosts:

1. Fetch the presented chain (`openssl s_client -connect <host>:443 -servername <host> -showcerts`).
2. Take the top-of-chain certificate and compare its SHA-256 fingerprint against the pinned set.
3. **Fail** on a mismatch — the release would ship a firmware that cannot reach GitHub.
4. **Warn** if any pinned root expires within, say, 180 days.

This turns a silent fleet-wide outage into a build failure on the developer's machine, which is the same bargain the size gate already makes.

One honest limitation: chains can vary by CDN edge and geography, so a check from one machine is evidence, not proof. It still catches the case that matters — a vendor-wide root migration.

## Resolution notes

> 🟢 Resolved 2026-08-16 — implemented, verified on hardware, and shipped in **v0.0.5**. Status had been left at `open` after the work landed; corrected here.

**Recovered 69,200 bytes.** Headroom went from 14,800 to **84,000** (93% used).

Two corrections to this issue's original specification, both found during implementation:

1. **The served top-of-chain certificates do not match the embedded roots.** Both hosts present *cross-signed* copies — Sectigo E46 signed by USERTrust ECC, ISRG Root YR signed by ISRG Root X1 — with the same public keys but different certificates and fingerprints. A literal fingerprint-equality gate, as originally specced, would have failed on day one. The gate instead runs `openssl verify` with the pinned roots as the entire trust store, which replays exactly what mbedTLS does on the C3; the public-key comparison runs alongside and only warns, since a server is not obliged to send its root at all.
2. **The real expiries are 2045 and 2046**, not the 2032/2038 recorded above — those dates belong to the cross-signed copies. And ISRG Root YR is **RSA-4096**, not ECDSA, so the note about cheaper verification only half holds.

The asset host was also corrected: releases are served from `release-assets.githubusercontent.com`, not `objects.githubusercontent.com`. Both chain to the same ISRG root so the pin was unaffected, but the gate now checks the host actually used and follows the redirect at runtime rather than assuming it.

**Hardware proof.** On the bench device, all four TLS handshakes verified against the pinned roots — including the ISRG leg to `release-assets.githubusercontent.com`, so the download path is proven and not just the version check:

```
OTA: checking for update (manual=true, current=0.0.5)
Certificate verified. -> connected to api.github.com:443
OTA: latest tag=0.0.4, running=0.0.5
Certificate verified. -> connected to release-assets.githubusercontent.com:443
OTA: update failed, error=-100: Not Enough space
```

The `-100` is the expected v0.0.4 oversize rejection, unrelated to TLS.

Gate negative-tested: swapping one pinned root exits 1, and reproduces the exact trap this issue warned about — both Sectigo hosts still pass while only the download host fails.

## Expected behavior

The firmware carries only the roots it needs (~2 KB), OTA continues to work against all three GitHub hosts, and the release script fails loudly if the pinned roots stop matching what those hosts present.

## Actual behavior

The full Mozilla root store is embedded — 69,876 bytes to validate one vendor — leaving 14,800 bytes of headroom in a release that is otherwise healthy.

## Notes

- Expected result: ~1,228,000 bytes, roughly **83,000 bytes spare** (94% used) versus 14,800 today.
- This is complementary to, not a substitute for, the `min_spiffs` partition change in [#0009](0009.md). This one ships over the air; that one needs USB but buys 655,360 bytes and immunity to toolchain drift. The Arduino core update between June and August silently added ~27 KB, which is more than this saving would leave in reserve.
- Extracting the PEMs is a one-liner per host with `openssl s_client -showcerts`, but they should be taken from a trusted source (the CA's own published root, or the system trust store) rather than from whatever the connection happened to present.
- Both pinned roots are ECDSA (Sectigo E46, ISRG YR), which is also cheaper to verify on the C3 than RSA.
