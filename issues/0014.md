# 0014 — Effect engine refactor: EffectMode enum, render dispatch, and the THEME_CUSTOM slot

| | |
|---|---|
| **Status** | open |
| **Module** | LED / Rendering / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-25 |

## Description

Phase 1 of [#0013](0013.md). Introduce an `EffectMode` enum and a `BUILTIN_EFFECT_MODE[]` table, rewire the render loop to dispatch on mode rather than on theme, and add the `THEME_CUSTOM` slot plus the `CustomEffectConfig` struct it renders from. **No new visual behavior ships in this phase** — the six built-in themes must look exactly as they do today.

## Plan

Written by the planning subagent. This is guidance, not a contract — where the code
disagrees with what's below, the code wins; say so in `## Fix` and move on.

### 0. What this phase is, in one line

Move the two existing renderers behind an `EffectMode` dispatch, add the
`THEME_CUSTOM` slot and its (unpopulated) `CustomEffectConfig`, and make the
"renders identically" promise machine-checkable. Zero visual change.

### 2. `EffectMode` and the dispatch

**Where it lives.** New header `src/effects.h`, **header-only** (all definitions
`inline`). Header-only is deliberate: `[env:native]` builds test sources only
(`test_build_src` is off, which is why `test/test_rollover` links `src/time_utils.h`
today), so a `src/effects.cpp` would not be linkable from a native test without
turning on project-source building — which would drag `main.cpp`, `WiFi.h` and
`FastLED.h` into the host build and fail. A header included by both `main.cpp`
and the test needs no `platformio.ini` change at all: `[env:native]` already
carries `-I src`.

`src/effects.h` contains:

```c
enum EffectMode {
    EFFECT_BLEND = 0, EFFECT_FLICKER = 1, EFFECT_CHASE = 2, EFFECT_WIPE = 3,
    EFFECT_SCAN = 4, EFFECT_SPARKLE = 5, EFFECT_PULSE = 6, EFFECT_STROBE = 7,
    EFFECT_COLORLOOP = 8
};
```

All nine values ship now; only `EFFECT_BLEND` and `EFFECT_FLICKER` have
renderers. [#0015](0015.md) fills the rest.

**The table.** In `src/effects.h` (or `src/themes.h`, see §7):

```c
static const EffectMode BUILTIN_EFFECT_MODE[CYCLEABLE_THEME_COUNT] = {
    EFFECT_FLICKER,  // THEME_GREEN
    EFFECT_BLEND,    // THEME_RAINBOW
    EFFECT_BLEND,    // THEME_PINK_PONY
    EFFECT_BLEND,    // THEME_OCEAN_WAVES
    EFFECT_BLEND,    // THEME_SUNSET
    EFFECT_BLEND     // THEME_FOREST
};
static_assert(sizeof(BUILTIN_EFFECT_MODE)/sizeof(BUILTIN_EFFECT_MODE[0])
              == CYCLEABLE_THEME_COUNT, "one mode per cycleable theme");
```

Add the matching `static_assert` for `THEME_NAMES[]` too — it is the thing most
likely to drift in [#0015](0015.md) and it is indexed unguarded in
`publishState()` and the heartbeat log.

**The selector:**

```c
inline EffectMode getCurrentEffectMode() {
    if (currentTheme == THEME_CUSTOM) return customEffect.mode;
    if ((int)currentTheme >= CYCLEABLE_THEME_COUNT) return EFFECT_BLEND; // corrupt value
    return BUILTIN_EFFECT_MODE[currentTheme];
}
```

The `THEME_CUSTOM` test must come **first**: `THEME_CUSTOM == 6 ==
CYCLEABLE_THEME_COUNT`, so the bounds check alone would swallow it.

**The render loop** (`loopLED()`, 1256–1264) becomes:

```c
switch (getCurrentEffectMode()) {
    case EFFECT_FLICKER: /* renderFlicker */ break;
    case EFFECT_BLEND:
    default:             /* renderBlend   */ break;
}
```

`default → renderBlend` is load-bearing for this phase: the seven unimplemented
modes are unreachable (nothing populates `customEffect`), but if one ever is
reached the strip blends rather than going dark or falling off the end of a
jump table.

Nothing else in `loopLED()` changes — the heartbeat `logTimeout` block and the
`ledsEnabled` black-fill early-return stay exactly as they are.

### 3. `THEME_CUSTOM`, `CustomEffectConfig`, and the accessors

**Enum shape — follow the spec, not the ticket's phrasing.** The ticket says
"past `THEME_COUNT`"; the spec (`docs/glowkitchen-custom-effects-spec.md` §2)
says:

```c
enum HueTheme {
    THEME_GREEN = 0, ..., THEME_FOREST = 5,
    THEME_CUSTOM = 6,
    THEME_COUNT = 7
};
const int CYCLEABLE_THEME_COUNT = 6;
```

Take the spec form. [#0015](0015.md)–[#0017](0017.md) are written against it, and
`THEME_COUNT = 7` is what makes `savedTheme < THEME_COUNT` in
`loadAllPreferences()` accept a persisted custom theme in [#0016](0016.md)
without another enum edit. The cost is that **every current use of
`THEME_COUNT` must be triaged** — there are six:

| Line | Use | Becomes |
|---|---|---|
| 473, 504 | `DEV_THEME_OVERRIDE` bounds | `CYCLEABLE_THEME_COUNT` (the comment says "0-5") |
| 480 | `savedTheme < THEME_COUNT` NVS validation | leave as `THEME_COUNT` — the boot guard below handles the custom case |
| 520 | `(currentTheme + 1) % THEME_COUNT` | `% CYCLEABLE_THEME_COUNT` |
| 534 | `(currentTheme - 1 + THEME_COUNT) % THEME_COUNT` | `CYCLEABLE_THEME_COUNT` both places |

Getting 520/534 wrong is the whole "`NEXT_THEME`/`PREV_THEME` still cycle six"
requirement, so grep for `THEME_COUNT` after editing and confirm each remaining
hit is deliberate.

**`THEME_NAMES[]` must grow to 7 entries** (`"Custom"`). It is indexed by
`currentTheme` in `saveThemeToPreferences()`, `publishState()`, the heartbeat
log and the switch-theme logs; with 6 entries a `THEME_CUSTOM` value is an
out-of-bounds read. This is the single most likely crash in the phase.

`getThemeMqttCommand()` currently `default: return "GREEN"` — leave it; it is
correct-by-accident for this phase and [#0016](0016.md) owns the custom reply.

**The struct** — spec §3, verbatim, in `src/effects.h`:

```c
#define MAX_CUSTOM_COLORS 8
struct CustomEffectConfig {
    EffectMode mode;
    CRGB       colors[MAX_CUSTOM_COLORS];
    uint8_t    colorCount;
    uint8_t    speed;          // default 128
    uint8_t    intensity;      // default 128
    uint32_t   timeoutMs;      // 0 = no timeout
    uint32_t   activatedAt;
    HueTheme   revertTheme;
};
```

Use `uint32_t`, not `unsigned long`, for the two time fields — same reasoning as
`src/time_utils.h` ([#0008](0008.md) type-width note): `unsigned long` is 64 bits
on a native host and 32 on the C3, and these fields will be fed to `timeReached()`
in [#0017](0017.md). Define one file-scope `CustomEffectConfig customEffect = {};`
in `main.cpp`. **Nothing populates it in this phase** — say so in a comment
pointing at [#0016](0016.md), so a reviewer doesn't read the dead struct as an
oversight.

**The accessors.** Rename `getCurrentHueArray()` → `getCurrentColorArray()` and
`getCurrentHueCount()` → `getCurrentColorCount()` (14 call sites; mechanical).

Keep the return type `const uint8_t*` — a **hue** array — for this phase, even
though the spec sketches `const CRGB*`. This matters: `slowBlend()` does hue-space
arithmetic (shortest path around the 256-hue circle, `BLEND_THRESHOLD = 60`) that
has no meaning on RGB triples. Converting built-in themes to `CRGB` here would
change what BLEND renders and break the compatibility promise this ticket exists
to keep. Converting the *custom* colors into hue space is [#0016](0016.md)'s
problem, not this one.

For `THEME_CUSTOM`, add a small derived cache so the accessors are genuinely
wired rather than stubbed:

```c
static uint8_t customHues[MAX_CUSTOM_COLORS];   // derived from customEffect.colors
inline void refreshCustomHues() {
    for (uint8_t i = 0; i < customEffect.colorCount && i < MAX_CUSTOM_COLORS; i++)
        customHues[i] = rgb2hsv_approximate(customEffect.colors[i]).hue;
}
```

`getCurrentColorArray()` returns `customHues` and `getCurrentColorCount()`
returns `customEffect.colorCount` for `THEME_CUSTOM`. In this phase
`colorCount == 0` and the cache is all zeros; [#0016](0016.md) calls
`refreshCustomHues()` after parsing. *If the reviewer prefers a smaller diff,
dropping `refreshCustomHues()` and returning `GREEN_HUES` / `NUM_GREEN_HUES`
for the custom branch is an acceptable deviation* — the boot guard makes the
branch unreachable either way. Say which you did.

**The boot guard.** In `loadAllPreferences()`, after the theme is loaded
(around 480–486):

```c
if (currentTheme == THEME_CUSTOM && customEffect.colorCount == 0) {
    currentTheme = THEME_GREEN;
    ESP_LOGI(TAG, "THEME_CUSTOM with no effect configured, falling back to Green");
}
```

In this phase the guard fires for every possible path that reaches
`THEME_CUSTOM`, which is the point — a device whose NVS somehow holds `6` boots
green instead of rendering a zero-length color array (a division/modulo by
`currentHueCount == 0` in `slowBlend()`, i.e. a crash loop).

### 4. The compatibility check — recommendation: **frame-capture diff**

I looked at how coupled the two renderers actually are before recommending
this. The verdict is that the extraction is **practical**, and the frame diff is
worth doing.

**What the coupling actually is.** `flickerLEDs()` and `slowBlend()` are ~90
lines between them and touch FastLED in exactly five places: `CHSV(...)`
construction assigned into `leds[i]`, `sin8()`, `FastLED.getBrightness()`,
`FastLED.show()`, and (blend only) `applyMirror()`. There is no `EVERY_N_*`
macro anywhere in the file — both already use `timeReached()` from
[#0008](0008.md). Randomness is Arduino `random(lo, hi)` in the flicker path
only; `random8()`/`random16()` are not used. That is a small, well-defined seam.

**The seam.**

1. `src/effects.h` must not `#include <FastLED.h>`. It relies on `CRGB`, `CHSV`
   and `sin8` already being declared by whoever includes it: `main.cpp` includes
   `FastLED.h` first (line 2), the native test includes a shim first. Document
   this include-order contract in a comment at the top of the header — it is the
   one genuinely fragile thing in this design.
2. Renderers take state explicitly and return "did I draw?" instead of calling
   `FastLED.show()` themselves:

```c
struct EffectState {
    // owned across frames
    uint32_t  blendTimeout, rotateTimeout, hueTimeout;
    uint8_t   blendOffset;          // MUST stay uint8_t — see below
    uint32_t* timeouts;             // -> timeouts[MAX_LEDS]
    // per-frame inputs
    CRGB*     leds;
    int       numLeds, ledsPerColor;
    const uint8_t* colors;
    int       colorCount;
    int       hueIndex;             // in/out
    bool      colorChangeEnabled;
    int       brightness, maxBrightness;
    uint32_t (*rng)(uint32_t lo, uint32_t hi);   // Arduino random() on device
};
inline bool renderBlend(EffectState& s, uint32_t now);   // true = pixels changed
inline bool renderFlicker(EffectState& s, uint32_t now);
```

   `main.cpp` keeps one file-scope `EffectState fx;` that **owns**
   `blendTimeout` / `rotateTimeout` / `hueTimeout` / `blendOffset` (delete those
   globals; only `setupLED()` and the `SET_CLOCK_OFFSET` handler reference them
   externally). `hueIndex` stays a global — it has 17 references across
   preferences, MQTT and logging — and is copied in and out around the render
   call, one line each way. This keeps the diff small and reviewable.

   `loopLED()` then does:

```c
fx.leds = leds; fx.numLeds = numLeds; fx.ledsPerColor = ledsPerColor;
fx.colors = getCurrentColorArray(); fx.colorCount = getCurrentColorCount();
fx.hueIndex = hueIndex; fx.colorChangeEnabled = colorChangeEnabled;
fx.brightness = FastLED.getBrightness(); fx.maxBrightness = MAX_BRIGHTNESS;
bool drew = (mode == EFFECT_FLICKER) ? renderFlicker(fx, millis())
                                     : renderBlend(fx, nowMs());
hueIndex = fx.hueIndex;
if (drew) { if (mirrorEnabled && mode != EFFECT_FLICKER) applyMirror(); else FastLED.show(); }
```

3. **Preserve these exactly** — each is a real behavior trap:
   - `blendOffset` stays `uint8_t`. `blendOffset = (blendOffset + 1) % (numLeds * colorCount)`
     has a modulus of ~1920 at the default 240 LEDs / 8 hues, so the assignment
     truncates at 256 and *that truncation is the shipped animation*. Widening it
     to `int` silently changes the scroll. (This is precisely the class of bug
     the frame diff catches.)
   - `renderFlicker` is driven by `millis()`, `renderBlend` by `nowMs()` — as
     today. Unifying them would strand the flicker `timeouts[]` under the
     `SET_CLOCK_OFFSET` bench harness, which only rebases the two blend timers.
     Out of scope; leave the asymmetry and note it.
   - `FastLED.getBrightness()` is read *inside* the per-LED loop today. Hoisting
     it to a per-frame input is safe (it cannot change mid-frame) — but keep the
     surrounding `int` arithmetic and the `min(MAX_BRIGHTNESS, ...)` types
     identical; a stray `uint8_t` changes the saturation behavior.
   - In `slowBlend()` the show happens *before* `blendTimeout` is advanced and
     before the rotate check. Moving the show to the caller reorders it after the
     rotate check; that is safe (the rotate check touches only `blendOffset`, and
     `now` was sampled once at the top) but should be stated in `## Fix`.
   - `timeouts[]` becomes `uint32_t[]` (identical on the C3, and correct on a
     64-bit host — same lesson as `src/time_utils.h`).

4. **Randomness.** `s.rng` is a function pointer so the native test can inject a
   fixed-seed LCG. On device it is a two-line wrapper over Arduino
   `random(lo, hi)`, so the shipped behavior is unchanged. A FLICKER frame can
   never be byte-identical run-to-run — the diff is only meaningful when both
   paths draw from the same seeded stream, which also makes the test a check that
   the refactor consumes exactly the same number of draws in the same order.

**The test.** New folder `test/test_effects/`:

- `fastled_shim.h` — host stubs. `CRGB` stores the raw triple and
  `operator=(const CHSV&)` stores `{h, s, v}` **without converting to RGB**.
  That is deliberate: the store is injective, so byte-equality of two shim
  buffers is exactly equivalence of the `CHSV` arguments the two paths computed,
  and no one has to reimplement `hsv2rgb_rainbow` to make the diff meaningful.
  Also needs `sin8`, `min`, `max`. Any deterministic `sin8` makes the diff valid
  (both paths call the same one); copying FastLED's table-free `sin8_C` is nicer
  if you want the captured frames to resemble real output, but it is **not**
  load-bearing — do not sink time into matching FastLED bit-for-bit.
- `legacy_effects.h` — **frozen verbatim copies** of today's `flickerLEDs()` and
  `slowBlend()`, taken with `git show main:src/main.cpp` *before* you edit
  anything, renamed `legacyFlicker()`/`legacyBlend()`, adapted **only** at the
  seam (state access, `rng`, no `FastLED.show()`). Never touch the math. Test-only;
  never compiled into firmware, so it costs zero flash. Note honestly in `## Fix`
  that the reference is a transcription, so the diff is only as good as the
  copy-paste.
- `test_effects.cpp` — for each of the six built-in themes: two independent
  `EffectState`s + two `leds[]` buffers + two `timeouts[]` arrays, identical
  seeds; step `now` by 10 ms for ~600 frames (covers the 100 ms blend, 500 ms
  rotate, 500–750 ms flicker and 2000 ms hue rotation, i.e. ~6 s of animation);
  after every frame assert `memcmp(ledsA, ledsB, numLeds * sizeof(CRGB)) == 0`
  **and** that `hueIndex` / `blendOffset` / `timeouts[]` agree. Add one run that
  starts `now` near `2^32` so the rollover path inside the renderers is exercised
  too — a free bonus given [#0008](0008.md).

The six hue arrays live in `main.cpp` and the test cannot see them. Move
`HueTheme`, `THEME_NAMES[]`, the six hue arrays, the `NUM_*_HUES` counts and
`BUILTIN_EFFECT_MODE[]` into a new `src/themes.h` included by `main.cpp` and by
the test. This follows the precedent `src/time_utils.h` set — the test links the
*real* tables, not hand-copied stand-ins. If that move turns out to be more
churn than it's worth, copying the six arrays into the test is an acceptable
fallback, but it is strictly weaker and should be called out.

**Why frame-capture over visual inspection.** The extraction is ~5 touchpoints
and needs no `platformio.ini` change, no new dependency and no flash cost; the
harness already exists from [#0008](0008.md). Visual inspection cannot see a
truncation bug like `blendOffset`, cannot be repeated by [#0015](0015.md)–
[#0017](0017.md), and cannot be run by an agent at all. **Do the frame diff.**

A visual smoke check on a flashed board is still *desirable* — the diff cannot
cover `FastLED.show()` call sites, mirror mode, the real HSV→RGB conversion or
WS2812 output — but it is no longer what the promise rests on.

### 5. Timing

Timers touched by this refactor: `blendTimeout`, `rotateTimeout`, `hueTimeout`,
`timeouts[i]`. All four already go through `timeReached()` and **must continue
to** — they move into `EffectState` but the comparisons do not change form.
`logTimeout` and the `lastBlackUpdate` subtraction in `loopLED()` are untouched.

**Do not substitute `EVERY_N_MILLISECONDS` or any other `EVERY_N_*` macro.** They
wrap `millis()` internally and sidestep `timeReached()` entirely, which is
exactly the [#0008](0008.md) failure re-entering by the back door. There are
currently zero `EVERY_N_*` uses in the firmware; keep it that way. Grep for
`EVERY_N` and for `< now` / `> now` before you commit.

The `SET_CLOCK_OFFSET` handler (~838) rebases `blendTimeout` and `rotateTimeout`
by name. If those move into `fx`, **that handler must be updated** — and it is
compiled **only** under `ENABLE_CLOCK_OFFSET`, i.e. only in `[env:esp32c3-debug]`.
A green `pio run -e esp32c3` will not catch a break there. Build the debug env too.

### 6. Flash budget

The OTA slot is `0x140000` = 1,310,720 bytes (`scripts/release.sh`, `OTA_PARTITION_SIZE`).
The checked-in build artifact `.pio/build/esp32c3/firmware.bin` is 1,226,720 bytes,
which is where the umbrella's **84,000 bytes** of headroom comes from — that
number checks out. But that artifact predates [#0008](0008.md) landing, so it is
**not** a valid baseline: build `main` fresh and measure before touching anything.

`release.sh` hard-fails over 1,310,720 and warns under 20,480 spare. Report
`firmware.bin` size and headroom **before and after** in `## Verification`.
Expect roughly neutral: header-only inline renderers, one 6-byte table, a
~40-byte struct, `THEME_NAMES` +1 entry. `rgb2hsv_approximate()` (if you keep
`refreshCustomHues()`) is a few hundred bytes. Anything over ~2 KB of growth
means something got duplicated rather than moved — investigate before committing.

Do **not** run `scripts/release.sh`; it publishes. Measure with
`stat -f%z .pio/build/esp32c3/firmware.bin`.

### 7. Step-by-step

Each step should build and be independently committable on `issue/0014`.

1. **Baseline.** `pio run -e esp32c3`, record `firmware.bin` size. Save the
   pre-refactor `flickerLEDs()`/`slowBlend()` (`git show main:src/main.cpp`) —
   you need the untouched text for `legacy_effects.h`.
2. **`src/themes.h`** — move `HueTheme` (+ `THEME_CUSTOM = 6`, `THEME_COUNT = 7`,
   `CYCLEABLE_THEME_COUNT = 6`), `THEME_NAMES[]` (7 entries), the six hue arrays
   and counts out of `main.cpp`. Fix the four `THEME_COUNT` sites per §3. Build.
   `NEXT_THEME`/`PREV_THEME` now modulo 6.
3. **`src/effects.h` skeleton** — `EffectMode`, `MAX_CUSTOM_COLORS`,
   `CustomEffectConfig`, `EffectState`, `BUILTIN_EFFECT_MODE[]`, the
   `static_assert`s, `getCurrentEffectMode()`. Define `customEffect` in
   `main.cpp`. Build.
4. **Rename** `getCurrentHueArray`/`getCurrentHueCount` →
   `getCurrentColorArray`/`getCurrentColorCount`, add the `THEME_CUSTOM` branch
   and `refreshCustomHues()`, add the boot guard in `loadAllPreferences()`. Build.
5. **Move the renderers** into `src/effects.h` as `renderBlend()`/`renderFlicker()`
   taking `EffectState&` and `now`, returning `bool`. Delete the old globals,
   update `setupLED()` and the `SET_CLOCK_OFFSET` handler. Rewrite the
   `loopLED()` dispatch (§2). Build **both** `-e esp32c3` and `-e esp32c3-debug`.
6. **`test/test_effects/`** — shim, frozen legacy copies, the diff test.
   `pio test -e native`. Expect it to fail at least once on a real difference;
   if it passes first try, deliberately perturb one line (e.g. widen
   `blendOffset` to `int`) and confirm the test **fails** before trusting it.
   A test that cannot fail is not a test.
7. **Re-measure** `firmware.bin`, record before/after and headroom.
8. **`## Verification`** — commands, outputs, the frame-diff result, the
   before/after sizes, and an explicit statement of which mechanism you chose
   and why (the ticket asks for this in `## Fix` either way).

### 8. Verification — what counts as proof

```
pio run -e esp32c3            # must reach [SUCCESS]
pio run -e esp32c3-debug      # ENABLE_CLOCK_OFFSET path must still compile
pio test -e native            # must RUN the new tests, not skip them
stat -f%z .pio/build/esp32c3/firmware.bin
```

- A green build with **zero tests executed is a failure, not a pass.** Paste the
  Unity summary line and confirm the `test_effects` cases appear in it — both
  device envs set `test_ignore = *`, so a misplaced test folder silently runs
  nothing and still exits 0. If the output says `No test cases found` or lists
  only `test_rollover`, the work is not done.
- `pio test -e native` must also still pass all ten existing `test_rollover`
  cases.
- **Requires hardware, therefore cannot be verified by an agent:** actual LED
  output on a strip, mirror mode, IR remote behavior, MQTT round-trips
  (`NEXT_THEME`/`PREV_THEME` cycling, theme commands, `STATUS`), and the
  `SET_CLOCK_OFFSET` bench procedure. Per `issues/Issues.md`, that is a **bail —
  name exactly what could not be verified in `## Verification`, do not call it a
  pass.** The frame diff substantially narrows what's left, but it does not
  eliminate it.

### 9. Uncertainties and permitted deviations

- **`THEME_COUNT = 7` vs staying 6.** I chose the spec's form over the ticket's
  "past `THEME_COUNT`" phrasing because the three downstream tickets assume it.
  If it causes trouble at the `savedTheme < THEME_COUNT` site, keeping
  `THEME_COUNT = 6` and adding `THEME_CUSTOM = 6` separately is defensible —
  just make sure whichever you pick, the cycling arithmetic uses 6 and
  `THEME_NAMES[]` covers every reachable index.
- **The include-order contract** on `src/effects.h` (FastLED-or-shim declared
  first) is the fragile part of the design. If it proves annoying, a thin
  `effects_types.h` that either includes `FastLED.h` or the shim behind
  `#ifdef ARDUINO` is a fine alternative.
- **`refreshCustomHues()`** may be dropped in favor of a plain fallback (see §3)
  if the reviewer wants less speculative code in a phase where nothing populates
  the struct.
- **Moving the hue tables to `src/themes.h`** is the largest mechanical part of
  the diff. It exists to let the test link the real data; copying them into the
  test instead is weaker but acceptable if the move fights you.
- **I have not built or run anything** — the line numbers above are from reading
  `src/main.cpp` at `a6650fe` and will shift as you edit. Trust the code.
- `docs/add_new_theme.md` describes themes as hue arrays and names
  `getCurrentHueArray()`/`getCurrentHueCount()` and `slowBlend()`/`flickerLEDs()`
  directly (lines 67–95, 140–145). The renames make those references *wrong*, not
  merely incomplete. Per the ticket's Notes, correct just the names there; leave
  the conceptual rewrite for [#0015](0015.md).

## Long Description

This is steps 1–2 of the spec's build order (`docs/glowkitchen-custom-effects-spec.md`, "Suggested build order"). It is deliberately the whole of one ticket because it is a pure refactor with a hard compatibility promise, and mixing it with new renderers would make a regression impossible to attribute.

Scope:

- `EffectMode` enum with all nine values (`BLEND`, `FLICKER`, `CHASE`, `WIPE`, `SCAN`, `SPARKLE`, `PULSE`, `STROBE`, `COLORLOOP`). Only `BLEND` and `FLICKER` get implementations here; the other seven land in [#0015](0015.md).
- `BUILTIN_EFFECT_MODE[]` mapping the six existing themes to their mode — Green → `FLICKER`, the other five → `BLEND`.
- Render loop dispatches on `EffectMode`, not on `HueTheme`.
- `THEME_CUSTOM` added as a theme slot past `THEME_COUNT`, with `getCurrentColorArray()` / `getCurrentColorCount()` wired for it.
- `CustomEffectConfig` struct defined and zero-initialized. Nothing populates it yet — that's [#0016](0016.md).
- `NEXT_THEME` / `PREV_THEME` continue to cycle only the original six, so `THEME_CUSTOM` is unreachable by cycling.
- The `THEME_CUSTOM` boot guard: booting with `currentTheme == THEME_CUSTOM` but an uninitialized effect falls back to `THEME_GREEN` rather than rendering an empty color array.

### Settle the compatibility check before writing code

[#0013](0013.md) flags this and it lands here: the spec guarantees the six built-ins render identically through the new engine, and nothing today can verify that. **Decide the mechanism as part of this ticket, not after.** The two candidates:

- **Frame-capture diff (preferred if feasible)** — extract the renderers so a `native` test can drive them against a stub `leds[]` buffer, run N frames through the old and new paths from the same seed, and assert the buffers match byte for byte. `[env:native]` already exists from [#0008](0008.md), so the harness cost is the extraction, not the infrastructure.
- **Visual inspection** — flash a board and look at each of the six themes.

The first makes the promise checkable in CI forever; the second makes it checkable once, by a human, and never again. Take the first unless the extraction proves genuinely impractical, and say so explicitly in `## Fix` either way.

### Timing

Every timer touched or introduced must go through `timeReached()` from `src/time_utils.h`. See [#0008](0008.md) — this is a hard constraint, not a preference.

## Expected behavior

All six built-in themes render exactly as before, the IR remote and every existing MQTT command behave identically, and `NEXT_THEME`/`PREV_THEME` still cycle the same six. Internally the render path now dispatches on `EffectMode`.

## Actual behavior

Rendering is hardcoded per theme; there is no mode abstraction and no slot for an ad hoc effect.
