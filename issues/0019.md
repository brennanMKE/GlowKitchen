# 0019 — rgb2hsv_approximate() undersaturates custom colors by ~40%, so pinks render as white

| | |
|---|---|
| **Status** | resolved |
| **Module** | LED / Rendering / MQTT |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-26 |
| **Closed** | 2026-08-28 |

## Description

`refreshCustomPalette()` converts `SET_EFFECT`'s hex colors to HSV with FastLED's `rgb2hsv_approximate()`, which loses roughly 40% of the saturation. Observed on hardware: a three-shade pink palette rendered as **plain white sparkles**, with none of the three colors identifiable.

## Long Description

Found while running the Dolly Parton demo (`scripts/demo_effect.sh <device> dolly`) on a 10-LED strip. The user's report was simply "I just see white sparkles."

### Measured error

| Hex | True H/S | `rgb2hsv_approximate` H/S | Rendered RGB |
|---|---|---|---|
| `#FF69B4` hot pink | 234 / 150 | 221 / **92** | (123, 64, 98) |
| `#FF1493` deep pink | 232 / 235 | 188 / **184** | (54, 12, 114) |
| `#FFB6C1` light pink | 249 / 73 | 240 / **40** | (149, 111, 119) |

Saturation lands ~40% low across the board. At s=40 a color is nearly achromatic, so `#FFB6C1` renders (149,111,119) — a pale grey that reads as white on an LED. The hue error is significant too: `#FF1493` is off by 44 units (~62°), which is why it reads violet rather than deep pink.

This is FastLED's documented trade-off — `rgb2hsv_approximate()` is fast and explicitly inexact. It is the wrong tool when the input is a user-specified color that must be recognizable.

### Why this defeats [#0013](0013.md)'s palette decision

[#0013](0013.md) widened the palette from a hue byte to `PaletteColor{h,s,v}` specifically so `SET_EFFECT` could express desaturated colors. That decision is sound and the storage is correct — but the *conversion feeding it* discards most of the saturation before it is ever stored, so the widening buys much less than intended. The [#0016](0016.md) review measured these exact values and judged the three pinks "distinct shades"; on real LEDs at strip brightness they are not distinguishable.

**The lesson worth keeping: the numbers were measured correctly and the conclusion drawn from them was still wrong.** Distinctness on paper is not distinctness to an eye looking at a 10-LED strip.

### Fix

Replace `rgb2hsv_approximate()` with an exact integer RGB→HSV conversion in `refreshCustomPalette()`. Standard max/min formulation; no floating point needed, and it runs once per `SET_EFFECT`, not per frame, so cost is irrelevant.

Note this cannot make the round-trip perfect: `CHSV` assignment goes through FastLED's `hsv2rgb_rainbow()`, which is a deliberately non-linear "rainbow" mapping rather than a colorimetric one. Exact HSV in removes the avoidable half of the error. If the remaining hue shift matters, the deeper fix is to bypass HSV entirely for the modes that don't need hue arithmetic — but that reopens [#0013](0013.md)'s decision and is not for this ticket.

## Expected behavior

`SET_EFFECT:{"colors":["#FF69B4","#FF1493","#FFB6C1"],...}` renders three recognizably pink, visibly distinct shades.

## Actual behavior

All three read as white or near-white on the strip.

## Notes

- Demo-blocking: the Dolly Parton preset in `scripts/demo_effect.sh` is the headline demo and it currently shows white.
- A native test can pin the conversion exactly — it is pure integer math with no FastLED dependency. Include the three pinks above as fixtures with their true H/S values, and make sure the test can actually fail (see [#0008](0008.md), [#0014](0014.md)).
- Verification must include a look at a real strip. This bug survived a numeric review precisely because it was only ever checked numerically.

## Fix

`refreshCustomPalette()` no longer calls FastLED's `rgb2hsv_approximate()`.
`src/effects.h` gained `rgbToPaletteColor(r, g, b)` — an exact integer RGB->HSV
conversion — and the palette cache is built from that instead. The approximate
version trades accuracy for speed in a way that costs roughly 40% of the
saturation, which is invisible on a fully saturated built-in theme and fatal
for the pastels a custom palette is most likely to contain.

Landed with the [#0015](0015.md)/[#0016](0016.md) work; this ticket was left
`open` because it had never been written up or confirmed on hardware, not
because the code was missing.

## Verification

```
pio test -e native            # 101 test cases: 101 succeeded
pio run -e esp32c3            # SUCCESS -- firmware.bin 1,236,112 bytes
```

Five native gates cover `rgbToPaletteColor()` in
`test/test_effects/test_effects.cpp`: `test_rgb_to_palette_demo_pinks` (this
ticket's exact three colours), `..._primaries`, `..._achromatic`,
`..._sector_seams` and `..._near_black_low_delta`.

**On hardware** — the confirmation [#0013](0013.md)'s handoff listed as
outstanding ("colour conversion fixed and merged; unconfirmed by eye"). Dev
board `84fce68774a4`, `demo_effect.sh 84fce68774a4 dolly 25`, pixel values
read from `EFFECT_TRACE`. The three palette entries now arrive as three
distinguishable colours, in the correct saturation order:

| Written | G/R | B/R | Source | Source G/R | Source B/R |
|---|---|---|---|---|---|
| `#26000c` | 0.00 | 0.32 | `#FF1493` deep pink | 0.08 | 0.58 |
| `#290812` | 0.20 | 0.44 | `#FF69B4` hot pink | 0.41 | 0.71 |
| `#31191b` | 0.51 | 0.55 | `#FFB6C1` light pink | 0.71 | 0.76 |

32 distinct colours written across the run. The original symptom was "plain
white sparkles, with none of the three colors identifiable" — three separable
pinks with near-zero green in the deepest is the opposite of that.

139 of 574 writes are near-grey, but every one of them peaks at value 10 or
below against a peak coloured write of 49: those are the tails of the sparkle
fade, where 8-bit quantisation collapses the channels toward each other. Not
the reported defect.

## Notes

**Residual, deliberately not fixed here.** Every colour above is shifted toward
red relative to its source — `B/R` runs 0.32 against 0.58, 0.44 against 0.71,
0.55 against 0.76. That is **not** the input conversion this ticket fixed; it
is FastLED's `hsv2rgb_rainbow()` on the output side, which warps hue by design
to produce more pleasing yellows and does not round-trip a mathematically exact
hue. The colours are correct relative to each other and clearly in the pink
family, which is what this ticket asked for; making a `#RRGGBB` request come
back byte-exact would mean writing RGB straight through and giving up the
rainbow curve for every renderer. That is a separate design decision with no
reported problem behind it.

Also unmeasured: effects render at roughly 50% of the configured brightness via
the same `hsv2rgb_rainbow` attenuation (peak write of 49 at `bright=113`).
Noted in [#0013](0013.md)'s handoff as unfiled; still unfiled.
