# 0002 — OTA can only install from a GitHub release, so local firmware iteration is impossible

| | |
|---|---|
| **Status** | open |
| **Module** | OTA / MQTT / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-15 |

## Description

Both halves of the OTA path are hardcoded to GitHub's `releases/latest`, so the only way to get new code onto a device is to cut a public release for the whole fleet. That makes iterative debugging impossible — you cannot try a diagnostic build on one strip without shipping it to all six. Add an MQTT command that updates a **single named device** from an arbitrary URL on the local network.

## Long Description

### Current behavior

`checkForOtaUpdate()` in `src/main.cpp` hardcodes both the version probe and the binary:

- version — `https://api.github.com/repos/brennanMKE/GlowKitchen/releases/latest` → `tag_name` (`src/main.cpp:1119`)
- binary — `https://github.com/brennanMKE/GlowKitchen/releases/latest/download/firmware.bin` (`src/main.cpp:1173`)

It is triggered three ways: ~15 s after WiFi join (`STARTUP_OTA_DELAY_MS`), nightly at 03:00, and on the MQTT `OTA_UPDATE` / `OTA_CHECK` command. All three go to the same URL.

GitHub's `/releases/latest` endpoint **excludes pre-releases and drafts**, so a pre-release cannot be used as a quiet test channel either — devices ignore it entirely. There is no escape hatch short of USB.

### Proposed change

A new MQTT command carrying an explicit URL, published to a single device topic:

```
lights/kitchen/cmd  →  OTA_URL:http://192.168.1.50:8000/firmware.bin
```

The handler calls the existing `httpUpdate.update()` with that URL, reusing the progress/error callbacks and controlled-reboot logic already in `checkForOtaUpdate()`. Because the URL is explicit and operator-issued, the update is **unconditional** — no tag comparison, no version equality check. Serving the build is then just:

```bash
cd .pio/build/esp32c3 && python3 -m http.server 8000
```

Plain `http://` on the LAN needs a `WiFiClient` rather than the `WiFiClientSecure` + CA bundle used for GitHub; both paths should be supported and chosen by URL scheme.

### The trap this must avoid

A locally-flashed dev build will report a `FIRMWARE_VERSION` that differs from the current GitHub release tag. The existing check is equality-based, not newer-only:

```cpp
if (tagName == String(FIRMWARE_VERSION)) return;   // src/main.cpp:1150
```

So a device running `0.0.4-dev` sees tag `0.0.3`, decides they differ, and **downgrades itself back to the released build** — roughly 15 seconds after its next boot. Without a guard, local OTA is self-defeating: every dev build gets clobbered almost immediately.

The fix needs a way to suspend automatic GitHub checks on a device that is being worked on. Options, cheapest first:

1. **`OTA_AUTO:false`** — a bool in NVS that short-circuits both the startup and nightly checks. `OTA_AUTO:true` restores normal behavior. Explicit, trivially implemented, and visible in `publishState()`.
2. Treat any version containing `-dev` as pinned and skip auto-checks while it is running.
3. Switch the comparison to newer-only semver so a dev build is never replaced by an older tag. Worth doing regardless — see the note in [#0001](0001.md) — but on its own it does not stop a *newer* release from landing mid-debug.

Option 1 is the one to implement here; option 3 belongs with the canary work.

### Safety

The command applies an unsigned binary from an operator-supplied URL, which is the same trust level the fleet already has today (unsigned GitHub artifacts, no signature verification — `OTA.md` lists signed OTA as a follow-up). Worth constraining anyway: accept the command only on a device-specific topic, never on `lights/all/cmd`, so a stray broadcast cannot re-flash the whole fleet at once.

## Expected behavior

`OTA_URL:<url>` published to one device's command topic makes that device download and flash the binary at that URL and reboot into it. `OTA_AUTO:false` keeps it on that build until explicitly re-enabled. No GitHub release is involved, and no other device is affected.

## Actual behavior

There is no way to install firmware except by cutting a GitHub release, which updates every device on the fleet at once (see [#0001](0001.md)). Local iteration requires physical USB access to each board.

## Plan

1. **Refactor the download path.** Extract the `httpUpdate` configuration (`onStart` / `onProgress` / `onError`, `rebootOnUpdate(false)`, `setFollowRedirects`, the result `switch` and controlled `ESP.restart()`) out of `checkForOtaUpdate()` into a helper such as `performOtaFromUrl(const String& url)`. `checkForOtaUpdate()` keeps the GitHub tag probe and calls the helper. No behavior change.
2. **Pick the client by scheme.** `https://` keeps `WiFiClientSecure` + `setCACertBundle`; `http://` uses a plain `WiFiClient`. Avoids dragging TLS into a LAN transfer.
3. **Add the `OTA_URL:` command** in `onMqttMessage()`, alongside the existing `OTA_UPDATE` / `OTA_CHECK` branch (`src/main.cpp:727`). Parse with the original-case `msg`, not `msgUpper` — URLs are case-sensitive and the existing handler upper-cases the payload. Reject it if it arrived on `lights/all/cmd`.
4. **Add `OTA_AUTO:<bool>`,** persisted in the `glow_kitchen` NVS namespace, checked at the top of the startup and nightly branches in `loopOta()`. Surface it in `publishState()` so `list_devices.sh` can show which devices are pinned.
5. **Update the scripts** — extend `scripts/ota_update.sh` (or add `scripts/ota_local.sh`) to take a device and URL, and print the `python3 -m http.server` line for the build directory.
6. **Document** the local-dev flow in `OTA.md`.
7. **Verify on the Dev board over USB first**, then confirm a wireless push to `kitchen`.

Because this ships as a fleet-wide release, it should carry the pre-existing build fix noted below.

## Notes

- **The tree does not currently build.** `pio run` fails in this same function: the Arduino core updated and `NetworkClientSecure::setCACertBundle` now requires a size argument, so `client.setCACertBundle(rootca_crt_bundle_start)` no longer compiles. A release cannot be cut until that is fixed (add the `_binary_x509_crt_bundle_end` symbol and pass the length).
- **Flash is at 98.8%** — 1,295,370 of 1,310,720 bytes on the default 2×1.25 MB OTA partitions, leaving ~15 KB. This change is small, but it is close to the ceiling. `-DCORE_DEBUG_LEVEL=5` in `platformio.ini` is the cheapest reclaim (dropping to 3 keeps all project `ESP_LOGI` output while removing verbose framework logging). Changing the partition scheme would break OTA compatibility and require a USB reflash of every device.
- The motivating need is diagnosing [#0003](0003.md); this issue is the enabler for that work.
