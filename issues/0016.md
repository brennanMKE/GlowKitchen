## Description

Phase 3 of [#0013](0013.md). Add the `SET_EFFECT` and `CLEAR_EFFECT` MQTT commands, a **hand-rolled** parser for the effect payload, and NVS persistence of `CustomEffectConfig` behind a `SETTINGS_VERSION` byte. The timeout field is parsed and stored here; acting on it is [#0017](0017.md).

## Fix

Followed the plan's order of work (§11) essentially as written, with one structural deviation from the plan's amendment (see below) and one flash-budget deviation (kept, not dropped, the immediate visual update — see `## Gotchas`).

- **`src/effects.h`** gained `EFFECT_MODE_NAMES[]` (`static const char* const`, per #0014's linkage lesson, with a `static_assert` pinning one name per `EffectMode`), `SETTINGS_VERSION = 2`, `resetCustomEffect()` (explicit field assignment, speed/intensity reset to **128** not 0), and `customEffectIsValid()` (`colorCount` 1–8, `mode <= EFFECT_COLORLOOP`, **`revertTheme < CYCLEABLE_THEME_COUNT`** — rejects a stored self-revert into `THEME_CUSTOM` — and `timeoutMs <= 28800000`).
- **`src/effect_parse.h`** (new, header-only, same rationale as `effects.h`/`time_utils.h`): `SET_EFFECT_PREFIX`, the `EffectParseResult` enum, `findField()`/`skipWs()` (lookup-shaped field extraction, so key order and whitespace are handled for free), `parseUIntCapped()` (one capped-accumulator helper shared by speed/intensity/timeout, so no digit string of any length can overflow `uint32_t`), `parseHexColor()`, `parseQuotedSpan()` (rejects any backslash — no escape processing), `parseMode()` (name lookup against `EFFECT_MODE_NAMES[]`, case-insensitive, no numeric form), `parseColorArray()` (stops and rejects on the 9th element rather than validating all of them first), `parseEffectPayload()` (the public entry point — resets its `out` parameter first, so a rejected parse structurally cannot leave a half-applied config), `effectParseResultName()`, and `applyLoadedCustomEffect()` (the pure NVS-load decision, Preferences-free so it's native-testable).
- **Plan amendment superseded by what #0015 actually landed** (`## Plan`'s 2026-08-26 blockquote said `parseHexColor()` would convert straight to `PaletteColor`): #0015 kept `CustomEffectConfig::colors` as `CRGB[8]`, with a *separate* derived cache (`customPalette`, `refreshCustomPalette()`) doing the RGB→HSV conversion at apply/load time. Per `## Plan`'s own "the code wins" instruction, `parseHexColor()` parses straight hex bytes into `CRGB` (no HSV conversion in the parser at all), and the `SET_EFFECT`/`CLEAR_EFFECT`/load-time call sites in `main.cpp` call `refreshCustomPalette()` (already provided by #0015) to populate the HSV-triple cache the renderers actually read. This is simpler than the amendment's literal text and needed no `CustomEffectConfig` size change — NVS blob size is whatever `sizeof(CustomEffectConfig)` already was after #0015 (colors are still 24 bytes: `CRGB[8]`).
- **`src/main.cpp`**:
  - `#include "effect_parse.h"` after `effects.h` (include-order contract already satisfied by the existing `<FastLED.h>` at the top of the file).
  - `saveCustomEffectToPreferences()` — a ninth per-key `Preferences` helper (this codebase has no `saveSettings()`), version byte written before the blob in the same session.
  - `cancelCustomEffect()` — the shared cancel-path helper (plan §6.3), a no-op if there was nothing to cancel.
  - The custom-effect load wired into `loadAllPreferences()` **before** the theme-resolution block (so the `THEME_CUSTOM` boot guard sees a real `colorCount`), followed by `refreshCustomPalette()`. A missing `fx_ver`/`fx_cfg` (pre-#0016 firmware, or a device that's never set an effect) is silently treated as "never written," not logged as corrupt.
  - `SET_EFFECT:` handler: parses into a scratch `CustomEffectConfig`, rejects with `ESP_LOGE` (never `LOGW`/`LOGI`) and changes nothing on failure; on success, captures `prevRevert` **before** `customEffect = parsed` overwrites `revertTheme` (the two-back-to-back-`SET_EFFECT`s trap from plan §6.1), sets `activatedAt = nowMs()` (never `millis()`), forces `hueIndex = 0`, calls `refreshCustomPalette()`, turns the strip on if it was off, persists both theme and effect, paints an immediate frame, and publishes state. No topic restriction, per the plan and #0013.
  - `CLEAR_EFFECT` handler: exact match, idempotent no-op off `THEME_CUSTOM`, explicitly **no** `/all/` guard (commented inline so a future reader doesn't "fix" the omission by analogy with `OTA_URL`), reverts to `customEffect.revertTheme` (falling back to `THEME_GREEN` if that's ever `>= CYCLEABLE_THEME_COUNT`), zeroes `timeoutMs`/`activatedAt` while keeping `mode`/`colors`/`colorCount` (so `colorCount == 0` keeps meaning "never configured" for the boot guard, not "cleared").
  - `cancelCustomEffect()` called from all three non-`CLEAR_EFFECT` exits: the theme-string dispatch block (guarded by `if (currentTheme == THEME_CUSTOM)`, before `currentTheme = newTheme`), `switchToNextTheme()`, and `switchToPreviousTheme()` — the latter two cover both `NEXT_THEME`/`PREV_THEME` over MQTT and the IR remote in one place, per the plan's reasoning.
  - **`mqtt.setBufferSize(512)`** added to `ensureMqtt()`, right after `setServer()`/`setCallback()` so it's re-applied on every reconnect attempt (binding constraint from the orchestrator's brief; not explicitly required by `## Plan` but load-bearing for `SET_EFFECT` actually reaching the device — see `## Plan` §9.1).
  - **`publishState()`'s `mqtt.publish()` return value is now checked**, with an `ESP_LOGE` on failure naming the payload size (binding constraint from the orchestrator's brief).
- **`docs/mqtt_commands.md`**: new "Custom Effects" section (full field table, the nine mode names, three worked examples, the clamp stated as a clamp, the silence-is-the-failure-mode note, the timeout-not-yet-acted-on forward reference to #0017, the ~233-byte payload ceiling); the stale Theme Control table (`HALLOWEEN`/`CHRISTMAS`, missing `OCEAN_WAVES`/`SUNSET`/`FOREST`) corrected in place, plus a note on Custom's position outside the cycle; the Helper Scripts §4 theme list corrected to match.

**Deviations from `## Plan`, all noted above or in `## Gotchas`:** the `parseHexColor()`-to-`PaletteColor` amendment was superseded by what #0015 actually shipped (CRGB storage + a separate derived HSV cache) — followed the actual code, not the amendment's literal text, per the plan's own instruction to do so. The immediate `fill_solid`/`FastLED.show()` on `SET_EFFECT`/`CLEAR_EFFECT` (plan §6.1/§6.2) was kept rather than dropped per §9's flash-budget remedy #4, since headroom stayed well clear of the investigate line without it. Everything else — the parser's structure, the validation table, the persistence decision, the cancel-path call sites, the `CLEAR_EFFECT` field-retention choice — matches `## Plan` as written.

## Gotchas

- **The plan's palette-representation amendment didn't match what #0015 actually shipped.** The `## Plan`'s 2026-08-26 blockquote assumed `parseHexColor()` would convert `#RRGGBB` straight into a `PaletteColor{h,s,v}` stored directly in `CustomEffectConfig`. What #0015 actually landed keeps `CustomEffectConfig::colors` as `CRGB[8]` (unchanged from #0014) and adds a *separate* derived cache, `customPalette`/`refreshCustomPalette()`, that renderers read instead. Per the plan's own "where the code disagrees with what's below, the code wins" instruction, `parseHexColor()` here parses straight into `CRGB` — a plain 3-byte hex triple, no HSV math in the parser at all — and every call site that changes `customEffect.colors` (both `SET_EFFECT` and the NVS load) calls the already-existing `refreshCustomPalette()` afterward. This is less code than the amendment's literal text would have required and needed no NVS blob size change.
- **`test_case20` and `test_case01`/`test_case14` are intentionally coupled to `test_case10` and the speed-default check respectively** (see the P1/P6 perturbation write-ups in `## Verification`) — a future edit to the parser that touches either the color-count bound or the speed default should expect *both* the dedicated test and its dependent test to fail together. This is by design (plan §7's own case-20 spec explicitly reuses case 10's payload) and not something to "fix" by decoupling.
- **`effectParseResultName()`'s eight string literals were kept rather than collapsed to a numeric code** (plan §9's remedy #3) — flash headroom (75,808 bytes after this ticket) stayed comfortably clear of the investigate line without it, so the more diagnosable string form was kept. If a future ticket needs to reclaim flash, this is the first place to look.
- **The immediate `fill_solid`+`FastLED.show()` on `SET_EFFECT`/`CLEAR_EFFECT` was kept** rather than dropped (plan §9's remedy #4) for the same headroom reason, and for parity with every existing theme-switch path (`switchToNextTheme()`, the theme-string dispatch) — the render loop would pick the new effect up within ~100 ms regardless, but an instant strip response reads better in a live demo.
- **`SET_EFFECT`'s log line reports `timeoutSec` (seconds), while `saveCustomEffectToPreferences()`'s log reports `timeoutMs` (milliseconds)** — a deliberate difference (the MQTT payload's own unit vs. the stored field's own unit), not an inconsistency to fix, but worth knowing before grepping the serial log for one or the other.
- **Not touched, per `## Plan` §6.4**: `publishState()`'s JSON schema still has no `"custom"` block (mode/colors/timeoutRemaining) — `THEME_NAMES[THEME_CUSTOM]` already yields `"theme":"Custom"` for free, which is enough for this phase's on-device verification. The richer block is [#0017](0017.md)'s, per [#0013](0013.md)'s children table.
- **Baseline drift**: `## Plan` §9's baseline (`1,226,976` bytes) was measured against `main` *before* #0015 merged; the actual branch point (`b837026`) already carries #0015's `1,229,328`. This ticket's before/after table in `## Verification` uses the real branch-point baseline, confirmed both by a fresh `esp32c3` build on this branch before any change and by a disposable `git worktree` at `b837026` for the `esp32c3-debug` figure (this branch had already diverged by the time the debug baseline was needed, and `Config.h` — gitignored — had to be copied into the worktree to build it at all).

### 2. New files, and why header-only

Two new headers; no new `.cpp`, no `platformio.ini` change, no new library.

- **`src/effect_parse.h`** (new) — the parser, the persistence *decision* function,
  and the `SET_EFFECT_PREFIX` literal. Includes `effects.h`. Every function
  `inline`. Depends on `<stdint.h>`, `<string.h>` only — **no `Arduino.h`, no
  `String`, no FastLED calls** (it touches `CRGB` only as a plain byte triple,
  which the test shim already provides).
- **`src/effects.h`** (edit) — add `EFFECT_MODE_NAMES[]`, `SETTINGS_VERSION`,
  `resetCustomEffect()`, `customEffectIsValid()`. These belong next to the enum and
  the struct they describe, and #0015/#0017 both want the name table.

Header-only for the same reason `time_utils.h` and `effects.h` are: `[env:native]`
does not compile project sources (`test_build_src` is off), so a `src/effect_parse.cpp`
could not be linked from a native test without dragging `main.cpp`, `WiFi.h` and
`FastLED.h` into the host build. `[env:native]` already carries `-I src`, so a header
needs no build change at all.

**Include-order contract applies transitively.** `effect_parse.h` includes
`effects.h`, which uses `CRGB`/`CHSV`/`sin8`/`min`/`max` without including
`<FastLED.h>`. Any test TU must include `fastled_shim.h` first. Restate this at the
top of `effect_parse.h`.

**Do not use Arduino `String` inside the parser.** It cannot compile natively, it
heap-churns per field, and `String` operator+ is a meaningful slice of the flash
this ticket is trying not to spend. The parser is `const char*` in, struct out.
`main.cpp` bridges with `msg.c_str()`.

```cpp
// src/effect_parse.h
static const char SET_EFFECT_PREFIX[] = "SET_EFFECT:";

enum EffectParseResult {
    EFFECT_PARSE_OK = 0,
    EFFECT_PARSE_NOT_OBJECT,     // missing/unbalanced braces, empty payload
    EFFECT_PARSE_NO_MODE,
    EFFECT_PARSE_BAD_MODE,
    EFFECT_PARSE_NO_COLORS,
    EFFECT_PARSE_BAD_COLOR_COUNT, // 0, or > MAX_CUSTOM_COLORS
    EFFECT_PARSE_BAD_COLOR,       // not #RRGGBB / RRGGBB
    EFFECT_PARSE_BAD_NUMBER       // speed/intensity non-numeric or > 255
};

inline EffectParseResult parseEffectPayload(const char* json, CustomEffectConfig& out);
inline const char* effectParseResultName(EffectParseResult r);
```

**`out` is a scratch struct owned by the caller, never the live `customEffect`.**
This is the structural guarantee behind "on any parse failure, keep prior state":
partial application is not a discipline the implementer has to remember, it is
unreachable. `main.cpp` does:

```cpp
CustomEffectConfig parsed;
EffectParseResult r = parseEffectPayload(msg.c_str() + (sizeof(SET_EFFECT_PREFIX) - 1), parsed);
if (r != EFFECT_PARSE_OK) { /* log, return — customEffect untouched */ }
```

`parseEffectPayload()` starts by calling `resetCustomEffect(out)`, so a rejected
parse also leaves no half-filled scratch for a careless caller to copy.

**The prefix offset is derived, never typed.** `sizeof(SET_EFFECT_PREFIX) - 1`, not
`11`. This is the exact defect that cost [#0008](0008.md) two rounds: a hand-typed
`substring(18)` silently ate a digit, and the test that "covered" it compared one
copy of the literal against another. Declaring `SET_EFFECT_PREFIX` in
`effect_parse.h` lets the native test pin the arithmetic against the same literal
the handler uses.

#### 3.2 Field extraction

Field order and whitespace fall out for free from a *lookup*-shaped parser rather
than a *sequential* one:

```cpp
// Returns a pointer to the first non-space character after `"key" :`, or nullptr.
inline const char* findField(const char* json, const char* key);
```

Implementation: walk `json` looking for `"`; on each opening quote, compare the
following characters case-insensitively against `key` and require a closing `"`;
on a match, skip whitespace, require `:`, skip whitespace, return. Otherwise
continue past the closing quote and keep scanning. Because each field is found
independently by name, **ordering is irrelevant and needs no test-time
special-casing** (test it anyway — §7 case 3), and whitespace is handled in exactly
two helpers (`skipWs`, and the scan itself).

Case-insensitivity lives *inside* the parser, on both key names and mode names.
Do **not** pre-uppercase the payload in `main.cpp` and feed the parser `msgUpper`:
that would put a normalization step on the device path that the native tests do not
execute, which is precisely the "test passes but exercises something else" shape
this project has already been bitten by twice. `main.cpp` matches the command with
`msgUpper.startsWith(...)` (consistent with every other handler) but passes the
**original-case `msg`** to the parser, and logs the original-case `msg` on rejection.

#### 3.3 Value parsers

All four are `inline`, take `const char*`, return `bool`, and never write to `out`
on failure:

- **`parseUIntCapped(const char*& p, uint32_t cap, uint32_t& value, bool& capped)`** —
  requires ≥1 digit; consumes digits only (a leading `-`, `+`, `.` or quote is a
  failure, so `"speed":"128"` is rejected — a quoted number is a different type, and
  accepting it invites a second parse path nobody tests); once the accumulator
  exceeds `cap` it pins at `cap` and sets `capped`, so **no digit string of any
  length can overflow `uint32_t`**. The caller decides what `capped` means:
  `timeout` clamps (§4), `speed`/`intensity` reject. One helper, two policies,
  no duplicated accumulation logic.
- **`parseHexColor(const char* s, size_t len, CRGB& c)`** — accepts an optional
  leading `#`, then **exactly** six hex digits and nothing else. 5 digits, 7 digits,
  `0x` prefix, `#GG0000`, an empty string: all rejected. Three `hexByte()` calls,
  each two `hexNibble()` calls; `hexNibble` returns −1 on a non-hex character.
  Shorthand `#RGB` is deliberately **not** supported (document it; it is a second
  code path for a form nobody sends from a script).
- **`parseQuotedSpan(const char*& p, const char*& start, size_t& len)`** — requires
  `"`, records the span to the next `"`, and **fails on a backslash**. There is no
  escape processing: an escape has no meaning in a mode name or a hex color, and
  rejecting is cheaper and safer than half-implementing unescaping.
- **`parseColorArray(const char* p, CustomEffectConfig& out)`** — requires `[`,
  then quoted spans separated by `,` with whitespace anywhere, then `]`. Counts as
  it goes; **stops and rejects on the 9th element** rather than parsing all of them
  first (bounds are enforced by the loop, not by a check afterwards that a future
  edit can slip past). Empty array → `BAD_COLOR_COUNT`.
- **`parseMode(const char* s, size_t len, EffectMode& m)`** — linear scan of
  `EFFECT_MODE_NAMES[9]` with a case-insensitive length-checked compare. Names
  only; a bare integer `"mode":2` is **not** accepted (document it — the spec
  defines the wire format as names, and one form means one thing to test).

#### 3.4 Deliberate limitations, to be written into the header comment

This is a shape-specific extractor, not a JSON validator. State plainly what it
does not do, so a future reader does not assume guarantees it never made:

- Unknown extra keys are **ignored** (forward compatibility — a future field
  arriving from a newer script must not brick an older device).
- A key name occurring inside a *string value* could in principle be mistaken for a
  key. Unreachable with this schema (values are hex colors and mode names, none of
  which contain `mode`/`colors`/`speed`/`intensity`/`timeout`), and it is bounded
  by the fact that a mis-found field then has to parse as a valid value anyway.
- Only a top-level `{ … }` is accepted; nesting is neither parsed nor rejected
  beyond that.
- The only structural gate is: after trimming, the payload starts with `{` and ends
  with `}`. `SET_EFFECT:garbage` and `SET_EFFECT:` are rejected there.

### 4. Validation and the exact rejection surface

| Field | Rule | On violation |
|---|---|---|
| structure | trimmed payload starts `{`, ends `}`, non-empty | `NOT_OBJECT` |
| `mode` | required; matches one of the 9 `EFFECT_MODE_NAMES` (case-insensitive) | missing → `NO_MODE`; unknown → `BAD_MODE` |
| `colors` | required; array of 1–8 entries | missing → `NO_COLORS`; 0 or ≥9 → `BAD_COLOR_COUNT` |
| each color | optional `#` + exactly 6 hex digits, fully consumed | `BAD_COLOR` |
| `speed` | optional, default **128**; bare integer 0–255 | non-numeric or >255 → `BAD_NUMBER` |
| `intensity` | optional, default **128**; bare integer 0–255 | non-numeric or >255 → `BAD_NUMBER` |
| `timeout` | optional, default **0** (= until changed); seconds; **>28800 clamped to 28800, never rejected** | non-numeric → `BAD_NUMBER` |
| `timeoutMs` | `timeoutSeconds * 1000UL`; max 28,800,000 — fits `uint32_t` | — |
| `revertTheme`, `activatedAt` | **not** payload fields; set by the caller (§6) | — |

Rationale for the two asymmetries, so a reviewer does not read them as
inconsistency: `timeout` clamps because [#0013](0013.md) settles it — "12 hours"
is an unambiguous intent to leave it running for the event, and refusing the whole
command over it produces nothing at all. `speed`/`intensity` reject because 0–255 is
the *entire expressible range* of the field — a 300 is a typo or a unit confusion,
not an intent, and there is no "more than maximum" to honour.

**The rejection surface, exactly:**

1. `ESP_LOGE(TAG, "SET_EFFECT rejected (%s): '%.160s'", effectParseResultName(r), msg.c_str())`.
   **`ESP_LOGE`, not `LOGW`/`LOGI`.** `[env:esp32c3]` builds at
   `CORE_DEBUG_LEVEL=1` / `CONFIG_LOG_MAXIMUM_LEVEL=1` (see the comment block at the
   top of `platformio.ini`) — **only `ESP_LOGE` survives in a release build.** A
   rejection logged at `W` or `I` is invisible on every device that will ever run
   this in the field, which silently voids the ticket's "diagnosable from the serial
   log" requirement while looking correct on the bench under `esp32c3-debug`. The
   existing `OTA_URL` refusals are `ESP_LOGW` and have this problem today; do not
   copy them.
2. The offending payload is **truncated to 160 characters** in the log
   (`%.160s`) — a full legal payload is ~166 bytes (§9.1), so a rejected one is
   bounded and readable, and a pathological one cannot flood the log.
3. **Nothing else happens.** No `publishState()`, no NVS write, no `currentTheme`
   change, no `hueIndex` reset, no `FastLED.show()`. An observer watching retained
   state sees literally no event. The device stays exactly on the theme or effect it
   was on.
4. No MQTT error reply. Diagnosis is serial-only in this phase — call this out in
   `docs/mqtt_commands.md` as a known limitation, because it means a malformed
   payload sent from the Pi produces *silence*, and the operator needs to know that
   silence is the failure mode rather than assume the broker ate it.

On success, log at `ESP_LOGI` with mode name, color count, speed, intensity and
timeout seconds. That one is genuinely debug-only and correctly invisible in release.

### 5. NVS persistence, the version byte, and the OTA rollout

#### 5.1 Additions to `src/effects.h`

```cpp
static const uint8_t SETTINGS_VERSION = 2;   // spec's suggested value; 1 == "the
                                             // pre-#0016 layout", which never wrote
                                             // a version byte at all (reads as 0)

static const char* const EFFECT_MODE_NAMES[] = {
    "BLEND","FLICKER","CHASE","WIPE","SCAN","SPARKLE","PULSE","STROBE","COLORLOOP"
};
static_assert(sizeof(EFFECT_MODE_NAMES)/sizeof(EFFECT_MODE_NAMES[0]) == EFFECT_COLORLOOP + 1,
              "one name per EffectMode");

inline void resetCustomEffect(CustomEffectConfig& c);        // explicit field assignment
inline bool customEffectIsValid(const CustomEffectConfig& c);
```

`static const char* const`, not `const char* NAMES[]` — [#0014](0014.md)'s round-2
review flagged that `THEME_NAMES[]` in `themes.h` has **external linkage** and would
be a duplicate-symbol link error the moment two TUs in one test binary include it.
Do not add a second instance of that bug.

`resetCustomEffect()` assigns fields explicitly rather than `memset`-ing, so the
zero-init that the ticket cares about is a named, native-testable function and not
an incidental property of a `memset` call site in `main.cpp`. Values:
`mode = EFFECT_BLEND`, all colors black, `colorCount = 0`, `speed = 128`,
`intensity = 128`, `timeoutMs = 0`, `activatedAt = 0`, `revertTheme = THEME_GREEN`.

> Note `speed`/`intensity` reset to **128, not 0**. Zero speed is a stopped
> animation; the defaults documented everywhere else in this tree are 128, and a
> zero-initialized config that renders as "frozen" would be a confusing failure mode
> for a device that fell back after a version mismatch. The ticket's "zero-initialize"
> means "known-good defaults, not leftover bytes" — that is what this does.

`customEffectIsValid()` — `colorCount >= 1 && colorCount <= MAX_CUSTOM_COLORS`,
`mode <= EFFECT_COLORLOOP`, **`revertTheme < CYCLEABLE_THEME_COUNT`** (so a stored
`revertTheme == THEME_CUSTOM` — an infinite self-revert — is rejected outright),
`timeoutMs <= 28800000UL`.

#### 5.2 The load decision, as a pure function

`Preferences` does not exist natively, so the *decision* must be separable from the
I/O or requirement 3 has no native coverage at all. Put this in `effect_parse.h`:

```cpp
// Returns true if the stored blob was accepted; false if `out` was reset to defaults.
inline bool applyLoadedCustomEffect(uint8_t storedVersion, size_t storedLen,
                                    const void* bytes, CustomEffectConfig& out);
```

Logic, in order: reset `out` first; accept only if
`storedVersion == SETTINGS_VERSION` **and** `storedLen == sizeof(CustomEffectConfig)`
**and** the copied struct passes `customEffectIsValid()`; on acceptance force
`out.activatedAt = 0`. `main.cpp`'s loader becomes a four-line `Preferences`
wrapper with no policy in it.

`activatedAt` is forced to 0 because a `millis()` stamp has no meaning across a
reboot. Nothing in this phase reads it; [#0017](0017.md) replaces the field's role
with an absolute wall-clock end time. **Do not** re-seed it to `nowMs()` on load —
that would establish exactly the "silently restart the timer" semantics
[#0013](0013.md) rejects, and #0017 would have to unpick it.

#### 5.3 Wiring into `loadAllPreferences()`

Insert the custom-effect load **inside the existing read-only session**, and
**before** the theme-resolution block at 388–417 — the `THEME_CUSTOM` boot guard at
419–423 tests `customEffect.colorCount == 0`, so it reads garbage if the config has
not been loaded yet. Concretely, after the LED-config safety checks (~386):

```cpp
uint8_t fxVer  = preferences.getUChar("fx_ver", 0);
size_t  fxLen  = preferences.getBytesLength("fx_cfg");
uint8_t fxBuf[sizeof(CustomEffectConfig)];
size_t  got = (fxLen == sizeof(fxBuf)) ? preferences.getBytes("fx_cfg", fxBuf, sizeof(fxBuf)) : 0;
if (!applyLoadedCustomEffect(fxVer, got, fxBuf, customEffect)) {
    if (fxVer != 0 || fxLen != 0) ESP_LOGE(TAG, "custom effect: stored v%u/%uB rejected, reset to defaults", fxVer, (unsigned)fxLen);
}
refreshCustomHues();
```

Then leave 388–423 exactly as they are. The boot guard now does real work for the
first time: a device that stored a custom effect, then took an OTA that changed
`SETTINGS_VERSION`, boots with `theme == 6` and `colorCount == 0` and correctly
falls back to Green. Add the `hueIndex` note: the existing clamp at 430–432 uses
`getCurrentColorCount()`, which for `THEME_CUSTOM` returns `colorCount` — the guard
running first is what keeps that from computing `maxHueIndex = -1`. **Do not reorder
those three blocks.**

Save side — `saveCustomEffectToPreferences()`, modelled on the seven existing
helpers:

```cpp
preferences.begin("glow_kitchen", false);
preferences.putUChar("fx_ver", SETTINGS_VERSION);
preferences.putBytes("fx_cfg", &customEffect, sizeof(customEffect));
preferences.end();
```

Both keys are ≤15 characters (the NVS key limit). Write the version byte **after**
nothing and the blob **after** it in the same session; if the blob write fails the
version byte is already correct, which is the safe direction (a correct version with
a stale/short blob is caught by the length check on the next load).

#### 5.4 OTA rollout compatibility — read this before touching the load path

This ships over the air to devices already running v0.0.5 with the old NVS layout.
Trace both directions:

- **Upgrade.** An old device has no `fx_ver` and no `fx_cfg` key. `getUChar` returns
  the default `0`, `getBytesLength` returns `0` → `applyLoadedCustomEffect` resets to
  defaults and the mismatch log is suppressed (`fxVer == 0 && fxLen == 0` is "never
  written", not "corrupt", and should not shout on every boot of every device on the
  first upgrade). `theme` still holds 0–5 because old firmware could not write 6, so
  `THEME_CUSTOM` is unreachable on that first boot. **The specific failure the
  version byte prevents** — reading whatever bytes happen to occupy a
  newly-used NVS region as a config — cannot occur, because the region is keyed and
  absent rather than merely uninitialized. Keep the byte anyway: it is the guard for
  the *next* layout change, which is the one that will actually have bytes there.
- **Downgrade / rollback.** `Preferences` is per-key, so pre-#0016 firmware reading
  this NVS simply never asks for `fx_ver`/`fx_cfg` and behaves exactly as before —
  except that `theme` may hold `6`, which old firmware validates as
  `savedTheme < THEME_COUNT`. On pre-#0014 firmware `THEME_COUNT` was 6, so 6 is
  rejected → falls back to Green. On #0014-or-later `THEME_COUNT` is 7, so 6 is
  accepted and the #0014 boot guard catches it (`colorCount == 0`) → Green. **Both
  rollback targets land on Green rather than a crash.** Say this in `## Verification`;
  it is the single most likely field scenario and it is free.
- **NVS exhaustion.** `putBytes` of ~44 bytes into a namespace holding eight small
  keys will not exhaust the default NVS partition, but if it ever fails, the next
  boot's length check rejects and resets. No special handling needed; do not add a
  retry.

### 6. Command semantics

#### 6.1 `SET_EFFECT:` — placement and the `revertTheme` trap

Insert the handler in the `startsWith` chain, immediately after the `OTA_AUTO:`
branch (~836) and **before** the final `else` that does theme-string dispatch.
Detect with `msgUpper.startsWith(SET_EFFECT_PREFIX)`; parse `msg` (original case).

On `EFFECT_PARSE_OK`, in this order:

```cpp
HueTheme prevRevert = customEffect.revertTheme;
customEffect = parsed;
customEffect.revertTheme = (currentTheme != THEME_CUSTOM) ? currentTheme : prevRevert;
customEffect.activatedAt = nowMs();
currentTheme = THEME_CUSTOM;
hueIndex = 0;
refreshCustomHues();
if (!ledsEnabled) ledsEnabled = true;
saveThemeToPreferences();
saveCustomEffectToPreferences();
fill_solid(leds, numLeds, CHSV(customHues[0], 255, 200));  // parity with the theme path
FastLED.show();
publishState();
```

The `prevRevert` ternary is the whole point of the ticket's item 4: **two
back-to-back `SET_EFFECT`s must not make the second one's revert target the first
effect.** Write it as an explicit local, not as an `if` around the assignment that a
later edit can reorder past `customEffect = parsed`. Note the ordering hazard:
`customEffect = parsed` overwrites `revertTheme` (with `resetCustomEffect`'s
`THEME_GREEN`), which is exactly why `prevRevert` is captured *before* the copy.

`nowMs()`, not `millis()` — the `ENABLE_CLOCK_OFFSET` bench harness exists so the
rollover can be reached in seconds, and a raw `millis()` here would silently opt this
field out of it right before [#0017](0017.md) starts doing arithmetic on it.

`hueIndex = 0` matters: the previous theme may have had 8 hues and the new effect 1,
and `renderFlicker()` indexes `colors[hueIndex]` unguarded.

`if (!ledsEnabled) ledsEnabled = true;` mirrors the theme-string handler at 878 —
setting an effect on a strip that is off should turn it on, same as sending
`RAINBOW` does. Deviation allowed if the implementer finds the theme path actually
behaves differently.

**No topic restriction.** `SET_EFFECT` on `lights/all/cmd` sets the whole
installation to one effect, which is a normal thing to want and trivially undone.
It is not `OTA_URL`.

#### 6.2 `CLEAR_EFFECT`

Exact match `msgUpper == "CLEAR_EFFECT"`, placed with the other exact-match commands
in the trailing `else` block (near `TOGGLE`/`ON`/`OFF`). **Explicitly no
`/all/` check** — add a one-line comment saying so and why, because the next person
to read the `OTA_URL` guard twelve lines up will otherwise "fix" the omission.

```cpp
if (currentTheme != THEME_CUSTOM) return;             // idempotent no-op
HueTheme t = customEffect.revertTheme;
if (t >= CYCLEABLE_THEME_COUNT) t = THEME_GREEN;      // never revert into THEME_CUSTOM
currentTheme = t;
hueIndex = 0;
customEffect.timeoutMs = 0;
customEffect.activatedAt = 0;
saveThemeToPreferences();
saveCustomEffectToPreferences();
fill_solid(...); FastLED.show(); publishState();
```

Keep `mode`/`colors`/`colorCount` rather than resetting the whole struct: it costs
nothing, and it keeps `colorCount == 0` meaning "never configured" for the boot
guard rather than the ambiguous "cleared". Zeroing `timeoutMs`/`activatedAt` is what
matters — a stale timeout left behind here is a live landmine the moment
[#0017](0017.md) lands. Deviation allowed (full reset is defensible) but say which
you chose and why.

#### 6.3 The cancel path — enumerate every site

Factor one helper and call it from **all three** non-`CLEAR_EFFECT` exits from a
custom effect:

```cpp
void cancelCustomEffect() {                 // caller sets currentTheme itself
    if (customEffect.timeoutMs == 0 && customEffect.activatedAt == 0) return;
    customEffect.timeoutMs = 0;
    customEffect.activatedAt = 0;
    saveCustomEffectToPreferences();
}
```

Call sites:

1. **Theme-string dispatch** (`GREEN`, `RAINBOW`, `PINK_PONY`, `OCEAN_WAVES`,
   `SUNSET`, `FOREST`, plus `THEME_*`/`SCENE_*`/`OCEAN`/`PINK_PONY_CLUB` aliases) —
   inside `if (themeIdentified)`, before `currentTheme = newTheme`, guarded by
   `if (currentTheme == THEME_CUSTOM)`. Note the existing gate
   `if (newTheme != currentTheme || !ledsEnabled)` already admits this case
   (`newTheme != THEME_CUSTOM` is always true), so the visual change already
   happens today — **what is missing is only the timeout teardown**, and that is
   precisely the thing that would otherwise yank the user off their chosen theme
   minutes later once #0017 exists.
2. **`switchToNextTheme()`** — covers `NEXT_THEME` over MQTT *and* the IR remote
   (`handleGrayRemoteButton()` → 602/607). One call here covers both; that is why
   the helper goes in the switch functions and not in `onMqttMessage()`.
3. **`switchToPreviousTheme()`** — same.

From `THEME_CUSTOM` (== 6), `(6 + 1) % 6` lands on Rainbow and
`(6 - 1 + 6) % 6` on Forest. That is arbitrary but harmless and needs no fix —
document it in `docs/mqtt_commands.md` so it is not filed as a bug later.

`OFF`/`TOGGLE` deliberately do **not** cancel: blanking the strip is not choosing a
different look, and a timed effect should still be configured when the lights come
back on.

#### 6.4 `publishState()` — leave it alone in this phase

`THEME_NAMES[THEME_CUSTOM]` is already `"Custom"`, so `STATUS` flips to
`"theme":"Custom"` for free and gives the on-device MQTT round-trip something to
observe. The `custom` block with `timeoutRemaining` is [#0017](0017.md)'s, per
[#0013](0013.md)'s children table — adding it here spends flash twice and splits one
schema change across two tickets. Deviate only if the on-device verification genuinely
cannot be done without it; if so, say so.

### 7. Native test matrix

New directory **`test/test_effect_parse/`** with a single `test_effect_parse.cpp`.

**Why a sibling directory and not a second file in `test/test_effects/`:** PlatformIO
builds each test subdirectory into its own binary, but all `.cpp` files *within* one
subdirectory link together — and `THEME_NAMES[]` in `src/themes.h` has external
linkage, so a second TU alongside `test_effects.cpp` is a duplicate-symbol link
error ([#0014](0014.md) `## Gotchas`, "Known limitations"). A sibling directory
sidesteps it entirely and keeps a parser failure from being confused with a renderer
regression. Include the shim as `#include "../test_effects/fastled_shim.h"` **first**
(include-order contract), then `"effects.h"`, `"effect_parse.h"`. Do not move or edit
`fastled_shim.h` — #0014's harness depends on it and must keep passing untouched.

test takes parameters. If a definition turns out to be needed (an inline that
odr-uses the externs), define them in the test file rather than reaching into

#### 9.1 The PubSubClient buffer — check this, it is the sharpest edge

`PubSubClient` is at its **default `MQTT_MAX_PACKET_SIZE` of 256 bytes** for the
whole packet (`.pio/libdeps/*/PubSubClient/src/PubSubClient.h:26`), and nothing in
`src/main.cpp` calls `setBufferSize()`. An oversized PUBLISH is **discarded without
invoking the callback** — no log, no error, nothing. Arithmetic:

- worst-case legal payload: `SET_EFFECT:` (11) + `{"mode":"COLORLOOP",` (20) +
  `"colors":[` (10) + 8 × `"#RRGGBB"` + 7 commas (79) + `],` (2) +
  `"speed":128,` (12) + `"intensity":128,` (16) + `"timeout":28800}` (16) = **166 bytes**
- packet overhead: fixed header 1 + remaining-length 2 + topic-length 2 + topic
  `lights/kitchen/cmd` 18 = **23**
- total **189 of 256** — fits, with ~67 bytes of margin.

So no change is required, but the margin is undocumented and would be silently
consumed by a longer device-name topic plus a future field. Actions: (a) test case
28 pins the arithmetic natively; (b) `docs/mqtt_commands.md` states the ~233-byte
payload ceiling and that an oversized command is dropped with no error;
(c) `mqtt.setBufferSize(512)` in `ensureMqtt()` before `mqtt.connect()` is an
allowed deviation if the on-device pass shows trouble — it costs ~512 bytes of heap
and a handful of flash, and it must be re-applied after every reconnect.

### 13. Uncertainties, and where to deviate

- **`SETTINGS_VERSION = 2`** follows the spec's suggestion. Nothing has ever written
  a version byte, so 1 or 2 are equally arbitrary; 2 matches the spec's text and
  leaves "1" meaning the historical layout. Not worth debating.
- **`sizeof(CustomEffectConfig)` (~44 bytes) as the stored length** couples the NVS
  blob to compiler struct layout. That is exactly what the version byte plus the
  length check exist to catch, and a byte-by-byte serializer would cost more flash
  than the problem is worth at this size. If the implementer would rather serialize
  field-by-field, that is a legitimate deviation — say so, and keep the same
  version/length/validity gate.
- **Rejecting `speed`/`intensity` > 255 vs. clamping.** §4 argues for rejecting.
  Clamping is defensible; if you clamp, say so in `## Fix`, update the docs, and
  update the test matrix (case 15) rather than leaving a test asserting the other
  behavior.
- **`CLEAR_EFFECT` keeping vs. wiping `colors`/`mode`.** §6.2 keeps them. Either is
  fine; the non-negotiable part is that `timeoutMs` and `activatedAt` are zeroed.
- **Numeric `"mode":2`** is rejected by this plan. If the on-device pass makes the
  string form awkward for some script, accepting integers too is a small addition —
  but then it needs its own test cases, including the out-of-range one.
- **`publishState()` untouched** (§6.4). If the on-device MQTT pass genuinely cannot
  confirm the effect applied without a `custom` block, add the minimum
  (`"mode"` only, no `timeoutRemaining`) and note the overlap with
  [#0017](0017.md).
- **`min_spiffs` / ArduinoJson.** Not in scope, not a fallback, not a tie-breaker.
  If the parser cannot be made to fit — which §9's estimate says will not happen —
  stop and report rather than deciding a partition change that requires a USB pass
  on every device.
- **Line numbers in §1 will have drifted.** Every symbol named there is stable;
  navigate by name.

## Long Description

Step 4 of the spec's build order. See `docs/glowkitchen-custom-effects-spec.md` § "New MQTT command" for the payload shape.

### Do not use ArduinoJson

The parent settles this and it is binding: current flash headroom is 84,000 bytes and ArduinoJson typically costs 20–30 KB before a single renderer is written — and [#0015](0015.md) is spending headroom at the same time. [#0009](0009.md) is what happens when a release exceeds the OTA slot: it shipped and no device could install it. The payload is a fixed shape with at most 8 hex color strings, so a purpose-built parser is both cheaper and easier to bound.

If someone concludes ArduinoJson is unavoidable anyway, **stop and settle the `min_spiffs` partition question first** ([#0009](0009.md) notes, [#0004](0004.md) item 6) — that decision needs a USB pass on every device and cannot be discovered late. Bail rather than deciding it inside this ticket.

### Validation — reject cleanly, never partially apply

- `mode` must be a valid `EffectMode`; anything else is a rejection.
- `colors` count must be 1–8; hex strings must parse fully.
- `speed` / `intensity` default to 128 when absent.
- `timeout` absent or `0` means "until changed"; values above 28800 are **clamped to 28800, not rejected** (the parent explains why).
- **On any parse failure, keep the prior state.** A half-applied config is worse than a rejected command — log the rejection with the offending payload so it's diagnosable from the serial log.

### Persistence

- `CustomEffectConfig` persisted to NVS with a `SETTINGS_VERSION` byte.
- **On version mismatch, zero-initialize** rather than trusting whatever bytes occupy the newly-used region after an OTA. This is the specific failure the version byte exists to prevent.
- The `THEME_CUSTOM` boot guard from [#0014](0014.md) must still hold: `currentTheme == THEME_CUSTOM` with an uninitialized effect falls back to `THEME_GREEN`.

### Topic scope

`CLEAR_EFFECT` is safe on `lights/all/cmd`, unlike `OTA_URL` and `RESTART` — worst case the whole installation returns to its normal theme, which is the recovery action anyway.

## Expected behavior

`SET_EFFECT` with a valid payload applies arbitrary colors and any of the nine modes, surviving reboot. `CLEAR_EFFECT` reverts to the previous theme immediately. Malformed payloads change nothing and are logged.

## Actual behavior

No such commands exist; effects can only be selected from the six built-in themes.

**APPROVED** by an independent Opus pass, which re-ran all builds and tests from scratch (release 1,234,912 / debug 1,282,256 / 60 of 60 cases actually executing, case list read rather than trusting the summary line).

### The palette round-trip, measured rather than assumed

The native shim's `rgb2hsv_approximate` is a stub returning `CHSV(r,g,b)`, so **no in-tree test covers the real conversion**. The reviewer host-compiled FastLED 3.10.3 to measure it:

| Input | Stored | Rendered |
|---|---|---|
| `#FF69B4` hot pink | h221 / s92 | (123, 64, 98) |
| `#FF1493` deep pink | h188 / s184 | (54, 12, 114) |
| `#FFB6C1` light pink | h240 / **s40** | (149, 111, 119) |

Saturation and value genuinely survive parse → store → render, and the three read as three distinct shades. The desaturated light pink is the *most* faithful of the three — which is the payoff [#0013](0013.md)'s palette decision was made for. The largest error is a hue drift on the saturated `#FF1493` toward violet, inherent to `rgb2hsv_approximate` + `hsv2rgb_rainbow` and therefore to that decision, not introduced here.

The plan-amendment deviation (parse to `CRGB`, convert at refresh time via `refreshCustomPalette()`) is behaviorally identical — same conversion function, later call site — and stores exact RGB in NVS, so it is strictly better than storing `PaletteColor` directly.

### `BLEND` and `FLICKER` discard saturation

`renderBlend()` and `renderFlicker()` hard-code `sat=255`, required by [#0015](0015.md)'s byte-identical-legacy constraint. The same three pinks under those two modes render (99,0,58) / (46,0,111) / (131,0,25) — crimson, violet, dark red. **Any custom effect relying on desaturated colors must use a saturation-preserving mode**: `CHASE`, `WIPE`, `SCAN`, `SPARKLE`, `PULSE`, `STROBE`, or `COLORLOOP`. Not a defect; a consequence of the compatibility promise, recorded so the demo scripts respect it.

### Independently verified

- The implementer's two anomalous perturbations (P1, P6) were reproduced and their "intentional test coupling" explanation **confirmed true, not a rationalization** — case 20 genuinely embeds case 10's 9-color payload, and case 01 independently pins the same speed default as case 14.

- Partial application is **structurally impossible** — the parser writes only a caller-owned scratch struct and resets it first; `customEffect` is copied into only on `EFFECT_PARSE_OK`.
- **Cancel sites: exactly three, none missed** — theme-string dispatch, `switchToNextTheme`, `switchToPreviousTheme` (the latter two covering IR), plus `CLEAR_EFFECT`.
- Scope clean: `timeoutMs` is only written, zeroed and logged. No expiry check anywhere — [#0017](0017.md) has not leaked in.
