# 0021 — A retained theme on lights/all/cmd cancels any custom effect seconds after it is applied

| | |
|---|---|
| **Status** | resolved |
| **Module** | MQTT / LED |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-28 |
| **Closed** | 2026-08-28 |

## Description

A custom effect could not survive on the dev board: `SET_EFFECT` applied correctly, then something reverted the strip to Forest a few seconds later. The cause was a **retained** `FOREST` on `lights/all/cmd`. MQTT redelivers a retained message to every subscriber on every reconnect, so nobody was publishing it — the broker was replaying it, forever, and any WiFi blip cancelled the running effect.

## Long Description

Carved out of [#0013](0013.md)'s handoff, which spent about an hour re-confirming "the firmware works" while the actual cause sat unexamined on the broker. A 45-second sniff of `lights/#` shows it immediately, since retained messages arrive at subscribe time:

```
lights/all/cmd  FOREST          (retained -- redelivered on every reconnect)
lights/tv/cmd   SET_BRIGHTNESS:113
...
```

Observed directly in the serial log while testing: the device reconnects to MQTT, and in the same millisecond receives the retained broadcast.

```
[4214440] ensureMqtt(): MQTT connected; subscribing...
[4214476] onMqttMessage(): MQTT Topic: lights/all/cmd, Payload: 'FOREST'
```

The device subscribes to `lights/all/cmd` like every other strip, so it obeyed. Two independent test runs lost their effect this way before the cause was identified.

### Why the device, not the broker, is the right place to fix it

Clearing the retained message works until the next one is published, and the publisher is outside this repo — a Home Assistant automation, or Glow Panel, whose `SetTheme` currently publishes **retained unconditionally** (`app.go:232`, `a.broker.Publish(id, true)`, unlike `SetBrightness`/`SetPower` which respect a config flag). Any of those can put it back at any time.

More to the point, the effect and its expiry are already device-owned state: persisted to NVS, resumed across reboots with a wall-clock end time ([#0017](0017.md)). A fleet-wide broadcast is not a reason to discard state the device is deliberately maintaining.

## Expected behavior

An active custom effect keeps running until its timeout expires, a `CLEAR_EFFECT` arrives, or someone deliberately commands *this* device to a different theme. A theme broadcast to the whole installation does not cancel it.

## Actual behavior

Any theme name arriving on `lights/all/cmd` — including a retained one nobody sent — immediately cancelled the effect and its timeout.

## Fix

In `onMqttMessage()`'s theme-command branch (`src/main.cpp`), a theme is ignored when a custom effect is active **and** the command arrived on a broadcast topic:

```c
// src/theme_command.h -- no Arduino, no FastLED, so the native suite can reach it
inline bool shouldIgnoreBroadcastTheme(const char* topic, bool customEffectActive) {
    if (!customEffectActive || topic == nullptr) return false;
    return strstr(topic, "/all/") != nullptr;
}

// src/main.cpp, onMqttMessage()'s theme branch
if (themeIdentified &&
    shouldIgnoreBroadcastTheme(topic, currentTheme == THEME_CUSTOM)) {
    ESP_LOGI(TAG, "Ignoring broadcast theme '%s' on %s: custom effect active "
                  "(mode=%s, %ld s remaining)", ...);
    themeIdentified = false;
}
```

**Scoped to broadcasts on purpose.** A theme sent to this device's own topic is someone deliberately taking control of this strip and still wins immediately — that and `CLEAR_EFFECT` are how a person overrides a running effect. Same reasoning as the existing `OTA_URL` broadcast refusal a few lines above: `/all/` is for the fleet, the device topic is for the device.

`SET_EFFECT` and `CLEAR_EFFECT` on `/all/` are unaffected and still apply to every device, per [#0016](0016.md)'s deliberate decision not to topic-restrict them.

## Verification

```
pio run -e esp32c3            # SUCCESS
pio run -e esp32c3-debug      # SUCCESS, flashed to the dev board over USB
pio test -e native            # 101 test cases: 101 succeeded
```

On hardware (dev board `84fce68774a4`), read through `scripts/monitor_serial.py`. Apply an effect, then fire the exact broadcast that used to kill it:

```
[23772] SET_EFFECT applied: mode=SPARKLE colors=3 speed=128 intensity=255 timeoutSec=60
[27860] Ignoring broadcast theme 'FOREST' on lights/all/cmd: custom effect active
        (mode=SPARKLE, 56 s remaining)
[31801] Heartbeat - theme: Custom, LEDs: ON
```

The effect survived. The device-targeted path still overrides, confirmed in the same session — `GREEN` published to `lights/84fce68774a4/cmd` while a SPARKLE effect was running:

```
[52746] saveThemeToPreferences(): Theme saved: Custom
[55826] saveThemeToPreferences(): Theme saved: Green
[61802] Heartbeat - theme: Green, hue index: 3, LEDs: ON
```

**Native test — added, and proved able to fail.** The predicate was originally
written inline in `onMqttMessage()` where no host test could reach it. It now
lives in `src/theme_command.h` as `shouldIgnoreBroadcastTheme(topic,
customEffectActive)`, free of Arduino and FastLED, with ten cases in
`test/test_theme_command/`: the two inputs crossed against each other, three
substring hazards (`lights/allotment/cmd`, `lights/hall/cmd`,
`lights/wall/cmd` — all contain "all", none is the broadcast topic), and null
and empty topics.

Deliberate perturbation, the standard [#0008](0008.md), [#0014](0014.md) and
[#0017](0017.md) each failed once:

- Dropping the `customEffectActive` guard so the rule always fires:
  `test_broadcast_obeyed_when_no_effect_active` **FAILED** — which is the case
  that would silently break every existing fleet-wide automation.
- Matching bare `"all"` instead of `"/all/"`: all three substring-hazard tests
  **FAILED**.
- Reverting both: 101/101.

Re-flashed and re-confirmed on hardware after the extraction, so the shipped
binary exercises the tested predicate rather than the original inline copy:

```
[12256] SET_EFFECT applied: mode=SPARKLE colors=3 speed=128 intensity=255 timeoutSec=60
[16243] Ignoring broadcast theme 'FOREST' on lights/all/cmd: custom effect active
        (mode=SPARKLE, 57 s remaining)
[20312] Heartbeat - theme: Custom, LEDs: ON
[22285] saveThemeToPreferences(): Theme saved: Green     <- device-targeted GREEN still wins
```

**Also not verified:** behavior on the five deployed strips, which run 0.0.5 and do not have this firmware.

## Notes

- Clearing the retained message is still worth doing once, so the fleet stops getting a spurious `FOREST` on every reconnect: `mosquitto_pub -h $MQTT_BROKER -u $MQTT_USERNAME -P $MQTT_PASSWORD -t lights/all/cmd -r -n`. That is a broker-side cleanup, not a substitute for this fix.
- Glow Panel's retained theme publish (`app.go:232`) is a likely source and is called out in `docs/glowpanel_effects_integration.md`. Worth changing to respect `a.cfg.Retain`; a separate repo, so not tracked here.
