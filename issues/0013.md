# 0013 — Ad hoc custom effects: nine effect modes, arbitrary colors, and a bounded auto-revert timeout

| | |
|---|---|
| **Status** | open |
| **Module** | LED / Rendering / MQTT |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-17 |

## Description

Colors and effects can only be chosen from six hardcoded themes. Implement the engine in `docs/glowkitchen-custom-effects-spec.md`: built-in themes become named presets of a generic renderer, arbitrary colors and effects arrive over MQTT, and a custom effect can carry an **optional timeout after which the strip reverts to its previous theme on its own** — up to a maximum of 8 hours, so an effect can be set for an event and left to run.

## Long Description

### The nine effect modes

| # | mode | new? | behavior |
|---|---|---|---|
| 0 | `BLEND` | existing | today's `slowBlend()` — gradient blending, scrolling |
| 1 | `FLICKER` | existing | today's `flickerLEDs()` — per-LED candle flicker |
| 2 | `CHASE` | new | a run of lit LEDs travelling along the strip |
| 3 | `WIPE` | new | color fills progressively from one end |
| 4 | `SCAN` | new | Larson/Cylon — a band sweeping back and forth |
| 5 | `SPARKLE` | new | random LEDs pop and fade |
| 6 | `PULSE` | new | breathing — whole strip fades up and down |
| 7 | `STROBE` | new | hard on/off flashing |
| 8 | `COLORLOOP` | new | whole strip cycles through the colors |

`speed` and `intensity` (0–255, default 128) modulate each; `intensity` is per-effect — flicker depth, chase width, sparkle density.

All six built-in themes become `(EffectMode, color array)` pairs — Green → `FLICKER`, the other five → `BLEND` — rendering identically while going through the new engine.

### Timeout and revert

A custom effect may carry an optional `timeout` in seconds:

- **omitted or `0`** — the effect stays until explicitly changed
- **1 … 28800** — after that many seconds the device reverts to the theme that was active before the effect was applied
- **above 28800 (8 hours)** — clamped to 28800, not rejected

8 hours covers an evening event without a strip being left in strobe indefinitely because someone forgot. Both ends of the range matter: 30 seconds for a quick look, 20 minutes for dinner, 8 hours for a party.

**Clamp rather than reject.** A request for 12 hours is a clear intent to "leave it on for the event", and refusing the whole command over it produces nothing at all. The clamp must be visible though — `STATUS` reports `timeoutRemaining`, so an unexpectedly short value is discoverable rather than silent.

`CLEAR_EFFECT` reverts immediately without waiting for the timeout:

```
lights/kitchen/cmd  →  CLEAR_EFFECT
```

Unlike `OTA_URL` and `RESTART`, this is safe on `lights/all/cmd` — the worst case is the whole installation returning to its normal theme, which is the recovery action anyway.

An explicit theme command (`RAINBOW`, `GREEN`, …) must also cancel an active custom effect rather than leaving it queued to revert later. Reverting to a theme the user has since moved away from would be baffling.

### Surviving a reboot — the part the spec does not settle

`activatedAt = millis()` resets to zero on boot, so a persisted effect would silently restart its timer. For an 8-hour event effect interrupted by a power blip at hour 7, that means another 8 hours.

Neither extreme is right: always reverting on boot loses a long-running event effect to a momentary glitch; always resuming restarts short ones that should have expired during the reboot itself.

Persist an **absolute wall-clock end time** instead of an elapsed offset. NTP is already configured for the OTA scheduler, so on boot:

- clock valid and `now < endTime` → resume the effect with the correct remaining time
- clock valid and `now >= endTime` → revert immediately, the effect expired while powered down
- clock not yet synced → revert; a wrong guess about a timed effect is worse than dropping it

This makes a 30-second effect expire across a reboot and an 8-hour one resume with the right remainder, which is what both cases want.

### Timing must use the rollover-safe helper

Every new renderer and the timeout check must go through `timeReached()`, not a `deadline < now` comparison. Seven of those were removed in [#0008](0008.md) after they froze four strips for days; nine new renderers are nine new chances to reintroduce the pattern. 8 hours is well inside the ~24.8-day window `timeReached()` handles.

The spec's own timeout example already uses the correct elapsed form — worth keeping, and worth checking that `EVERY_N_MILLISECONDS` (a FastLED macro that wraps `millis()` internally) is not substituted for it without thought.

### ArduinoJson will not fit

The spec says to pull in ArduinoJson and check headroom. **Current headroom is 84,000 bytes** and ArduinoJson typically costs 20–30 KB before a single renderer is written. Given [#0009](0009.md) — a release published that no device could install, for exactly this reason — the parse should be hand-rolled. The payload is a fixed shape with at most 8 hex strings, so a parser is far cheaper than a general-purpose one.

If ArduinoJson is used anyway, settle the `min_spiffs` partition question ([#0009](0009.md) notes, [#0004](0004.md) item 6) **first** — that decision needs a USB pass on every device and cannot be discovered late.

### The compatibility promise is currently untestable

The spec guarantees the six built-in themes produce the same visual output through the new engine. Nothing today can verify that; the only available check is looking at a strip. Decide up front whether "identical" means capturing `leds[]` after a fixed number of frames and diffing it against the old renderer, or whether visual inspection is accepted. A promise that cannot be checked is not a guarantee.

### From the spec, to keep as written

- **NVS versioning** — a `SETTINGS_VERSION` byte, with `customEffect` zero-initialized on mismatch rather than trusting whatever bytes occupy the newly-used region after an OTA.
- **`THEME_CUSTOM` guard** — booting with `currentTheme == THEME_CUSTOM` but an uninitialized effect falls back to `THEME_GREEN` rather than rendering an empty color array.
- **Malformed input** — validate `mode` against the enum and `colors` count (1–8), and on any parse failure keep the prior state rather than applying a partial config.
- **`NEXT_THEME` / `PREV_THEME` cycle only the original six**, so `THEME_CUSTOM` is unreachable by cycling.

## Expected behavior

Any color set and effect can be applied over MQTT, optionally for a bounded period after which the strip returns to its previous theme by itself. `CLEAR_EFFECT` returns it immediately. The six built-in themes, the IR remote, and every existing MQTT command behave exactly as before.

## Actual behavior

Only six hardcoded themes exist. There is no way to set arbitrary colors, no effects beyond blend and flicker, and no way to apply a temporary look that reverts on its own.
