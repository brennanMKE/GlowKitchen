# 0020 — The debug build freezes whenever nothing is reading the USB serial port

| | |
|---|---|
| **Status** | resolved |
| **Module** | Firmware / Logging / Tooling |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-28 |
| **Closed** | 2026-08-28 |

## Description

On the `esp32c3-debug` build the whole firmware stops — MQTT, the render loop, the effect timeout, everything — the moment no program on the host is draining the USB serial port. It resumes the instant a reader attaches. The board is not crashed; `loop()` is blocked inside a log write. This silently invalidates any hardware measurement taken without a monitor attached, which is why several results in [#0013](0013.md)/[#0016](0016.md)/[#0017](0017.md) could not be reproduced.

## Long Description

### How it shows up

Measured on the dev board (`84fce68774a4`). The probe publishes `STATUS` over MQTT and times how long the device takes to publish its state back — a referee that needs no serial port, so it cannot be confounded by the thing being measured.

| Condition | Replies | Latency |
|---|---|---|
| Before fix, no serial reader | **0 / 5** | all timed out (20 s) |
| Before fix, `cat` attached | **5 / 5** | 0.12 – 0.15 s |
| After fix, `cat` attached | **4 / 4** | 0.12 – 0.16 s |
| After fix, no serial reader | **4 / 4** | 0.14 – 0.29 s |
| After fix, no serial reader, sustained 10 probes over ~2.5 min | **10 / 10** | 0.12 – 1.26 s |

An earlier symptom from the same cause: a custom effect with a 30-second timeout reverted after **61 seconds**, because the serial reader was detached for the middle ~31 seconds and the device was not running. Re-measured with a reader attached throughout, the same 30-second timeout reverted after **29.991 s**.

### Root cause

`platformio.ini` builds both device environments with `-DARDUINO_USB_CDC_ON_BOOT=1` and `-DARDUINO_USB_MODE=1`, so the console is the C3's native USB Serial/JTAG peripheral (`HWCDC`), not a UART bridge.

`ESP_LOGx` output reaches it one character at a time through `ets_install_putc2(&cdc0_write_char)`. In `framework-arduinoespressif32/cores/esp32/HWCDC.cpp`:

```c
static void ARDUINO_ISR_ATTR cdc0_write_char(char c) {
    if (!HWCDC::isConnected()) {          // non-blocking FIFO-policy path
        flushTXBuffer((const uint8_t*)&c, 1);
        return;
    }
    ...
    xRingbufferSend(tx_ring_buf, (void*)(&c), 1, tx_timeout_ms / portTICK_PERIOD_MS);
}
```

`isConnected()` resolves to `HWCDC::isPlugged()`, which returns `s_usb_serial_jtag_conn_status` — **whether the USB cable is enumerated by the host**, not whether any application has the port open. A plugged-in board with nothing reading therefore looks "connected", so every character waits out the full `tx_timeout_ms` (default **100 ms**) for a drain that never comes. `HWCDC::write()` has the same structure with an equivalent blocking loop.

At `CORE_DEBUG_LEVEL=5` with `-DEFFECT_TRACE` the firmware emits a line per render frame plus verbose framework logging, so the writes arrive far faster than that ceiling permits and `loop()` never gets far enough to service MQTT or `loopEffectTimeout()`. The result is a total stall, not merely dropped log lines.

### What is *not* the cause

- **Not DTR, and not `cat` specifically.** The first hypothesis was that `cat` leaves DTR asserted on exit while pyserial lowers it, so the device wrongly believes a host is still listening. That is wrong twice over: `isPlugged()` never consults DTR, and the experiment that appeared to support it was confounded (see the next section). Any absent reader stalls the board, including never having attached one since boot.
- **Not the release build.** `[env:esp32c3]` builds at `CORE_DEBUG_LEVEL=1` with no `EFFECT_TRACE`, so it emits little enough that the ring buffer drains between writes. The five deployed strips run the release build and are unaffected — which is why this reads as "only the dev board misbehaves".

### Second finding: attaching a pyserial monitor reboots the board

While diagnosing the above, the first version of `scripts/monitor_serial.py` used pyserial. pyserial drives DTR/RTS on open, and the C3's USB Serial/JTAG peripheral treats those transitions as esptool's auto-reset request. Every attach rebooted the chip — `rst:0x15 (USB_UART_CHIP_RESET)` and a fresh `uptime: 1637` in the log where a running board should have shown minutes.

This is its own hazard: it wipes the in-RAM effect state and the uptime under test, and it made "monitor attached" look like it fixed the stall when it had really just restarted the board into a fresh working window. Holding DTR and RTS low across `open()` is **not** sufficient — pyserial still resets it.

`cat` does not reset the board, because it opens the tty as a plain file and never touches a control line. `scripts/monitor_serial.py` now does the same (`os.open` + `stty` for baud), and adds host timestamps and immediate flushing on top. Verified: 0 boot banners across an attach, uptime continuous at 51,637 ms.

### Why "it works in VS Code" is consistent with all of this

PlatformIO's monitor holds the port open and drains it continuously, which is exactly the working condition. Disconnecting it does not appear to break anything because nothing is measuring the board at that moment — the stall is invisible until something asks the device to respond.

## Expected behavior

The firmware keeps running whether or not anything is reading the serial port. Log output may be dropped when nobody is listening; `loop()` must not block on it.

## Actual behavior

`loop()` blocked inside the USB CDC write path for as long as no host drained the FIFO, halting MQTT handling, rendering and the effect-timeout check.

## Fix

One line in `setup()`, immediately after `Serial.begin(115200)` in `src/main.cpp`:

```c
Serial.setTxTimeoutMs(0);
```

`tx_timeout_ms` is the same static the blocking paths above spin on. At zero, a character that cannot be queued is dropped instead of waited on, so logging becomes lossy exactly when nobody is reading — the right trade in both directions, since nobody listening means nobody misses the output.

Applied unconditionally rather than only under the debug env: the release build is only *accidentally* safe (it happens to log little enough to stay under the ceiling), and a burst of `ESP_LOGE` on a release build could hit the same wall on a USB-powered strip with no host attached.

`scripts/monitor_serial.py` (new) is the companion tooling fix — a persistent, non-resetting, timestamping logger. Use it instead of `cat`; use `cat` in preference to anything pyserial-based.

## Verification

```
pio run -e esp32c3            # SUCCESS -- firmware.bin 1,236,032 bytes (74,688 spare in the OTA slot)
pio run -e esp32c3-debug      # SUCCESS, flashed to the dev board over USB
pio test -e native            # 87 test cases: 87 succeeded
```

Behavioral proof is the table in **How it shows up**: 0/5 replies before the fix with no reader attached, against 10/10 after it across a sustained 2.5-minute run with nothing attached to the serial port at any point. The `cat`-attached rows are the control — they rule out the board simply having been rebooted into a working state, since `cat` does not reset it.

Also re-confirmed end to end through the new monitor with the fix in place: `demo_effect.sh 84fce68774a4 dolly 20` logged `SET_EFFECT applied: mode=SPARKLE colors=3 speed=128 intensity=255 timeoutSec=20`, and the board stayed responsive (3/3) after the monitor detached.

**Not verified:** whether `setTxTimeoutMs(0)` costs log lines while a monitor *is* attached. A small non-zero value (~5 ms) would bound the stall while preserving more output; nothing measured that trade here, and the log looked complete by eye during the demo run above.
