# 0008 — Deadline-style millis() timers strand for 49.7 days if the loop blocks across the rollover

| | |
|---|---|
| **Status** | in-progress |
| **Branch** | issue/0008 |
| **Module** | LED / Timing / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-15 |

## Description

Every periodic timer in the firmware stores a future deadline and tests it with `if (deadline < now)`. That pattern survives the `millis()` rollover **only if the main loop samples the clock during the interval straddling the wrap**. If the loop is blocked at that instant, the deadline is left ~4.29 billion ms in the future and the timer does not fire again for another 49.7 days. This is the probable root cause of [#0003](0003.md): `slowBlend()` has the shortest interval in the firmware and so is the likeliest timer to strand.

## Long Description

### The pattern

```c
unsigned long blendTimeout = 0;
unsigned long blendInterval = 100;

void slowBlend() {
    unsigned long now = millis();
    if (blendTimeout < now) {
        ...render...
        blendTimeout = now + blendInterval;
    }
}
```

### Why it normally survives the wrap

Let `T = 2^32`. As `now` approaches `T`, `blendTimeout = now + 100` wraps to a small value. `blendTimeout < now` then evaluates true on the next iteration, so the branch runs every loop for roughly 100 ms until `now` itself wraps, after which both are small and normal throttling resumes. Left alone, it recovers by itself. This is why the bug is not obvious from reading the code.

### Why it strands

Recovery depends on the loop sampling `millis()` at least once inside that ~100 ms window. If a single iteration spans the rollover, `now` jumps from just under `T` to a small value while `blendTimeout` still holds a near-`T` deadline. `blendTimeout < now` is then **false for another full rollover period**.

The firmware has several ways to block far longer than 100 ms:

- `ensureWifi()` — a **30-second** blocking `while (WiFi.status() != WL_CONNECTED && millis() - start < 30000) { delay(100); }` whenever WiFi drops.
- `checkForOtaUpdate()` — an HTTPS GET to the GitHub API plus a ~1 MB download; seconds to tens of seconds. Runs ~15 s after every boot and nightly.
- `mqtt.connect()` — blocks until it succeeds or times out.

Any of these overlapping the rollover instant strands the timer.

### Why this matches the observed failure exactly

| observation | explained by |
|---|---|
| `slowBlend()` froze while everything else worked | its 100 ms interval is the narrowest window in the firmware, so it is the most likely to strand. `hueTimeout` is 2 s, the heartbeats 10 s |
| theme switches still repainted the strip | `fill_solid()` runs in the MQTT callback, gated by no timer |
| MQTT stayed responsive | `mqtt.loop()` runs unconditionally while connected; only reconnects are timer-gated |
| only 4 of 6 devices affected | it is a race against a ~100 ms window — devices that sampled cleanly through the wrap self-corrected |
| power-cycled devices are fine | `blendTimeout` resets to 0 |
| it appeared around 2026-08-15 | 0.0.3 shipped ~2026-06-25; 49.71 days later lands on 2026-08-13/14 |

`workbench` and `recycling` had both been power-cycled and both render correctly. `recycling` looks unusual on Rainbow for an unrelated, already-understood reason — its `ledsPerColor` of 20 over 58 LEDs shows only ~36% of the color wheel (see [#0004](0004.md) item 1).

### The fix

Store the last-fired time and compare **elapsed** time, which is immune to both the rollover and to arbitrarily long blocking:

```c
unsigned long lastBlend = 0;

void slowBlend() {
    unsigned long now = millis();
    if (now - lastBlend >= blendInterval) {
        lastBlend = now;
        ...render...
    }
}
```

Unsigned subtraction is well-defined on overflow, so `now - lastBlend` is the true elapsed interval across the wrap. A blocked loop causes one late frame, never a permanent stall.

### Every timer that needs converting

Deadline-style, **unsafe** — all in `src/main.cpp`:

| variable | interval | site |
|---|---|---|
| `blendTimeout` | 100 ms | `slowBlend()` — the one that broke |
| `rotateTimeout` | 500 ms | `slowBlend()`, function-static |
| `hueTimeout` | 2 s | `flickerLEDs()` |
| `timeouts[i]` | 500–750 ms | `flickerLEDs()`, per-LED array |
| `logTimeout` | 10 s | `loopLED()` |
| `irLogTimeout` | 10 s | `loopIR()` |
| `mqttRetryAt` | 5 s | `ensureMqtt()` |

Already elapsed-style and **safe**, left alone:

- `lastButtonTime` in `isButtonDebounced()`
- `lastBlackUpdate` in `loopLED()`
- `wifiConnectedAt` in `loopOta()`
- the `millis() - start` guard inside `ensureWifi()`

### Making it testable

A bug with a 49.7-day feedback loop cannot be verified by waiting. Route all timing through one helper so the clock can be shifted to just before the rollover on demand:

```c
// Offset lets a dev build sit near the 2^32 ms rollover so the wrap can be
// exercised in minutes instead of 49.7 days. Zero in normal builds.
uint32_t clockOffsetMs = 0;
inline uint32_t nowMs() { return millis() + clockOffsetMs; }
```

Set it over MQTT (`SET_CLOCK_OFFSET:4294900000`) to put the device ~67 seconds from the wrap, then watch whether the strip keeps animating through it. Combining that with a deliberate block — force a WiFi drop, or trigger an OTA check timed to straddle the wrap — reproduces the stranding case directly and proves the fix rather than assuming it.

This also makes the failure reproducible on the bench for any future timing change.

## Expected behavior

Periodic rendering continues across the `millis()` rollover regardless of how long the main loop is blocked at that moment.

## Actual behavior

A loop iteration spanning the rollover leaves the render timer's deadline ~49.7 days in the future, freezing `slowBlend()` on whatever frame was last shown until the device is power-cycled.

## Notes

- **The reboot from the `v0.0.4` OTA clears the stuck state on every device**, so the symptom disappears tonight and cannot be observed again until the next rollover. Fix from the analysis rather than waiting to reproduce.
- This is a strong hypothesis with an exact mechanism and a matching timeline, but it is **not yet proven on hardware**. The clock-offset harness above is how to prove it. Worth doing before closing [#0003](0003.md).
- Consider also making `ensureWifi()` non-blocking. A 30-second blocking wait in the main loop is the largest single contributor to the stranding window, and it freezes the LEDs outright whenever WiFi drops.
- Rendering should arguably not be gated on a timer that can fail this way at all — a frame counter or an unconditional render with an elapsed-time throttle would be more robust.

## Root cause

Every periodic render timer stored a future deadline (`blendTimeout = now + interval`) and tested it with `deadline < now`. That comparison is correct only if the loop samples `millis()` at least once during the interval that straddles the `2^32` rollover; if a single loop iteration is blocked across that instant (`ensureWifi()`'s 30s wait, an OTA check, `mqtt.connect()`), `now` jumps from just under `2^32` to a small post-wrap value while the deadline is still holding a large, un-wrapped, just-under-`2^32` number. The naive comparison then reads as "deadline is still ~4.29 billion ms in the future" and does not fire again until `now` catches back up to it — another ~49.7 days. See `## Long Description` above for the full mechanism and the evidence match against the four frozen strips.

## Fix

Landed in `bc7e664`. All seven deadline tests now go through one helper rather than being rewritten individually:

```c
static inline bool timeReached(unsigned long now, unsigned long deadline) {
    return (long)(now - deadline) >= 0;
}
```

Chosen over the `now - last >= interval` form because `timeouts[]` carries a *random per-LED* interval, which the elapsed form would have required storing separately (an extra 2 KB of RAM) — and because one idiom applied uniformly is easier to keep correct than two. Unsigned subtraction is well-defined on overflow, so reading the difference as signed answers the question correctly for any deadline within ~24.8 days of now. A blocked loop now costs one late frame instead of a permanent stall.

Converted: `blendTimeout`, `rotateTimeout`, `hueTimeout`, `timeouts[i]`, `logTimeout`, `irLogTimeout`, `mqttRetryAt`. The four already-safe subtraction sites (`lastButtonTime`, `lastBlackUpdate`, `wifiConnectedAt`, the `ensureWifi()` guard) were left alone.

### Type-width fix, native tests, and the clock-offset harness — landed in `900b60c`

`timeReached()` moved out of `main.cpp` into `src/time_utils.h`, changing its signature from `unsigned long`/`long` to fixed-width `uint32_t`/`int32_t`:

```c
// was — correct on ESP32-C3 only by accident, because unsigned long/long
// happen to be 32 bits there
static inline bool timeReached(unsigned long now, unsigned long deadline) {
    return (long)(now - deadline) >= 0;
}

// now — src/time_utils.h, included by both main.cpp and the native test suite
static inline bool timeReached(uint32_t now, uint32_t deadline) {
    return (int32_t)(now - deadline) >= 0;
}
```

The signed cast is only meaningful when the signed and unsigned types are the *same width*. `unsigned long` is 64 bits on a PlatformIO `native` build (macOS/Linux), so a test built against the old signature would never see the `2^32` wrap at all — the exact bug this issue is about could not even be expressed. Fixed-width types make the wrap point identical between the device build and the native test build. No behavior change on device: `unsigned long`/`long` are already 32 bits on xtensa/riscv32, so every call site (all of which pass `unsigned long`/`uint32_t` locals) converts implicitly with no truncation and no new compiler warnings.

The helper now lives in its own header specifically so the native test suite links against the *real* implementation rather than a hand-maintained copy that could drift from what ships.

**Native test suite** (`test/test_rollover/test_rollover.cpp`, `[env:native]` in `platformio.ini`): six Unity tests exercising the real `timeReached()` — the exact blocked-wrap failure from this issue; a check that the naive `deadline < now` form gets that same case wrong (documenting the bug the tests prevent); the unblocked self-healing case; a basic near-future negative case; the ~24.8-day (`2^31` ms) validity boundary where the signed-cast trick stops giving a meaningful answer; and a dedicated type-width regression guard (`static_assert(sizeof(uint32_t) == 4)` plus an explicit 64-bit recomputation of the blocked-wrap case showing it disagrees with the 32-bit answer). Manually confirmed the suite actually catches the regression it's named for: temporarily reverting `time_utils.h` to `unsigned long`/`long` and rerunning `pio test -e native` fails 4 of the 6 tests.

**Clock-offset harness** (`nowMs()` / `clockOffsetMs` / MQTT `SET_CLOCK_OFFSET:<ms>`), matching the design sketched in `## Long Description` above: lets a debug build sit within seconds of the `2^32` rollover on demand instead of waiting 49.7 days. Guarded behind `-DENABLE_CLOCK_OFFSET`, set only by `[env:esp32c3-debug]` and never by the release env `[env:esp32c3]` — in a release build `nowMs()` compiles to a bare `millis()` call and the `SET_CLOCK_OFFSET` handler is absent from the binary entirely. `slowBlend()`'s `blendTimeout` and `rotateTimeout` — the two timers that actually froze — were routed through `nowMs()` so the harness can move them; the other five converted timers (`hueTimeout`, `timeouts[i]`, `logTimeout`, `irLogTimeout`, `mqttRetryAt`) were deliberately left reading `millis()` directly, to keep the diff to the timers the harness needs to reach. See `## Gotchas`.

### Round 2 — two blocking defects in the harness itself, found on review

The first review pass confirmed the type-width fix and the six-test native suite, but flagged the clock-offset harness — the only mechanism for the on-device verification this issue is blocked on — as broken in two ways. Both are fixed here, in `src/main.cpp`'s `SET_CLOCK_OFFSET` handler:

1. **Off-by-one in the parse offset.** `"SET_CLOCK_OFFSET:"` is 17 characters; the handler called `msg.substring(18)`, eating the first digit of the value. The documented bench command `SET_CLOCK_OFFSET:4294900000` parsed as `294900000` — ~46.3 days from the wrap instead of ~67 seconds — with no error and no visible symptom. Fixed to `substring(17)`. Covered by `test_set_clock_offset_prefix_length_matches_literal` and `test_set_clock_offset_payload_parses_at_correct_offset` in `test/test_rollover/test_rollover.cpp`, which pin the prefix length to a literal `strlen()` check rather than to whatever offset the handler happens to use, so the two can't silently drift apart again.

2. **Setting the offset stranded the very timers it was meant to move.** `blendTimeout` and `rotateTimeout` hold deadlines computed against the OLD clock. Jumping `clockOffsetMs` by `4294900000` is, in the signed arithmetic `timeReached()` uses, a **67-second jump backwards** relative to those stale deadlines — so `slowBlend()` freezes for ~67s immediately after the command, and the `2^32` wrap of `nowMs()` (~37s after the command) happens *inside* that frozen window. An operator following the old documented steps would see the strip freeze right after issuing the command — the exact symptom this issue is about — and would reasonably conclude the fix had failed, while the wrap itself passed unobserved. Fixed by re-basing both deadlines onto the new clock at the moment the offset changes: `blendTimeout = nowMs(); rotateTimeout = nowMs();`. `rotateTimeout` was a function-static inside `slowBlend()` and therefore unreachable from the MQTT handler; it is now a file-scope variable (same lifetime and initial value as before — this is a visibility change only, not a behavior change) declared next to `blendTimeout`. Covered by `test_offset_jump_without_rebasing_strands_the_timer` (demonstrates the strand) and `test_offset_jump_with_rebasing_does_not_strand_the_timer` (demonstrates the fix) in the same test file.

Also in this pass: the handler now logs the raw payload alongside the parsed value, and rejects (with a warning, not silently) a non-numeric payload instead of letting `strtoul()` map it to `0` and silently resetting the offset with no other sign anything went wrong. `clockOffsetMs` is now `static`, matching `nowMs()`. `[env:esp32c3]`/`[env:esp32c3-debug]` gained `test_ignore = *` so a bare `pio test` (no `-e`) no longer attempts to build `test/test_rollover` against them and fail on an unrelated linker error (`undefined reference to 'setup()'`) — confirmed both ways: reproduced the failure before this change, confirmed no build failure after. See the corrected note in `## Verification` below: PlatformIO does not actually print `SKIPPED` lines for `test_ignore`'d envs when no `-e` is given — it exits 0 having silently run zero test cases, which is its own (mild) footgun.

### Round 3 — the substring guard didn't guard, and the bench procedure could silently pass having tested nothing

The second review pass confirmed round 2's two fixes as genuinely correct (verified by execution and independent arithmetic — release size unchanged, all 10 native tests really execute). It found two new defects, both the same class as round 1 and round 2's: something that claimed to guarantee correctness without actually doing so.

1. **The substring guard didn't guard, and both `src/main.cpp` and this file claimed it did.** The reviewer reintroduced the real `substring(18)` bug and all 10 tests still passed, because `test_set_clock_offset_prefix_length_matches_literal` asserts `strlen("SET_CLOCK_OFFSET:") == 17` against a *second copy* of the literal declared in the test file — a tautology that only fails if someone edits the test, not if `main.cpp`'s handler drifts from it. `src/main.cpp` (the comment above the handler) and this file (`## Gotchas`, below) both asserted the test "pins" the count "so this can't drift again unnoticed." That was false, and shipping a false correctness claim next to real code is worse than shipping no claim at all. Fixed by making the claim true instead of removing it: `SET_CLOCK_OFFSET_PREFIX` now lives once, in `src/time_utils.h` (shared by `main.cpp` and the native test suite, same rationale as `timeReached()`), and the handler derives its `substring()` offset from it directly — `msg.substring(sizeof(SET_CLOCK_OFFSET_PREFIX) - 1)` — rather than a hand-typed number that could silently drift from the string again. The offset is now structurally tied to the prefix; there is no longer a second number to keep in sync. `test_set_clock_offset_payload_parses_at_correct_offset` now documents that this is what it's pinning (the arithmetic, not the handler, since `onMqttMessage()` itself is Arduino-coupled and not native-test-linkable) rather than claiming coverage it doesn't have.

2. **The bench procedure silently produces a false pass if uptime is over ~67s when the command is published.** `nowMs() = (millis() + 4294900000) mod 2^32` wraps once `millis() >= 67296`. The `## Verification` write-up stated the ~67s runway unconditionally, but it only holds if the command is published within seconds of boot — realistically a coin flip once WiFi association, MQTT connect, and an operator switching terminals are accounted for, and there is no `RESTART` command to reset uptime on demand. Past that window, the same documented command parks `nowMs()` **~49.7 days** from the wrap instead of ~67s: the wrap is jumped over, never crossed, and every bench observable (strip animates, log line looks sane, parsed offset matches what was sent) still looks like a pass. Fixed three ways: (a) the `SET_CLOCK_OFFSET` handler now logs the actual distance to the wrap (`0u - nowMs()`, computed inside the existing `ENABLE_CLOCK_OFFSET` block — zero release impact) alongside the existing payload/offset log line, printing ~62000 in the good case and ~4294900000 in the bad one; (b) step 5 of the hardware verification procedure below now tells the operator to confirm that logged runway is small (tens of seconds) before trusting anything else, and to power-cycle and re-publish promptly if it isn't; (c) the procedure now states the rule plainly — publish within ~30s of boot, or compute `offset = 4294967296 - millis() - 60000` from the logged uptime if more time has passed. This also unblocks step 4 (pulling WiFi right before the offset would cross): the operator now has a way to know when the wrap instant actually is.

## Verification

What is *not* yet verified is the fix itself: the failure cannot recur until the next rollover, so the clock-offset harness described above is still the only way to prove `timeReached()` actually holds across the wrap. Do not close this on the power-cycle evidence alone — that only confirms the diagnosis.

## Gotchas

- **Only the render timers are shiftable — and the other five animating normally during a shifted-clock run is NOT evidence they are rollover-safe.** `slowBlend()`'s `blendTimeout`/`rotateTimeout` go through `nowMs()`; `flickerLEDs()`'s `hueTimeout`/`timeouts[i]`, `loopLED()`'s `logTimeout`, `loopIR()`'s `irLogTimeout`, and `ensureMqtt()`'s `mqttRetryAt` still read `millis()` directly. `SET_CLOCK_OFFSET` does not move those five: during a bench session with the clock shifted, they are still running on the real, un-shifted `millis()`, nowhere near their own rollover, so of course they keep animating normally — that continued animation says nothing about whether they would survive a *real* wrap. This matters concretely for `flickerLEDs()`'s `hueTimeout`/`timeouts[i]`, which drive the visible flicker an operator running this bench procedure will be staring at the whole time: seeing it flicker normally during a `SET_CLOCK_OFFSET` session is not a passing result for those five timers, it is simply them not being under test. They were deliberately left unrouted to keep the diff to the timers that actually froze (`blendTimeout`/`rotateTimeout`); their rollover safety rests entirely on `timeReached()` itself and the native test suite, not on anything observable in this harness. Routing the rest through `nowMs()` is a small, mechanical follow-up (swap `millis()` for `nowMs()` at five more call sites) if a future bench session needs to watch them directly.
- **`SET_CLOCK_OFFSET` parses with `strtoul()`, not `String::toInt()`.** The offset values this harness needs (e.g. `4294900000`, to land ~67s from the wrap) exceed `INT32_MAX`, and `String::toInt()` returns a signed `long` that would silently misparse or saturate. `strtoul()` on the trimmed payload avoids that. As of round 2, a non-numeric payload is rejected with a logged warning rather than silently parsed to `0` (an unnoticed offset reset); the raw payload is also logged alongside the parsed value on success, so a misparse of a technically-numeric-but-wrong payload is still visible even though it isn't rejected — bench-tool leniency on range, not on obvious garbage.
- **The MQTT handler's `substring()` offset used to have to match the literal prefix length by hand, and that was proven not to work.** `"SET_CLOCK_OFFSET:"` is 17 characters; round 1 used `substring(18)`, which ate the first digit of every value with no error, no log, and no visible on-bench symptom other than the device sitting ~46 days from the wrap instead of ~67 seconds. Round 2 fixed the number but claimed a native test "pinned" it against regression — false: reintroducing `substring(18)` on round-3 review still passed all 10 tests, because the test compared the handler's hard-coded number against a *second, independently hard-coded* copy of the same literal in the test file, not against what the handler actually used. Round 3 fixed this structurally instead of re-testing it: `SET_CLOCK_OFFSET_PREFIX` now lives once, in `src/time_utils.h`, and the handler computes its `substring()` offset as `sizeof(SET_CLOCK_OFFSET_PREFIX) - 1` rather than typing a number at all. There is no longer a second value that can drift from the first — if this prefix string is ever edited, the offset moves with it automatically.
- **Changing `clockOffsetMs` must re-base every deadline that reads through `nowMs()`, or the harness strands the exact timers it exists to move.** `blendTimeout`/`rotateTimeout` are computed against whatever clock was current when they were last set; jumping `clockOffsetMs` by ~4.2949e9ms without resetting them is, in `timeReached()`'s signed arithmetic, a ~67-second jump *backwards* relative to those stale deadlines, freezing `slowBlend()` for that whole window and hiding the wrap (which lands inside it). The `SET_CLOCK_OFFSET` handler now does `blendTimeout = nowMs(); rotateTimeout = nowMs();` right after updating `clockOffsetMs`. Any future timer routed through `nowMs()` (see the first bullet above) needs the same re-basing added to this handler, or it will strand exactly the same way.
- **`clockOffsetMs` is not part of `publishState()`'s JSON schema.** It's bench tooling, not device state a dashboard needs to display, and adding it would mean threading `#ifdef ENABLE_CLOCK_OFFSET` into a function that also runs in release builds. `ESP_LOGI` on `SET_CLOCK_OFFSET` (now including the raw payload) is the only visibility into the current offset (besides re-deriving it from `millis()` vs. observed behavior).
- **The bench procedure's documented `SET_CLOCK_OFFSET:4294900000` only lands ~67s from the wrap if uptime is under ~67s when it's published — otherwise it silently produces a false pass.** `nowMs() = (millis() + 4294900000) mod 2^32` wraps once `millis() >= 67296`. Publish later than that (a coin flip in practice, once WiFi/MQTT connect time and operator lag are accounted for, and there is no `RESTART` command to reset uptime) and the same command instead parks `nowMs()` ~49.7 days from the wrap. Nothing on the bench looks different either way — the strip animates, the log line reads sensibly, the parsed offset matches what was sent — so an operator can complete every step of the old procedure and have verified nothing. The `SET_CLOCK_OFFSET` handler's log line now includes the actual distance to the wrap (`0u - nowMs()`); confirm it reads in the tens-of-seconds before trusting anything else in the procedure. See the corrected hardware verification steps below.
- **The `~24.8-day` (`2^31` ms) boundary is inherent to the technique, not a residual bug.** `test_boundary_near_24_8_day_limit` documents rather than "fixes" it: past that distance from `now`, the signed-cast interpretation is ambiguous between "far future" and "far past" and can flip. No interval in this firmware is within orders of magnitude of that limit (seconds, not weeks), so this is a documented property, not follow-up work.
