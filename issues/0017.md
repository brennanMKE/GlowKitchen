# 0017 — Effect timeout and auto-revert, with a wall-clock end time that survives reboot

| | |
|---|---|

## Description

Phase 4 of [#0013](0013.md). Act on the `timeout` that [#0016](0016.md) parses: after it elapses, the strip reverts to the theme that was active before the effect was applied. Persist an **absolute wall-clock end time** so a reboot neither restarts a long effect's timer nor resurrects one that expired while powered down. Extend `STATUS` with `timeoutRemaining`.

### 0. Scope, in one line

### 1. The two halves, and the cut line — read this first

There is an event coming and this must demo. The work splits cleanly:

| Half | Steps | Est. | Demo-critical? |
|---|---|---|---|
| **A — live timeout + revert + STATUS** | 1–5 | ~2–2.5 h | **Yes.** This *is* the demo: `SET_EFFECT` with `timeout:30`, watch the strip return to its prior theme. |
| **B — reboot semantics (wall-clock end time)** | 6–9 | ~4.5–6 h | No. Field robustness. |

**Half B is roughly 2–2.5× half A**, and the honest reason is in §6.1: the naive
reading of the ticket's decision table ("on boot: clock valid? …") **cannot be
implemented at boot at all**, because NTP is not configured until `loopOta()` runs
after WiFi joins. It is a small state machine in the main loop with a grace window,
not an `if`/`else` in `loadAllPreferences()`. Budget accordingly.

**The cut line is between step 5 and step 6.** Half A is independently
verifiable, independently shippable, and leaves the tree in a coherent state.

**What is lost by cutting B** — state this verbatim in `## Fix` if you cut it:

- A mid-effect power blip restarts the timer from full duration. An 8-hour effect
  interrupted at hour 7 runs 8 more hours.
- A short effect that expired while the device was powered down comes back running.
- `STATUS timeoutRemaining` after a reboot reports the full duration, not the true
  remainder.
- Nothing crashes and nothing is stuck forever — the effect still expires, just late.

**If you cut B, you must still write one explicit line (§9, Cut-A).** Doing nothing
does *not* give you "revert on boot"; it silently gives you "resume with a fresh full
timer", which is precisely the behavior [#0013](0013.md) § "Surviving a reboot"
rejects. `applyLoadedCustomEffect()` forces `activatedAt = 0` on load, so
`timeReached(nowMs(), 0 + timeoutMs)` is false for another full `timeoutMs`
after boot. **Silence here is a wrong answer, not a deferred one.**

### 2. The live timeout check (demo-critical)

#### 2.1 The predicate — pure, native-testable, rollover-safe

New header **`src/effect_timeout.h`**. Same header-only rationale as `effects.h` /
`effect_parse.h` (`[env:native]` does not build project sources; `-I src` is already
there). Includes `effects.h` and `time_utils.h`; no `Arduino.h`, no `String`, no
FastLED calls. Restate the include-order contract at the top: a test TU must include
`fastled_shim.h` first.

```cpp
// True when an active custom effect's timeout has elapsed.
// `isCustom` is passed in rather than read off the `currentTheme` global so this
// stays a pure function the native env can call without linking main.cpp.
inline bool effectTimeoutExpired(bool isCustom, uint32_t timeoutMs,
                                 uint32_t activatedAt, uint32_t now) {
    if (!isCustom || timeoutMs == 0) return false;
    return timeReached(now, activatedAt + timeoutMs);
}
```

**Why this shape and no other.** The spec writes
`millis() - activatedAt >= timeoutMs`. That elapsed form is already rollover-safe,
and the ticket says keep it — so keep it, but route it through the helper.
`timeReached(now, activatedAt + timeoutMs)` is *arithmetically identical* to the
elapsed form for any `timeoutMs < 2^31` (both reduce to the same unsigned
subtraction read as signed), and `timeoutMs` is capped at 28,800,000 by #0016, four
orders of magnitude inside that bound. The gain is that there is now exactly **one**
deadline idiom in this codebase, which is the whole point of [#0008](0008.md)'s fix.
The unsigned `activatedAt + timeoutMs` addition wrapping is not a bug — it is the
mechanism.

**Forbidden, and say so in a comment:** `deadline < now`;
`EVERY_N_MILLISECONDS` (a FastLED macro wrapping `millis()` internally — it would
also silently opt out of the `nowMs()` harness); and any `unsigned long` in this
path (64-bit natively, 32-bit on the C3 — the exact trap `time_utils.h` documents at
length).

#### 2.2 Where it runs in the loop

A new `loopEffectTimeout()`, called from `loop()` **before `loopLED()`**:

```cpp
void loop() {
    ensureWifi();
    ensureMqtt();

    loopEffectTimeout();   // <-- new
    loopLED();
    loopIR();
    loopOta();
}
```

Two placement decisions, both load-bearing:

- **Before `loopLED()`**, so a revert takes visual effect on the same iteration
  rather than one frame later.
- **In `loop()`, not inside `loopLED()`.** `loopLED()` returns early when
  `!ledsEnabled`. [#0016](0016.md) § 6.3 deliberately makes `OFF`/`TOGGLE` *not*
  cancel a timed effect, so a timed effect must still be able to expire while the
  strip is off — otherwise turning the lights off parks a live timeout indefinitely
  and it fires whenever they come back on. Putting the check inside `loopLED()`
  would reintroduce exactly that.

It must also run with WiFi down and MQTT disconnected. `loop()` gives that for free;
`loopOta()` (which returns early on `WiFi.status() != WL_CONNECTED`) would not — do
not put it there.

```cpp
void loopEffectTimeout() {
    // Half B's resume resolution goes here first -- see section 6.3.

    if (!effectTimeoutExpired(currentTheme == THEME_CUSTOM,
                              customEffect.timeoutMs,
                              customEffect.activatedAt, nowMs())) return;
    ESP_LOGI(TAG, "Custom effect timed out after %lu s, reverting to %s",
             (unsigned long)(customEffect.timeoutMs / 1000),
             THEME_NAMES[customEffect.revertTheme]);
    revertFromCustomEffect();
}
```

`nowMs()`, never `millis()`. See §5.

#### 2.3 The revert path — one function, shared with `CLEAR_EFFECT`

[#0016](0016.md) § 6.2 writes the revert inline inside the `CLEAR_EFFECT` handler.
**Factor it out into `revertFromCustomEffect()` and have `CLEAR_EFFECT` call it**,
so the timed revert and the manual revert are the same code by construction rather
than by two authors agreeing. If they drift, one of them stops clearing the NVS end
time and a ghost effect comes back after the next reboot.

```cpp
void revertFromCustomEffect() {
    if (currentTheme != THEME_CUSTOM) return;          // idempotent
    HueTheme t = customEffect.revertTheme;
    if (t >= CYCLEABLE_THEME_COUNT) t = THEME_GREEN;   // never revert into THEME_CUSTOM
    currentTheme = t;
    hueIndex = 0;
    customEffect.timeoutMs  = 0;
    customEffect.activatedAt = 0;
    effectEndEpoch = 0;                                // half B; see section 6.2
    effectResumePending = false;                       // half B
    saveThemeToPreferences();
    saveCustomEffectToPreferences();                   // also writes fx_end = 0
    // Force immediate visual update, mirroring the theme-string handler.
    const PaletteColor* pal = getCurrentColorArray();
    fill_solid(leds, numLeds, CHSV(pal[hueIndex].h, pal[hueIndex].s, pal[hueIndex].v));
    FastLED.show();
    publishState();
}
```

`hueIndex = 0` before reading the palette matters — the custom effect may have had 1
color and the revert target 8, or vice versa; `renderFlicker()` indexes
`colors[hueIndex]` unguarded.

The `fill_solid` line is written against #0015's widened `PaletteColor` accessors.
**Check the actual signature of `getCurrentColorArray()` as #0015 leaves it** and
match whatever the theme-string handler at the `themeIdentified` block does — copy
that, do not invent a parallel form.

#### 2.4 The revert target

[#0016](0016.md) § 6.1 already persists it: `customEffect.revertTheme`, captured from
`currentTheme` at `SET_EFFECT` time, with the `prevRevert` ternary so back-to-back
`SET_EFFECT`s do not make the second one revert into the first. It is inside
`CustomEffectConfig`, so it is inside the NVS blob, so a reboot-resumed effect
reverts to the right theme. **Confirmed — use it, add nothing.**
`customEffectIsValid()` already rejects a stored `revertTheme == THEME_CUSTOM`
(the infinite self-revert), and `revertFromCustomEffect()` re-checks at use. Both
guards are cheap; keep both.

### 3. Cancellation — the audit, done against the code

The ticket asks for confirmation, so here it is done exhaustively rather than

| Site | What it is | Cancel needed? |
|---|---|---|

Plus the two [#0016](0016.md) adds: the `SET_EFFECT` handler (sets `THEME_CUSTOM`,
and overwrites `timeoutMs`/`activatedAt` wholesale — self-cancelling by
construction) and `CLEAR_EFFECT` (now `revertFromCustomEffect()`).

**#0016's three cancel sites are complete — there is no fourth.** The IR remote
reaches `switchToNextTheme()`/`switchToPreviousTheme()`, which is exactly why #0016

**What #0017 changes about them:** `cancelCustomEffect()` as #0016 writes it zeroes
`timeoutMs` and `activatedAt` and saves. Half B adds a third field —
`effectEndEpoch` — and it **must be zeroed in the same helper**, or an explicit
theme command leaves a stale wall-clock end time in NVS that resurrects a revert on
the next boot. One line, in one place, and it is the single easiest thing in this
ticket to miss:

```cpp
void cancelCustomEffect() {
    if (customEffect.timeoutMs == 0 && customEffect.activatedAt == 0
        && effectEndEpoch == 0 && !effectResumePending) return;
    customEffect.timeoutMs  = 0;
    customEffect.activatedAt = 0;
    effectEndEpoch      = 0;      // <-- issue #0017
    effectResumePending = false;  // <-- issue #0017
    saveCustomEffectToPreferences();
}
```

Note the early-return guard grew two terms. If you leave it as #0016 wrote it, a
device sitting in the "resume pending" state with `timeoutMs == 0` returns early and
never clears `fx_end`. **Widen the guard.**

If you cut half B, `effectEndEpoch`/`effectResumePending` do not exist and
`cancelCustomEffect()` is left exactly as #0016 wrote it.

`OFF` / `TOGGLE` still do **not** cancel — #0016 § 6.3 settles that and §2.2 above
is what makes it safe.

### 4. `STATUS` — `timeoutRemaining` (demo-critical, cheap)

#### 4.1 The arithmetic — pure, native-testable

In `src/effect_timeout.h`:

```cpp
// Seconds remaining on an active custom effect's timeout.
//   -1  -> no timeout ("runs until changed")
//   0.. -> whole seconds remaining, rounded UP
// Rollover-safe: the elapsed interval is an unsigned subtraction.
inline int32_t effectTimeoutRemainingSeconds(uint32_t timeoutMs,
                                             uint32_t activatedAt, uint32_t now) {
    if (timeoutMs == 0) return -1;
    uint32_t elapsed = now - activatedAt;              // wraps correctly
    if (elapsed >= timeoutMs) return 0;
    return (int32_t)((timeoutMs - elapsed + 999) / 1000);
}
```

Rounding **up**, deliberately: a `timeout:1800` effect must report `1800` the instant
it is set, not `1799`. Floor would make every `STATUS` immediately after `SET_EFFECT`
look like the clamp had silently shaved a second off, which is the exact confusion
`timeoutRemaining` exists to prevent.

**Computed from the `millis()` clock, not the wall clock**, even once half B lands.
The wall clock may be unsynced while an effect is running perfectly well (a
session-started effect on a device that never joined WiFi). `timeoutRemaining` must
answer "how much longer will this actually run", and the `millis()` countdown is what
governs that. Half B's epoch only decides *how the countdown is seeded at boot*.

#### 4.2 The encoding for "no timeout" — pinned, with the reason

**`"timeoutRemaining": -1` means no timeout.** `0`–`28800` is a real remainder.

Why `-1` and not `0`, `null`, or an absent key:

- `0` is ambiguous with "about to expire" and there is no way for a client to tell
  the two apart. Rejected.
- `null` is honest JSON but forces every consumer into a type check, and the
  consumers here are `scripts/*.sh` doing `grep -o`. Rejected.
- An absent key is the cheapest on the wire, but it makes the field's *presence*
  carry meaning, which is a second thing to document and a second thing for a shell
  script to get wrong.
- `-1` is a single always-present integer, unambiguously outside the legal 0–28800
  range so no client can mistake it for a remainder, `String(int)` to produce, and
  one `grep`/`jq` expression to consume.

`0` is reachable in practice only in the sub-loop-iteration window where a `STATUS`
races the revert. Document that.

#### 4.3 The `custom` block — and the packet-size landmine

Per the spec: omit the `custom` block **entirely** when `currentTheme != THEME_CUSTOM`,
so old clients see byte-identical `STATUS` payloads. Emit:

```json
"custom":{"mode":"COLORLOOP","timeoutRemaining":214}
```

**Do not emit `colors`, even though the spec's example shows it.** This is not a
style preference — it does not fit on the wire:

`PubSubClient` is at its default 256-byte buffer for the whole packet, and
`src/main.cpp` never calls `setBufferSize()`. `PubSubClient::publish()` returns
`false` **without transmitting and without logging** when
`bufferSize < MQTT_MAX_HEADER_SIZE(5) + 2 + strlen(topic) + payloadLen`.
`publishState()` ignores that return value. So the payload budget is
`236 - strlen(deviceName)` bytes. Measured against the current builder:

| `STATUS` payload | bytes | longest device name that still publishes |
|---|---|---|
| today (no `custom` block) | 166 | 70 |
| `+ {"mode","timeoutRemaining"}` | 221 | **15** |
| `+ mode + 8 × `"#RRGGBB"` + timeoutRemaining` | 312 | **impossible** |

The eight-color form **cannot be published at all**. The mode+remaining form fits
today's device names (`kitchen`, `workbench`, `recycling`, `desk`, `tv` — all ≤ 9)
with 6 bytes to spare, and the failure mode when it does not fit is that `STATUS`
**silently stops publishing entirely** whenever a custom effect is active. That is a
much worse bug than the one this ticket fixes.

Two required mitigations, both cheap:

1. **`mqtt.setBufferSize(512);` in `ensureMqtt()`**, next to the existing
   `setServer`/`setCallback` calls, before `mqtt.connect()`. ~256 bytes of extra
   heap, a handful of flash. `setBufferSize()` `realloc`s on every call, so if the
   per-reconnect churn bothers you, guard it with a `static bool` — behavior is
   identical either way. This is listed as an allowed deviation in #0016's plan; #0017
   is the ticket that actually consumes the margin, so it lands here.
2. **Check `publish()`'s return in `publishState()`** and
   `ESP_LOGE(TAG, "publishState: payload %u B too large for MQTT buffer", …)` on
   false. `ESP_LOGE`, not `LOGW` — `[env:esp32c3]` builds at
   `CONFIG_LOG_MAXIMUM_LEVEL=1` and only `ESP_LOGE` survives in a release build.
   This turns an invisible failure into a diagnosable one for four lines of code.

With `setBufferSize(512)` the budget becomes `492 - strlen(name)` and even the
eight-color form fits — but still leave `colors` out. `SET_EFFECT` is the only thing
that sets them, the sender already knows them, and re-serializing eight RGB triples
into every retained state publish spends flash and wire for no consumer.

`EFFECT_MODE_NAMES[]` for the `mode` string is added by #0016 § 5.1 — reuse it, do
not add a second table.

### 5. The `SET_CLOCK_OFFSET` rebase trap

`customEffect.activatedAt` is a `millis()`-domain base, and `SET_EFFECT` seeds it
with `nowMs()`. When `SET_CLOCK_OFFSET:<ms>` jumps `clockOffsetMs`, every deadline
computed against the old `nowMs()` is stranded — [#0008](0008.md)'s round-2 defect,
verbatim. The handler currently rebases `fx.blendTimeout` and `fx.rotateTimeout`;
[#0015](0015.md) adds `fx.effectTimeout`. **#0017 adds one more line:**

```cpp
fx.blendTimeout  = nowMs();
fx.rotateTimeout = nowMs();
fx.effectTimeout = nowMs();   // issue #0015
customEffect.activatedAt = nowMs();   // issue #0017 -- rebase the timeout deadline
if (effectResumePending) effectResumeGraceUntil = nowMs() + RESUME_GRACE_MS;  // #0017, half B
```

Three things the implementer must internalize:

1. **This code compiles only under `-DENABLE_CLOCK_OFFSET`, i.e. only
   `[env:esp32c3-debug]`.** A green `pio run -e esp32c3` proves nothing about it.
   **Build both envs.** #0015 was warned about exactly this and #0008 shipped the
   defect twice.
2. **Rebasing `activatedAt` restarts the countdown.** That is correct and
   intentional for a debug-only bench harness — the alternative is the stranded
   deadline that froze four strips for days. Write a comment saying so, so a reviewer
   does not file it as a bug: "an 8-hour timeout restarts when the bench clock jumps;
   the harness is not part of the release build."
3. **A native test cannot reach this.** #0008 round 3 proved it by experiment:
   reintroducing the handler's off-by-one left all 10 native tests passing, because
   `onMqttMessage()` is Arduino-coupled and never enters the native link. Do **not**
   claim native coverage of this line. Its only proofs are that
   `pio run -e esp32c3-debug` compiles and the on-device bench run in §10.

### 6. Half B — reboot semantics, and why it is not an `if` statement

#### 6.1 The trap: the clock is never ready at boot

The ticket's decision table reads like boot-time logic. It cannot be. Trace the
actual startup:

```
setup() -> setupLED() -> loadAllPreferences()   <-- NTP not configured, WiFi not up
        -> setupIR()
        -> ensureWifi()                          <-- blocks up to 30 s
loop()  -> loopOta() -> configTzTime(...)        <-- FIRST NTP configuration, and only
                                                     after WiFi.status()==WL_CONNECTED
        ...SNTP round trip, seconds later...     <-- clock actually becomes valid
```

`configTzTime()` is called **inside `loopOta()`**, guarded on WiFi being connected.
At `loadAllPreferences()` time `getLocalTime()` is false on every boot, always.
**A literal boot-time implementation of the table therefore takes the "clock not
synced → revert" row 100% of the time and the whole feature is a no-op that
looks implemented.** This is the single most likely way this ticket ships broken.

So the decision must be **deferred and resolved in the loop**, with a bounded grace
window after which the unsynced row applies for real. That is what makes half B
cost what it costs.

#### 6.2 Storage: a separate NVS key, not a struct field

```cpp
static uint32_t effectEndEpoch = 0;   // UTC seconds; 0 = no timeout / not resumable
static bool     effectResumePending = false;
static uint32_t effectResumeGraceUntil = 0;
```

Persist the epoch under its own key, **`fx_end`**, written inside
`saveCustomEffectToPreferences()` in the same `begin`/`end` session as `fx_ver` and
`fx_cfg`:

```cpp
preferences.begin("glow_kitchen", false);
preferences.putUChar("fx_ver", SETTINGS_VERSION);
preferences.putBytes("fx_cfg", &customEffect, sizeof(customEffect));
preferences.putUInt("fx_end", effectEndEpoch);   // issue #0017; always written
preferences.end();
```

**Why a separate key rather than a field in `CustomEffectConfig`:**

- Adding a field changes `sizeof(CustomEffectConfig)`, which #0016's
  `applyLoadedCustomEffect()` gates on, which forces a `SETTINGS_VERSION` bump to 3
  and invalidates #0016's native cases 24 and 26 — churn in a file another ticket
  just wrote.
- It keeps half B **purely additive**: one key, one loop branch, one line in two
  save/cancel helpers. Cutting it removes nothing from #0016.
- The usual objection (two writes that can diverge) does not apply, because both are
  written unconditionally in the same session by the same function. `fx_end == 0` is
  a legal, meaningful value ("no timeout"), so it can never be stale.

In-struct is an **allowed deviation** if the implementer prefers it — bump
`SETTINGS_VERSION` to 3 and update #0016's size-dependent test cases. Say which you
chose in `## Fix`.

Read side, in `loadAllPreferences()`, immediately after #0016's
`applyLoadedCustomEffect()` call and inside the same read-only session:

```cpp
effectEndEpoch = accepted ? preferences.getUInt("fx_end", 0) : 0;
```

Gate it on the config having been accepted. If `applyLoadedCustomEffect()` rejected
and reset the config, a leftover end time is meaningless; treat it as 0. No need to
erase the key — the next save rewrites it.

#### 6.3 The resume state machine

At `SET_EFFECT` time, alongside `customEffect.activatedAt = nowMs()`:

```cpp
uint32_t epoch = 0;
effectEndEpoch = (customEffect.timeoutMs && clockEpochNow(epoch))
                 ? epoch + customEffect.timeoutMs / 1000 : 0;
```

An effect set while the clock is unsynced gets `fx_end == 0` and is therefore
**not** resumable across a reboot — it reverts on boot. That is the right answer and
it falls out for free: without a wall clock there is no honest remainder to compute.
Log it at `ESP_LOGI` so it is explicable.

At boot, after #0016's load and after the `THEME_CUSTOM` boot guard has run:

```cpp
if (currentTheme == THEME_CUSTOM && customEffect.timeoutMs > 0) {
    effectResumePending    = true;
    effectResumeGraceUntil = nowMs() + RESUME_GRACE_MS;   // 120000
    customEffect.activatedAt = 0;   // countdown does NOT start until resolved
    customEffect.timeoutMs   = 0;   // <-- see the note below
}
```

**Keep the effect rendering while the decision is pending.** Do not blank the strip
or bounce to the revert theme for 20 seconds and back. A visible flicker to Green
and back is worse than either outcome.

Careful with the two zeroed fields: the pending state needs `timeoutMs` out of the
way so §2.2's live check cannot fire on a half-seeded countdown, but the *original*
duration is still needed as the resume clamp. Keep it in a local
`pendingTimeoutMs` file-scope variable rather than re-reading NVS. **An implementer
who zeroes `timeoutMs` without stashing it will silently turn every resumed effect
into an untimed one** — a `revertFromCustomEffect()` that never fires. Alternative
and arguably cleaner: leave `timeoutMs` intact and gate §2.2's check on
`!effectResumePending`. Either works; pick one and be explicit.

Then, first thing in `loopEffectTimeout()`:

```cpp
if (effectResumePending) {
    uint32_t epoch;
    if (clockEpochNow(epoch)) {
        effectResumePending = false;
        if (effectEndEpoch == 0 || epoch >= effectEndEpoch) {
            ESP_LOGI(TAG, "Custom effect expired while powered down; reverting");
            revertFromCustomEffect();
        } else {
            customEffect.timeoutMs   = resumeTimeoutMs(epoch, effectEndEpoch);
            customEffect.activatedAt = nowMs();
            ESP_LOGI(TAG, "Custom effect resumed, %lu s remaining",
                     (unsigned long)(customEffect.timeoutMs / 1000));
        }
    } else if (timeReached(nowMs(), effectResumeGraceUntil)) {
        effectResumePending = false;
        ESP_LOGI(TAG, "Clock never synced within grace window; reverting custom effect");
        revertFromCustomEffect();
    }
    return;
}
```

**The resume writes no NVS.** It adjusts the in-RAM `activatedAt`/`timeoutMs` only.
Two reasons: a second reboot must re-derive from the *unchanged* `fx_end` rather than
from a progressively shortened `timeoutMs`, and it avoids a flash write on every
boot. Say this in a comment.

`RESUME_GRACE_MS = 120000` — WiFi association plus an SNTP round trip is seconds in
the normal case; 120 s is generous enough that a slow AP does not cost a legitimate
8-hour effect, and short enough that a device with no network reaches a definite
answer while someone is still standing there. It is a judgement call; say so, and
deviate if the bench says otherwise.

#### 6.4 "Clock ready" — reuse, do not reinvent

`loopOta()` already owns the project's notion of a valid clock:
`getLocalTime(&now, 0)` plus `if (now.tm_year + 1900 < 2020) return;`. Factor that
into one helper and have **both** call it:

```cpp
static const uint32_t CLOCK_VALID_EPOCH = 1577836800UL;  // 2020-01-01T00:00:00Z --
                                                         // same 2020 threshold loopOta() uses
static bool clockEpochNow(uint32_t& outEpoch) {
    time_t t = time(nullptr);
    if (t < (time_t)CLOCK_VALID_EPOCH) return false;
    outEpoch = (uint32_t)t;
    return true;
}
```

`time(nullptr)` returns UTC epoch regardless of the `TZ` `configTzTime()` installed,
which is exactly what an absolute end time wants — no DST arithmetic, no local-time
ambiguity across a spring-forward. `getLocalTime()`'s own internal validity test is
`tm_year > 116`, i.e. the same threshold expressed differently, so this is genuinely
one notion and not a second one.

Refactoring `loopOta()`'s `tm_year + 1900 < 2020` line to call `clockEpochNow()` is
**optional and recommended** — it makes the reuse literal rather than parallel. It
touches the OTA scheduler, so if you would rather not, leave `loopOta()` alone and
put a comment in `clockEpochNow()` naming the line it mirrors. Do not silently pick
a different threshold.

`uint32_t` epoch is good until 2106 and the NVS key is `putUInt`. Note it; do not
widen to 64-bit for a field with an 8-hour horizon.

#### 6.5 Resume clamp

```cpp
inline uint32_t resumeTimeoutMs(uint32_t nowEpoch, uint32_t endEpoch) {
    if (endEpoch <= nowEpoch) return 0;
    uint32_t secs = endEpoch - nowEpoch;
    if (secs > 28800UL) secs = 28800UL;      // never exceed the #0016 clamp
    return secs * 1000UL;
}
```

The clamp is defensive, not decorative: a corrupt `fx_end`, or a clock that synced to
a wrong year and then corrected, can produce an arbitrarily far-future end time, and
without the clamp `secs * 1000` overflows `uint32_t` above ~49.7 days and yields a
short or negative-looking remainder. Clamping to the same 28,800 s ceiling #0016
enforces on input means a resumed effect can never outlive a freshly-set one.

### 11. Uncertainties, and where to deviate

- **`RESUME_GRACE_MS = 120000`** is a judgement call, not a derived number. If the
  bench shows SNTP settling in 3 s, 30 s is plenty and gets to a definite answer
  faster. Deviate freely; state the value and why.
- **Separate `fx_end` key vs. a struct field** (§6.2). The key is cheaper and keeps
  half B cuttable; the field is tidier. Either is fine — if you take the field, bump
  `SETTINGS_VERSION` to 3 and fix #0016's size-dependent test cases in the same
  commit rather than leaving them asserting a stale `sizeof`.
- **Zeroing `timeoutMs` while pending vs. gating on `effectResumePending`** (§6.3).
  The gate is less error-prone; the zeroing matches the "countdown has not started"
  mental model. Pick one, be explicit, and if you zero, *stash the original*.
- **`-1` as the no-timeout sentinel** (§4.2). If a downstream consumer
  (`scripts/get_device_status.sh`, a Home Assistant template) turns out to choke on a
  negative integer, omitting the key is the fallback — but then document that absence
  means "no timeout" and update the doc and any script in the same pass. Do not leave
  two encodings documented.
- **`mqtt.setBufferSize(512)`** (§4.3) is a real behavior change to the MQTT client,

- **Omitting `colors` from the `custom` block** contradicts the spec's example. It is

## Long Description

Steps 5–6 of the spec's build order, plus the reboot semantics the spec leaves unsettled.

### Reboot behavior — the part the spec does not settle

`activatedAt = millis()` resets to zero on boot, so a persisted effect would silently restart its timer: an 8-hour event effect interrupted by a power blip at hour 7 would run another 8 hours. Neither blanket policy is right — always reverting loses a long effect to a momentary glitch, always resuming restarts short ones that should have expired during the reboot itself.

Persist an absolute end time instead of an elapsed offset. NTP is already configured for the OTA scheduler, so on boot:

| condition | action |
|---|---|
| clock valid and `now < endTime` | resume the effect with the correct remaining time |
| clock valid and `now >= endTime` | revert immediately — it expired while powered down |
| clock not yet synced | revert — a wrong guess about a timed effect is worse than dropping it |

A 30-second effect expires across a reboot; an 8-hour one resumes with the right remainder.

### Cancellation paths

All of these must cancel a pending revert rather than leaving it queued:

- `CLEAR_EFFECT` — reverts immediately, without waiting for the timeout.
- An explicit theme command (`RAINBOW`, `GREEN`, …) — reverting to a theme the user has since moved away from would be baffling.
- A second `SET_EFFECT` — replaces both the effect and its timeout.

### STATUS

`STATUS` reports `timeoutRemaining` so a clamped value is discoverable rather than silent — this is the visibility half of the parent's "clamp rather than reject" decision. Report remaining seconds, `0`, or an explicit "no timeout" for an untimed effect; say which encoding was chosen in `## Fix` and document it in `docs/mqtt_commands.md`.

### Timing

The timeout check goes through `timeReached()` (see [#0008](0008.md)). 8 hours is well inside the ~24.8-day window it handles. The spec's own timeout example already uses the correct elapsed form — keep it. Do not substitute `EVERY_N_MILLISECONDS`.

Note the two clocks are doing different jobs and both are needed: `timeReached()` on `millis()` drives the in-session countdown, while the persisted NTP wall-clock end time survives the reboot. Don't collapse them into one.

## Expected behavior

A custom effect with `timeout: 1800` runs for 30 minutes, then the strip returns to its prior theme on its own. `CLEAR_EFFECT` returns it immediately. A reboot mid-effect resumes or expires it correctly per the table above. `STATUS` shows the remaining time.

## Actual behavior

No timeout exists; a custom effect (once [#0016](0016.md) lands) would stay until explicitly changed.

## Notes

- The revert target is "the theme active before the effect was applied" — it must be persisted alongside the effect, or a reboot-resumed effect will revert to the wrong theme when it finally expires.
- Clock-valid detection: reuse whatever the OTA scheduler already relies on rather than inventing a second notion of "NTP is ready".
- Native-testable: the boot decision table and the clamp/remaining arithmetic are pure logic. Cover them in `[env:native]`.
- Docs to update here: `docs/mqtt_commands.md` (`timeoutRemaining` in the `STATUS` response).
