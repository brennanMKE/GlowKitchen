## Description

Switching themes or effects changes the strip on the very next frame — a hard cut. It should crossfade: the outgoing look fades out while the incoming one fades in, over a **full second**, then the old one is torn down.

## Long Description

Today `loopLED()` renders one `EffectState` into the single `leds[]` buffer and pushes it with `FastLED.show()`. A theme change swaps the palette pointer; an effect change swaps `EffectMode` and calls `resetEffectState()`. Either way the next frame is already fully the new look.

A crossfade means running **two renderers in parallel** for the transition window: the old mode/palette and the new one each render into their own buffer, and the two are mixed per-LED by a progress factor before `show()`. `EffectState` was deliberately written to make that possible — its header comment says a test can "construct two independent instances and diff their output", and every renderer writes only through `s.leds` / `s.numLeds`. The open questions are memory (a second `CRGB[MAX_LEDS]` at MAX_LEDS = 500 is 1500 bytes of RAM), which state must be duplicated (`timeouts[]` and `sparkleVal[]` are per-LED side buffers, so a second renderer needs its own or must be made not to need them), what happens when a second switch arrives mid-fade, and whether brightness/power changes should ride the same mechanism.

## Expected behavior

- Any change of theme, effect, or custom-effect config starts a 1000 ms crossfade from the currently-rendered look to the new one.
- The transition is smooth on the strip — no visible stutter, no frame-rate drop, no flash to black or white between the two looks.
- Both looks stay *animated* during the fade (this is a crossfade of two live animations, not a fade through a frozen snapshot) unless the plan finds a good reason otherwise.
- After 1000 ms the new look is rendered alone and the transition state is released.
- A second switch arriving mid-fade is handled sanely and never leaves the strip stuck part-way blended.

## Actual behavior

The new theme or effect appears in full on the first frame after the command lands. There is no transition at all.

### 0. The design in one paragraph

A switch no longer touches the strip. Instead, the handler calls `startLookTransition()` *before* it mutates `currentTheme`/`customEffect`, which copies the live `fx` into a second `EffectState` (`transition.out`) together with everything that describes the look being left (mode, palette pointer or snapshot, speed, intensity) and its per-LED side buffers. For the next 1000 ms `loopLED()` renders **both** states — `out` into `ledsOut[]`, `fx` (the new look, exactly as today) into `ledsIn[]` — and writes a per-LED linear mix of the two into `leds[]`, the buffer FastLED is bound to. At 1000 ms `ledsIn[]` is copied back into `leds[]`, `fx.leds` points at `leds[]` again, and the strip is byte-for-byte what it would have been without the fade. Outside a transition not one line of the render path changes. Both looks stay live animations; the only time the outgoing side is a still frame is when a second switch lands mid-fade (section 5) or the strip was off when the switch arrived.

**Rejected:** detecting the change inside `loopLED()` by comparing the look against the previous frame (no handler edits). It cannot work for custom→custom: `SET_EFFECT` overwrites the single shared `customPalette[]` (`src/effects.h:185`, via `refreshCustomPalette()` at `src/main.cpp:1118`) before the next frame runs, so there is nothing left to snapshot by the time the loop would notice. The capture must happen inside the handler, before the mutation.

### 2. Two-renderer architecture

**Why three `CRGB` buffers, not two.** Every renderer returns `false` without painting when its deadline has not been reached (`renderBlend()` `:324`, `renderChase()` `:554`, … , and FLICKER/NEON paint only the LEDs whose per-LED deadline expired, `:427`, `:886`). They all rely on their target buffer holding the previous frame between paints. Mixing in place into the buffer either renderer paints would therefore corrupt that renderer's next non-painting frame (it would re-mix an already mixed value). So during a fade each renderer needs its own persistent buffer, and the mixed result needs a third — which must be `leds[]`, because `FastLED.addLeds<>(leds, MAX_LEDS)` (`:1447`) is bound to that address. Outside a fade `fx` paints `leds[]` directly, exactly as today.

**New header `src/effect_transition.h`** (include-order contract inherited from `effects.h`; header-only for the same `[env:native]` reason as `effect_timeout.h`):

```c
static const uint32_t TRANSITION_MS       = 1000;
static const uint32_t TRANSITION_FRAME_MS = 20;    // max re-mix/show cadence during a fade (~50 fps)

struct EffectTransition {
    bool        active;
    bool        outFrozen;    // outgoing is a still frame: no renderer runs on it
    bool        fillPending;  // ledsIn not yet primed with the incoming look's first colour
    uint32_t    startedAt;    // nowMs() at the (re)start
    uint32_t    lastMixAt;

    // The look being left: a copy of fx, plus the per-look inputs loopLED()
    // would otherwise re-seed from globals every frame.
    EffectState         out;
    EffectMode          outMode;
    const PaletteColor* outColors;
    int                 outColorCount;
    uint8_t             outSpeed, outIntensity;
    PaletteColor        outPalette[MAX_CUSTOM_COLORS];  // snapshot when outColors was customPalette

    // Owned storage, wired once in setupLED() like fx.timeouts / fx.sparkleVal.
    CRGB*     ledsIn;       // incoming renders here during a fade
    CRGB*     ledsOut;      // outgoing renders here during a fade
    uint32_t* timeoutsOut;  // outgoing FLICKER/NEON per-LED deadlines
    uint8_t*  sparkleOut;   // outgoing SPARKLE per-LED brightness
};
```

**Mixing.** Do **not** use FastLED's `blend()`/`nblend()`/`blend8()`: none exist in `test/test_effects/fastled_shim.h`, and #0015's ground rule 3 pins the FastLED surface inside these headers to `CRGB`/`CHSV`/`sin8`/`min`/`max`. Three lines of integer math are exact at both endpoints, which is what the tests pin:

```c
inline uint8_t lerp8(uint8_t a, uint8_t b, uint8_t amt) {
    return (uint8_t)((int32_t)a + (((int32_t)b - (int32_t)a) * (int32_t)amt) / 255);
}
inline void mixFrames(const CRGB* from, const CRGB* to, CRGB* dst, int n, uint8_t amt) {
    for (int i = 0; i < n; i++) {
        dst[i].r = lerp8(from[i].r, to[i].r, amt);
        dst[i].g = lerp8(from[i].g, to[i].g, amt);
        dst[i].b = lerp8(from[i].b, to[i].b, amt);
    }
}
```
`int32_t`, not `int16_t`: `(b - a) * amt` reaches ±65,025. `amt = 0` returns `a` exactly, `amt = 255` returns `b` exactly, and the sequence is monotone in `amt` (integer division of a monotone sequence). On device this is an RGB crossfade; on the host shim it lerps the stored `{h,s,v}` bytes, which is fine because the tests check the mixer's arithmetic, not colour accuracy.

**Begin / prime / end**, all in the header:

```c
inline void beginTransition(EffectTransition& t, EffectState& fx, CRGB* leds, int numLeds,
                            EffectMode outMode, const PaletteColor* outColors, int outColorCount,
                            bool outColorsAreCustom, uint8_t outSpeed, uint8_t outIntensity,
                            bool live, uint32_t now) {
    memcpy(t.ledsOut, leds, sizeof(CRGB) * numLeds);   // whatever is on the strip becomes the outgoing picture
    if (t.active || !live) {
        t.outFrozen = true;                              // re-trigger: freeze the composite; off: freeze black
    } else {
        t.outFrozen = false;
        t.out = fx;
        t.out.leds = t.ledsOut;
        t.out.timeouts = t.timeoutsOut;
        t.out.sparkleVal = t.sparkleOut;
        if (fx.timeouts)   memcpy(t.timeoutsOut, fx.timeouts,   sizeof(uint32_t) * numLeds);
        if (fx.sparkleVal) memcpy(t.sparkleOut,  fx.sparkleVal, sizeof(uint8_t)  * numLeds);
        t.outMode = outMode; t.outColorCount = outColorCount;
        t.outSpeed = outSpeed; t.outIntensity = outIntensity;
        if (outColorsAreCustom) {
            int n = min(outColorCount, (int)MAX_CUSTOM_COLORS);
            for (int i = 0; i < n; i++) t.outPalette[i] = outColors[i];
            t.outColors = t.outPalette;
        } else {
            t.outColors = outColors;                     // a const built-in table in themes.h; immutable
        }
    }
    t.fillPending = true;
    t.startedAt = now;
    t.lastMixAt = now - TRANSITION_FRAME_MS;             // first loop iteration mixes and shows
    t.active = true;
}

// Called by loopLED() once fx is seeded with the NEW look. Reproduces what the
// deleted fill_solid() blocks did, into the incoming buffer instead of the strip.
inline void primeIncoming(EffectTransition& t, const PaletteColor* colors, int colorCount,
                          int hueIndex, int numLeds) {
    if (!t.fillPending) return;
    t.fillPending = false;
    PaletteColor c = (colors && colorCount > 0) ? colors[hueIndex % colorCount] : PaletteColor{0, 0, 0};
    for (int i = 0; i < numLeds; i++) t.ledsIn[i] = CHSV(c.h, c.s, c.v);
}

inline void endTransition(EffectTransition& t, CRGB* leds, int numLeds) {
    if (!t.active) return;
    memcpy(leds, t.ledsIn, sizeof(CRGB) * numLeds);      // the strip is now exactly the incoming look
    t.active = false; t.outFrozen = false; t.fillPending = false;
}
```

`primeIncoming()` is lazy (a flag, filled on the first transition frame) so that each trigger site is **one** call placed before the mutation; the fill colour comes from the *new* look, which does not exist yet at that point. The `%` guard matters: `renderFlicker()` indexes `s.colors[s.hueIndex]` unguarded (`:432`), and handlers zero `hueIndex` after the capture anyway.

### 3. Memory budget

Which per-LED side buffers each renderer touches (verified by reading every renderer in `src/effects.h`):

| buffer | readers/writers |
|---|---|
| `timeouts[]` (`uint32_t[MAX_LEDS]`, 2000 B) | `renderFlicker()` `:427-430`, `renderNeon()` `:886-888` only |
| `sparkleVal[]` (`uint8_t[MAX_LEDS]`, 500 B) | `renderSparkle()` `:753-767` only; zeroed by `resetEffectState()` `:309` |
| none | BLEND, CHASE, WIPE, SCAN, PULSE, STROBE, COLORLOOP, RAIN (in-struct 32 B), TRAIL, STACK |

Sharing is not viable: FLICKER→FLICKER (Green → a custom FLICKER effect, or NEON → Green) would have two renderers consuming the same per-LED deadlines, and the incoming's mode-change `resetEffectState()` zeroes `sparkleVal[]` (`:309`), which would kill an outgoing SPARKLE on frame one. So the outgoing gets its own copies, taken at `beginTransition()`; the incoming keeps the primaries, so its behaviour is identical to today's switch (where `timeouts[]` is deliberately never reset — #0014).

Added static RAM: `ledsIn` 1500 + `ledsOut` 1500 + `timeoutsOut` 2000 + `sparkleOut` 500 + `EffectTransition` (one `EffectState` ≈ 124 B + palette 24 B + fields) ≈ **5,700 B**. Current build: 43,504 B of 327,680 B (13.3 %); after: ≈ 49,200 B (≈ 15.0 %). **Static, fixed-size, per `AGENTS.md`'s "avoid dynamic allocation".** Rejected: allocating the four buffers only for the fade's duration — it saves 1.7 % of RAM the project does not need, and adds a `malloc` failure path plus heap fragmentation next to WiFi/TLS buffers. Flash: expect +1–2 KB against 71,712 B of headroom; record the `firmware.bin` size in `## Verification` as #0015 did.

### 4. Progress curve and timing

```c
inline uint8_t transitionMix(uint32_t now, uint32_t startedAt) {
    uint32_t elapsed = now - startedAt;              // unsigned: correct across the 2^32 wrap
    if (elapsed >= TRANSITION_MS) return 255;
    return (uint8_t)((elapsed * 255u) / TRANSITION_MS);
}
inline bool transitionDone(uint32_t now, uint32_t startedAt) {
    return timeReached(now, startedAt + TRANSITION_MS);   // the project's one deadline idiom (#0008)
}
```
Clock is `nowMs()` in `main.cpp` (the header takes `now` as a parameter, like every other header). Both forms survive the wrap; `effect_timeout.h:26-35` explains why they are arithmetically identical for any duration < 2^31.

**Linear, no easing.** WS2812 output is already perceptually non-linear (no gamma correction anywhere in this firmware), so an ease-in-out on top makes the middle of a 1 s fade feel like it stalls; linear gives ~5 mix levels per 20 ms frame, which is smooth. Rejected `ease8InOutQuad`: it is not in the shim, and the midpoint test would then pin FastLED's table instead of a formula. If the user wants easing later it is one line inside `transitionMix()` plus one test.

### 5. Re-entrancy: a second switch mid-fade

**Rule: the frame currently on the strip — the half-mixed composite — is frozen and becomes the new outgoing; the new look fades in over a fresh 1000 ms.** Implemented by the `if (t.active) t.outFrozen = true;` branch in `beginTransition()`: `ledsOut[]` gets `leds[]` (which always holds the last shown frame), no outgoing renderer runs, `startedAt` restarts.

Why this and not "hand the in-flight incoming over to the outgoing slot": at 30 % into A→B the strip shows 70 % A + 30 % B; promoting B to outgoing means B's first tick repaints its whole buffer and 70 % of A vanishes in one frame — a visible pop. Keeping all three animated needs a third renderer and buffer set. Freezing the composite costs nothing, cannot pop, and only ever happens when someone switches twice within a second (IR remote scrolling), where a still outgoing for ≤ 1 s is invisible in practice.

Why it cannot leave the strip stuck part-way: `transitionDone()` is a pure function of `now - startedAt`, so any active transition ends at most 1000 ms after its most recent `beginTransition()`, and `endTransition()` copies the incoming buffer to `leds[]` unconditionally. There is no state that can hold `active == true` past that point — the only other exits (`OFF`, `SET_NUM_LEDS`, `SET_CLOCK_OFFSET`) also call `endTransition()`.

### 6. Interaction with existing state

- **#0014's `resetEffectState()` contract** (`src/effects.h:291-310`) is untouched: the function is not edited, and `fx` still receives exactly one call per mode change from `loopLED():1566-1569`. `transition.out` is a *copy* of `fx` taken before that reset runs (the handler runs from `ensureMqtt()`/`loopIR()`, both outside `loopLED()`), so the outgoing keeps its `blendTimeout`/`rotateTimeout`/`hueTimeout`/`blendOffset`/`timeouts[]` and continues its animation; the incoming inherits the primaries exactly as it does today. Same-mode switches (Rainbow → Forest, both BLEND) fire no reset, as today.
- **`lastMode`** stays on `fx` only. `out.lastMode` is copied and never read.
- **`hueIndex` global** (`:1576`, `:1635`): seeded into and copied back from `fx` only; `out.hueIndex` is private to the outgoing and always indexes the outgoing's own (snapshotted) palette, so FLICKER's unguarded `s.colors[s.hueIndex]` stays in bounds.
- **`customPalette[]`** (`src/effects.h:185`): the one mutable shared table; snapshotted into `outPalette[]` when the outgoing theme is `THEME_CUSTOM`. Built-in tables are `const` in `themes.h` and are referenced by pointer.
- **Brightness / power**: brightness is a `show()`-time scalar and needs nothing. `OFF` ends the fade (section 1). `!ledsEnabled` early return in `loopLED():1535-1544` runs before any transition code, so a fade never renders while off.
- **Effect-timeout expiry (#0017/#0021)**: `loopEffectTimeout()` runs before `loopLED()` (`:2013-2014`), calls `revertFromCustomEffect()`, which is a trigger site — the revert takes visual effect as a fade starting on the same iteration. `effectResumePending`, `effectEndEpoch`, NVS writes: untouched.
- **`EffectState` does not grow**, so `LegacyEffectState` and the eight frame-diff cases are structurally unaffected.

### 10. Risks and gotchas

- **Frame-rate.** During a fade `show()` runs at most every `TRANSITION_FRAME_MS` (20 ms). WS2812 at 240 LEDs is ≈ 7.5 ms per `show()`, at `MAX_LEDS` 500 ≈ 15 ms — 37 % / 75 % duty for one second. This is *not* a new worst case: SCAN at speed 255 already ticks every 4 ms (`:612`) and shows on every tick. `mqtt.loop()` and IR still run between frames. Render cost is negligible next to `show()`; the only float in the tree is `renderBlend()`'s per-LED `blendFraction` (`:340`, soft-float on the FPU-less C3), and it runs once per 100 ms per instance.
- **Renderers hostile to two instances: none.** All thirteen read and write only through `s`. The two shared things outside `EffectState` — `customPalette[]` and the global `hueIndex` — are handled by the snapshot and by copying back from `fx` only. `getCurrentEffectMode()`/`getCurrentColorArray()` read globals and are only ever used for the incoming.
- **Ordering inside `beginTransition()`:** `t.out = fx` copies the `leds`/`timeouts`/`sparkleVal` *pointers*; all three must be overridden afterwards or the outgoing paints the primary buffers. Test 5 catches the `timeouts` case; be as careful with the other two.
- **Capture-before-mutate** is the one discipline the implementer must not slip on. In `SET_EFFECT` the call goes before `:1112`, not after `:1118`; in `revertFromCustomEffect()` before `:477`. A misplaced call fades from the *new* look to itself (no visible fade) rather than crashing, so the on-device checklist is what catches it.
- **`fx.hueIndex` vs the new palette**: the handlers zero `hueIndex` after the capture; `primeIncoming()` still uses `% colorCount` because `loopLED()` seeds `fx.hueIndex = hueIndex` at `:1576` from the global, which may be stale by one frame only in theory — the guard costs nothing.
- **Mirror + outgoing FLICKER** gets mirrored for ≤ 1 s (section 2). Cosmetic.
- **Interrupted transition**: `OFF`, `SET_NUM_LEDS`, `SET_CLOCK_OFFSET` end it; a reboot loses it (fine); `revertFromCustomEffect()` firing during a fade is just the re-trigger rule. Nothing about a transition is persisted.
- **RGB crossfade dips through dark** for complementary hues (red↔cyan passes through grey at half value). Standard crossfade behaviour; HSV mixing is impossible on device because `leds[]` holds RGB. Note it, do not fix it.
- **The debug env**: `endTransition()` in the `SET_CLOCK_OFFSET` handler compiles only there. Build it.
