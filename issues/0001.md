# 0001 — OTA updates apply to the whole fleet at once with no canary/scout gating

| | |
|---|---|
| **Status** | open |
| **Module** | OTA / MQTT / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-06-26 |

## Description

Each device independently checks GitHub at 3 AM (and ~15 s after boot) and updates whenever the latest release tag differs from its running version. A bad build therefore propagates to **every** device with no safeguard, and recovery means physically re-flashing each board over USB. Add a canary/scout stage — coordinated through a **retained MQTT topic** — so one device validates a new release (health check + automatic rollback) before the rest of the fleet applies it.

## Long Description

### Goal
Introduce progressive/canary rollout to the existing OTA pipeline (`OTA.md`, `checkForOtaUpdate()` / `loopOta()` in `src/main.cpp`). Discovery stays decentralized (each device still finds new releases via the GitHub API), but **application** is gated on a shared decision held in retained MQTT messages, so the broker (Home Assistant) is the single source of truth rather than a fragile peer election.

### Proposed coordination (retained topics)
- `lights/ota/deployment` (retained): `{ "version": "x.y.z", "state": "canary" | "approved" | "failed", "scout": "<deviceId>" }` — the current rollout decision for a specific version.
- `lights/ota/bad_versions` (retained): a deny-list of versions known to fail the canary, so even a rolled-back scout or a late-joining device permanently skips them.

Using retained messages is deliberate: any device reads the current decision whenever it connects, so devices that were offline during a live broadcast still behave correctly. This avoids the split-brain / missed-message / re-election failure modes of a "highest random number wins" peer election (see Notes).

### Scout (canary) flow
1. A device discovers release `x.y.z`. Before updating it reads `lights/ota/deployment` and `lights/ota/bad_versions`.
2. If `x.y.z` is in `bad_versions`, skip it.
3. If no claim exists for `x.y.z`, the device becomes scout: write the retained `deployment` topic with `state:canary` and its own id. Otherwise it waits for a decision.
4. The scout updates, then runs a **health check** (see below). On success it writes `state:approved`; on failure it appends `x.y.z` to `bad_versions`, sets `state:failed`, and rolls back.
5. All other devices apply `x.y.z` only once `deployment` shows `state:approved` for that exact version.

### Health check + rollback (the single-device foundation)
- After an OTA boot, confirm health before "committing" the new image: reconnect to WiFi **and** MQTT, soak for N minutes with no crash/reboot, and ideally a functional check (LEDs actually rendered a frame).
- Track a **boot-loop counter in NVS**: N rapid reboots ⇒ treat the release as failed.
- On failure, roll back to the previous slot (`Update.rollBack()` / `esp_ota` APIs — app-level rollback; the inactive slot still holds the last-good firmware) and record the bad version.
- On success, mark the running image valid (`esp_ota_mark_app_valid_cancel_rollback()`).

### Suggested implementation staging
1. **Stage 1 — single-device health-check + rollback** (no coordination yet). Prove a deliberately-broken build auto-reverts on the dev board. This is the foundation and de-risks everything.
2. **Stage 2 — retained-topic canary coordination** across the fleet, per the flow above.

## Expected behavior

A new release is validated by a single scout device first; the rest of the fleet updates only after the scout passes its health check. A release that fails the health check is rolled back on the scout and skipped fleet-wide, so a bad build never reaches every device.

## Actual behavior

Every device updates to a new release independently and near-simultaneously (3 AM check, or on boot). There is no health check, no rollback, and no fleet-level gate — a broken release bricks the entire fleet and requires per-device USB recovery.

## Notes

- Design discussion concluded that the strategy (canary → health gate → skip bad version) matches standard fleet practice (canary/progressive rollout, A/B commit-confirm, health-check rollback, known-bad deny-list — cf. AWS IoT Jobs, Mender, Balena, Azure Device Update).
- The weak part of the original sketch was electing the scout via "pick a random number 1–1000, highest wins" over transient MQTT — effectively the bully algorithm without reliable messaging or known membership (split brain / missed broadcasts / lone re-election by offline devices). Replacing peer election + live broadcasts with a **retained coordination topic** is the key correction the user accepted.
- Relevant code: `loopOta()` and `checkForOtaUpdate()` in `src/main.cpp` (nightly 3 AM check + ~15 s on-boot startup check), `publishState()` (already publishes `firmwareVersion`), `scripts/ota_update.sh` (manual `OTA_UPDATE` trigger), `scripts/list_devices.sh` (fleet version readout).
- Current version compare is equality-only ("differs ⇒ update"), which also allows accidental downgrades; consider switching to "newer-only" semver as part of this work or a sibling ticket.
- `OTA.md` lists signed OTA and full bootloader-driven auto-rollback as out-of-scope v1 follow-ups; this issue targets app-level rollback, not a custom bootloader.
- Verification must be on-device (dev board + MQTT), not just a green `pio run`.
