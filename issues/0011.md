# 0011 — Add OTA_VERSION:&lt;tag&gt; so test builds ship as GitHub pre-releases instead of LAN pushes

| | |
|---|---|
| **Status** | open |
| **Module** | OTA / MQTT / Firmware |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-16 |

## Description

Local OTA ([#0002](0002.md)) requires standing up an HTTP server on the developer's machine and trusts any host on the LAN. Publishing a test build as a GitHub **pre-release** and installing it by tag avoids both: no server, and the trust boundary becomes "who can push to the repo" rather than "who can reach the network". Add `OTA_VERSION:<tag>`, which installs a specific release without consulting `/releases/latest`.

## Long Description

### Why this is better than the LAN path for routine work

| | LAN `OTA_URL` | GitHub pre-release |
|---|---|---|
| infrastructure | a local HTTP server per push | none |
| who can push firmware | anyone who can reach the broker, from any host on the LAN | anyone with write access to the repo |
| bytes authenticated | no — plain HTTP, no TLS | yes — pinned roots ([#0010](0010.md)) |
| works remotely | no | yes |

The LAN boundary is weaker than it appears: the workshop has Ethernet ports, so an attacker does not even need the WiFi password. GitHub write access is a much smaller and better-audited set.

### Mechanics (verified 2026-08-16)

A tag-specific asset URL needs **no API call at all**:

```
https://github.com/brennanMKE/GlowKitchen/releases/download/v0.0.5-beta1/firmware.bin
  → 302 → release-assets.githubusercontent.com → 200
```

Same two hosts, and therefore the same two roots already pinned in [#0010](0010.md). Skipping the API also sidesteps the 60-requests/hour unauthenticated rate limit and the `tag_name` parsing.

**Pre-releases are invisible to the automatic path.** GitHub's `/releases/latest` excludes pre-releases and drafts, confirmed live against this repo. So a beta never reaches the fleet through the startup or nightly checks — it is installed only when explicitly asked for by tag. That is exactly the gating this needs.

**Use pre-release, not draft.** Draft release assets are not publicly downloadable and would 404 on the device.

### Proposed command

```
lights/Dev/cmd  →  OTA_VERSION:0.0.5-beta1
```

The handler builds the URL from a **hardcoded owner/repo** and the supplied tag, then calls the existing `performOtaFromUrl()`. Because the host half is not user-supplied, no host validation is needed — the device can only ever fetch from this repo.

**The tag must be sanitized.** Accept only `[A-Za-z0-9._-]` and reject anything else outright. Without that, `OTA_VERSION:../../../../evil` escapes the release path and the device fetches from wherever that resolves — which would quietly undo the whole point of the change. Reject rather than strip, so a malformed tag fails loudly instead of silently installing something adjacent.

Accept the tag with or without a leading `v`, since `FIRMWARE_VERSION` carries no `v` but the tag does.

### Version comparison: numeric triple only, in one tested function

Pre-release suffixes are not meaningfully orderable — there is no sane answer to whether `0.0.5-beta1` precedes `0.0.5-nebula2`, and inventing one would be guesswork. So comparison uses **only the three numeric components** and ignores everything from the first `-` or `+`.

That is precisely why the trigger must name the tag: an ordering rule cannot select a pre-release, so a human does, and the target must already exist on GitHub as a release or pre-release.

The automatic check keeps its own rule: **releases only, newer only.** `/releases/latest` already excludes pre-releases, so the filter is inherent today — but it should be stated in code rather than relied on implicitly, in case the check ever moves to listing `/releases`, where pre-releases would have to be filtered on the `prerelease` flag.

All of this belongs in one place, as pure logic with no Arduino or network dependency:

```c
// lib/Version/Version.h
struct Version { uint16_t major, minor, patch; };

// Accepts "0.0.5", "v0.0.5", "0.0.5-beta1", "0.0.5+build.7".
// Everything from the first '-' or '+' is ignored. Returns false on malformed
// input rather than guessing -- a tag we cannot parse must never be treated as
// newer, or a typo becomes a fleet-wide downgrade.
bool parseVersion(const char* tag, Version& out);

// -1 / 0 / +1 on the numeric triple alone.
int compareVersions(const Version& a, const Version& b);
```

`checkForOtaUpdate()` then replaces:

```c
if (tagName == String(FIRMWARE_VERSION)) return;      // equality: allows downgrades
```

with a newer-only test, which also closes the accidental-downgrade gap carried in [#0001](0001.md).

### The consequence that removes the OTA_AUTO footgun

Because suffixes are dropped, **`0.0.5-beta1` compares equal to `0.0.5`**. A device on a beta therefore does *not* see the eventual stable release as newer, and will not quietly revert to it — which is a cleaner fix than forcing `OTA_AUTO:false` on every `OTA_VERSION:` install. `OTA_AUTO` stays available for pinning a device across a *later* release (`0.0.6` would still be newer and would still land), but it is no longer required just to keep a beta installed.

**The trap this introduces, and it must be documented:** a device on `0.0.5-beta1` will never automatically take the final `0.0.5`, even though that is different code. Equality means "no update", not "same firmware". The operational rule is that a device tested on a beta must be moved to the final build **explicitly** with `OTA_VERSION:0.0.5`, or be given a version bump. Silent divergence between a beta device and the released fleet is exactly the kind of thing that goes unnoticed for weeks.

### Unit tests

The parse/compare logic is pure and hardware-independent, so it belongs in a PlatformIO `native` test environment where it runs in milliseconds. Putting it in `lib/Version/` lets both the firmware and the test compile it without duplication; `test/` already exists and is currently empty.

Cases that must be covered, chosen because each one has a plausible wrong implementation:

| case | why it matters |
|---|---|
| `0.0.4` &lt; `0.0.5` | the basic ordering |
| `0.0.5` == `0.0.5` | no self-update |
| `v0.0.5` == `0.0.5` | tags carry `v`, `FIRMWARE_VERSION` does not |
| `0.0.5-beta1` == `0.0.5` | suffix dropped |
| `0.0.5-beta1` == `0.0.5-nebula2` | unorderable suffixes collapse to equal |
| **`0.0.10` &gt; `0.0.9`** | **a string compare gets this backwards** |
| `0.1.0` &gt; `0.0.99` | field precedence |
| `1.0.0` &gt; `0.99.99` | major dominates |
| `0.0.5+build.7` == `0.0.5` | build metadata also ignored |
| `""`, `"abc"`, `"0.0"`, `"0.0.5.6"`, `"0.0.-1"` | malformed → parse fails, never "newer" |
| `"99999.0.0"` | overflow is rejected, not wrapped |

The `0.0.10` vs `0.0.9` case is the one to be most careful about: the current equality check hides it entirely, and any lexicographic shortcut gets it wrong the moment a component reaches double digits.

**A caution carried over from [#0008](0008.md):** native tests build for LP64, where fixed-width assumptions that hold on the C3 do not. Use explicit `uint16_t`/`int` types in this code, and do not let a green native test stand in for on-device verification of anything that depends on 32-bit wraparound.

### What this does not replace

`OTA_URL` stays. If a pinned root ever stops matching ([#0010](0010.md)), **every GitHub path dies at once, fleet-wide**, and a plain-HTTP LAN push is the only remaining way to install firmware. It moves from routine tool to emergency recovery, and should be exercised occasionally so it is known to work when it is needed.

Worth correcting a misconception recorded here deliberately: the LAN path does not require standing up server infrastructure. `scripts/ota_local.sh` starts `python3 -m http.server` on demand and tears it down afterwards.

### Residual risk

The MQTT command chooses which tag to install, so anyone able to publish to a device topic can force a **downgrade** to any published version, including a known-bad one. Deleting bad pre-releases limits the blast radius, and the newer-only semver comparison discussed in [#0001](0001.md) would close it properly. Worth noting the transport is still plain MQTT on port 1883 with a shared password.

### Cleaning up

Pre-releases can be removed once every test device has moved off them:

```bash
gh release delete v0.0.5-beta1 --yes --cleanup-tag
```

Devices already updated are unaffected — the firmware is in flash. A device that later asks for a deleted tag gets a 404 and fails harmlessly. Do not delete while a device still needs to fetch it.

## Expected behavior

`OTA_VERSION:0.0.5-beta1` on a device topic installs that exact release from GitHub, over TLS validated against the pinned roots, without touching `/releases/latest` and without any local server. The rest of the fleet is unaffected and never sees the pre-release.

## Actual behavior

The only ways to install a test build are a fleet-wide GitHub release, or a LAN push that requires a local HTTP server and trusts any host on the network.

## Notes

- Add a `scripts/ota_version.sh` wrapper alongside `ota_local.sh`, and document the workflow in `OTA.md`: build → `release.sh` (both gates) → `gh release create --prerelease` → `OTA_VERSION:` to one device → verify → delete the pre-release.
- `scripts/release.sh` currently prints publish instructions for a stable release. It should also print the `--prerelease` variant, since that is now the expected default for anything not going fleet-wide.
- Adding a `[env:native]` to `platformio.ini` for the version tests is new ground for this project — `test/` exists but is empty. Keep the native env free of the `esp32c3` build flags so it does not drag Arduino headers into a host build.
- The size and CA gates apply to pre-releases exactly as they do to releases — a beta that does not fit is as useless as a release that does not fit ([#0009](0009.md)).
