# 0003 — Rainbow theme shows a static solid color; slowBlend() frames never reach four of five strips

| | |
|---|---|
| **Status** | open |
| **Module** | LED / FastLED / Rendering |
| **Platform** | ESP32-C3 |
| **First seen** | 2026-08-15 |

## Description

On four of the five installed strips the Rainbow theme renders as one static color — usually solid red — instead of an animated gradient. The `fill_solid()` frame that `onMqttMessage()` writes on a theme switch **does** reach the strip, but no frame written by `slowBlend()` ever does. Only `workbench` animates correctly.

## Long Description

### Symptom

Setting `RAINBOW` leaves the strip a flat, unmoving color. It is not a dim or washed-out rainbow — it is one color, and it does not drift. Switching themes visibly recolors the strip to that theme's first hue and it then freezes again:

| command sent | what appears | that hue is |
|---|---|---|
| `RAINBOW` | solid bright red | `RAINBOW_HUES[0]` = 0 |
| `PINK_PONY` | solid purple | `PINK_PONY_HUES[0]` = 200 |
| `GREEN` | solid green | `GREEN_HUES[0]` = 85 |

Every observed color is exactly the `hues[0]` value that `fill_solid(leds, numLeds, CHSV(newHue, 255, 200))` writes at `src/main.cpp:675`. Nothing that `slowBlend()` produces has ever been observed on these four strips.

### Affected devices

| device | numLeds | ledsPerColor | mirror | IR | status |
|---|---|---|---|---|---|
| kitchen | 240 | 32 | false | false | broken |
| tv | 60 | 10 | false | true | broken |
| desk | 50 | 10 | false | false | broken |
| recycling | 58 | 20 | false | false | broken |
| workbench | 128 | 8 | **true** | true | **works** |

### Ruled out

Each of these was tested live over MQTT against `kitchen`, not merely reasoned about:

- **`ledsPerColor` too large for the strip.** The initial hypothesis was that the gradient's spatial period (`ledsPerColor × hueCount`) exceeded `numLeds`, leaving only a slice of the color wheel on screen. It correlated perfectly with the working/broken split. It is wrong: setting `kitchen` to 30/color — exactly one full 8-hue rainbow across its 240 LEDs — left it solid red. Setting it to 4/color (7.5 full cycles) also left it solid red.
- **Mirror mode.** `workbench` is the only working strip and the only one with `mirrorEnabled`. Enabling mirror on `kitchen` changed nothing.
- **Reboot / crash loop.** Every device was republishing state every ~8 s, which looked like reconnect churn. It was an external Go app (`glowpanel`, `~/Developer/RaspberryPi/glowpanel`) polling `STATUS` to `lights/all/cmd`. With it killed, a 45-second passive listen shows **zero** unprompted publishes — the devices are stable and are not rebooting. The red persists regardless.
- **FastLED power limiting.** `addLeds` registers `MAX_LEDS` (500) while `setMaxPowerInVoltsAndMilliamps(5, 500)` budgets 500 mA, and the 500-LED dark-current term alone consumes the whole budget. Modeling FastLED's `calculate_max_brightness_for_power_mW` gives a scale of 25 for kitchen and 83–92 for the short strips — dim, but proportional across channels. It cannot turn a gradient red.
- **The blend math.** Simulating `slowBlend()` against each device's exact `numLeds` / `ledsPerColor` / `blendOffset` produces a correct full gradient in every case (240 distinct hues for kitchen). The arithmetic is not the fault.

### Where that leaves it

`loop()` demonstrably runs — devices answer `STATUS` within milliseconds, and MQTT is serviced from the same loop that calls `loopLED()`. `ledsEnabled` is true and `currentTheme` is `Rainbow`, so `loopLED()` must reach `slowBlend()` (`src/main.cpp:1016`). Yet `FastLED.show()` from `slowBlend()` produces no visible change while `FastLED.show()` from `onMqttMessage()` does — the same call, differing only in calling context.

Two possibilities remain:

1. `slowBlend()`'s body never executes — i.e. `blendTimeout < now` is somehow never true.
2. It executes and fills `leds[]` correctly, but its `show()` calls do not transmit.

**A test that separates these is already available and needs no firmware change.** The `SET_BRIGHTNESS` handler (`src/main.cpp:603`) calls `FastLED.show()` **without touching `leds[]`**, so it re-transmits whatever `slowBlend()` last wrote:

```bash
./scripts/configure_device.sh kitchen brightness 224   # must differ from current; handler is change-guarded
```

If the strip jumps to a rainbow, `leds[]` holds a correct gradient and the fault is in the transmit path (case 2). If it stays red, `leds[]` holds the solid fill and the fault is upstream (case 1). This was sent to `kitchen` but the result was not observed.

## Steps to reproduce

1. `./scripts/set_theme.sh kitchen RAINBOW`
2. Watch the strip.

## Expected behavior

A smooth rainbow gradient across the strip, rotating slowly (`blendOffset` advances one LED every 500 ms).

## Actual behavior

A solid, static red that never changes until another theme command is sent, at which point it becomes that theme's first hue and freezes again.

## Notes

- Diagnosis is blocked on the ability to iterate firmware on one device — see [#0002](0002.md). The next concrete step is a build that logs, inside `slowBlend()`, whether the `blendTimeout < now` branch is entered and what `blendedHue` values are computed, flashed to `kitchen` alone.
- A latent bug found while investigating, not believed to be this fault but worth fixing: `publishState()` is called from **inside** the MQTT callback (`STATUS` handler, `src/main.cpp:585`). PubSubClient uses one shared buffer for send and receive, so publishing from within the callback — while it still owes a QoS 1 PUBACK — can corrupt that buffer. `glowpanel` publishes `STATUS` at QoS 1, so the fleet was doing this every 8 seconds. State should be published from `loop()` via a pending flag instead.
- Also latent: a retained `FOREST` sits on `lights/all/cmd` while each device topic retains its own theme. Devices subscribe to both on connect, so any reconnect delivers two conflicting theme commands. `scripts/set_theme.sh` publishes with `-r`, and `glowpanel`'s `SetTheme` publishes retained as well (`app.go`).
- `MAX_LEDS` is 500 and `addLeds` registers all 500, so `FastLED.show()` clocks out 500 LEDs' worth of data (~15 ms) regardless of `numLeds`.
